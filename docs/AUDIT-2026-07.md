## 1. Резюме

### Что сделано хорошо

Это не прототип-однодневка. Уровень инженерной культуры здесь заметно выше
среднего для внутренних порталов:

- **Слоистость соблюдена по-настоящему.** `UI → PortalContext → *Repo.ts →
  Supabase` — ни один компонент не ходит в БД напрямую. Это проверено grep'ом
  по проекту, а не только заявлено в документации.
- **Чистая логика реально отделена.** `candidateFilters.ts`,
  `demandAggregate.ts`, `demandRowMeta.ts` и т.д. — без React и без Supabase,
  и именно они покрыты тестами.
- **121 unit-тест в 10 файлах, все зелёные.** Для проекта такого возраста это
  редкость.
- **Миграции — образцовые.** Комментарии объясняют *почему*, а не *что*: почему
  `staffing_demand` без soft-delete, почему обычный `unique` вместо partial
  index (поведение PostgREST при upsert), почему `status` через `CHECK`, а не
  enum. RLS включён с первой миграции.
- **Аудит потребности сделан правильно** — `SECURITY DEFINER` триггеры, у роли
  `authenticated` нет `INSERT`-политики на `staffing_demand_history`. Клиент
  физически не может подделать или пропустить запись в журнале.
- **Секреты не утекли.** `.env*` в `.gitignore`, `supabase/.temp` не в git,
  `service_role` в коде отсутствует, используется только publishable-ключ.
- **Документация актуальна** и совпадает с кодом (проверено выборочно).

### Что блокирует версию 1.0

Пять вещей. Всё остальное — производные от них.

1. 🔴 **Нет модели прав доступа.** Любой авторизованный сотрудник может всё:
   прочитать все персональные данные всех кандидатов, удалить всю потребность,
   архивировать любого кандидата. RLS-политики — `using (true)` для роли
   `authenticated` на всех четырёх таблицах.
2. 🔴 **`supabase/config.toml` разрешает самостоятельную регистрацию**
   (`enable_signup = true`), при том что вся модель безопасности продукта
   построена на том, что регистрации нет. В сочетании с п.1 это означает: кто
   угодно регистрируется → получает полный доступ к базе персональных данных.
3. 🔴 **Половина продукта — выдуманные данные.** Обзор, Аналитика, Маркетинг и
   профиль/команда/интеграции в Настройках показывают вымышленные цифры и
   несуществующие проекты («X5 Group — Уфа», «ВкусВилл», «Ozon Fresh»),
   которых нет в реальном enum. Кнопка «Сохранить изменения» в профиле не
   сохраняет ничего — просто показывает тост.
4. 🟠 **Персональные данные без защиты.** ФИО, телефон, Telegram, зарплатная
   карта хранятся открыто, без журнала доступа, без политики хранения, без
   разграничения. Для коммерческого HR-продукта в РФ это зона 152-ФЗ.
5. 🟠 **Клиент грузит всю базу целиком.** `listCandidates()` тянет всех
   кандидатов через `select("*")` без пагинации и фильтрует их в JavaScript.
   GIN-индекс `idx_candidates_full_name_trgm` построен в БД и **не используется
   ни одним запросом** — поиск идёт в браузере.

## 3. Архитектура

### 3.1 🟠 `PortalContext` — божественный объект

`src/components/portal/context/PortalContext.tsx` — 687 строк, около 60
значений в одном `useMemo`, четыре независимых домена в одном провайдере:
mock-кандидаты, real-кандидаты, справочники, потребность (+ метаданные строк),
плюс сквозное: навигация, тосты, уведомления, плотность таблиц, auth.

Документация честно фиксирует это как тех-долг («пока не требуется»). **Уже
требуется** — по причине производительности, а не эстетики:

`pushToast` вызывает `setToasts` при показе тоста и ещё раз через 2800 мс при
автоскрытии. Оба вызова меняют `value` контекста → перерисовывается всё
поддерево портала, включая матрицу потребности. То есть каждое сохранение
ячейки, показывающее тост, стоит двух полных перерисовок матрицы.

Домены не связаны между собой: тосты не имеют отношения к `demandRows`, но
живут в одном объекте.

### 3.2 🟠 SPA внутри одного роута

Разделы переключаются через `activePage` в состоянии. Последствия:

- **Нет URL у разделов.** Нельзя отправить коллеге ссылку на «Кандидатов»,
  нельзя добавить раздел в закладки. Кнопка «Назад» в браузере уводит с
  портала целиком. Исключение — «Потребность», где фильтры и окно дат
  сериализуются в query-параметры (`demandQueryParams.ts`), но и она живёт на
  `/?section=demand`, а не на `/demand`.
- **Нет разделения кода.** `PortalApp.tsx` статически импортирует все восемь
  разделов, поэтому справочник вакансий на 326 КБ попадает в бандл всем
  пользователям (см. §6.1).
- **Оба дровера кандидатов смонтированы всегда** — и legacy `CandidateDrawer`
  (mock), и `RealCandidateDrawer`.

### 3.3 🟡 Сосуществование mock- и real-слоёв

В `PortalContext` живут одновременно `candidates` (сгенерированные
`generateCandidates()`) и `realCandidates` (Supabase). Mock-слой питает
`AnalyticsTabs`, `CommandPalette` и старый `CandidateDrawer`.

Практическое следствие: **командная палитра ищет по выдуманным кандидатам**.
Пользователь жмёт `⌘K`, набирает фамилию реального кандидата — не находит
ничего, потому что ищется по `generateCandidates()`.

### 3.4 🟡 Нет границ ошибок

Ни одного `error boundary` в проекте. Любое исключение при рендере любого
раздела обрушивает весь портал в белый экран. Для продукта, где рекрутер
работает в одной вкладке весь день, это дорого.

### 3.5 ⚪ `SettingsSection` монолитен

406 строк, три компонента в одном файле (`SettingsSection`,
`CandidateListsPanel`, `InviteModal`). Нарушает собственное правило проекта
(CLAUDE.md §5) о вынесении подкомпонентов. При этом единственная его часть,
работающая на реальных данных — `CandidateListsPanel` — как раз и заслуживает
отдельного файла.

## 4. База данных

Схема продумана. Замечания — про то, чего в ней ещё нет.

### 4.1 🔴 Нет пользователей, ролей и профилей

В `staffing_demand_history` аккуратно пишется `changed_by uuid` (из
`auth.uid()`), но **прочитать имя по этому uuid неоткуда** — таблицы профилей
не существует. Дровер истории может показать только UUID.

Нет таблицы `profiles`/`app_users`, нет ролей, нет привязки сотрудника к
проектам. Раздел «Команда и роли» в Настройках — статический массив в TSX.

### 4.2 ✅ `candidate_project` — enum, а не справочник — **решено (TASK-009)**

Один enum обслуживал и `candidates.project`, и `staffing_demand.project`
(позже — и `addresses.project`). Добавление проекта клиентом = `ALTER TYPE
... ADD VALUE` + миграция + деплой + регенерация типов. Для коммерческого
продукта, где заказчик заводит проекты сам, это неприемлемо.

Симптом уже виден: mock-константы (`constants.ts`) содержат «X5 Group»,
«ВкусВилл», «Ozon Fresh», которых в enum нет, — два несогласованных списка
проектов в одном приложении.

**Решено** миграцией `20260731120000_unify_project_free_text.sql`: все три
колонки переведены на `text` с общим управляемым справочником
`candidate_list_options` (`list_type = project`). Проект добавляется в
«Настройки → Списки → Проекты» без миграции и деплоя. Enum остался в схеме
неиспользуемым — см. `database/schema.md`. Замечание про mock-константы
`constants.ts` остаётся в силе: это отдельный demo-слой Обзора/Маркетинга/
Аналитики, он по-прежнему не связан с реальным списком.

### 4.3 🟠 Рассогласование типов между связанными таблицами

| Таблица | Колонка | Тип |
|---------|---------|-----|
| `staffing_demand` | `project` | `text` (было enum `candidate_project` до TASK-009) |
| `staffing_demand_rows` | `project` | `text` |

Обе описывают один и тот же «проект», связываются по значению, FK нет.
Миграция это оговаривает («сознательное отличие»), но следствие остаётся:
запись в `staffing_demand_rows` с проектом, которого нет в матрице,
вставится успешно и навсегда останется сиротой — её статус и комментарий не
отобразятся ни на одной строке.

После TASK-009 типы совпали (обе колонки — `text`), но сама проблема стала
шире, а не исчезла: раньше enum хотя бы гарантировал, что значение в
`staffing_demand.project` из фиксированного набора. Теперь оба поля —
свободный текст, и рассинхронизация возможна с обеих сторон. Это тот же
класс проблемы, что 4.4 ниже (`city` без нормализации), и решается тем же
способом — отдельной таблицей проектов с FK.

### 4.4 🟠 `city` — свободный текст без нормализации

`city` — `text` во всех таблицах, FK на `candidate_list_options` намеренно
нет. «Москва», «москва» и «Москва » (с пробелом) создадут **три разные строки
матрицы** для одного города, и никто этого не заметит, пока не разъедутся
итоги. `staffing_demand.city` не имеет ни `check`, ни триггера нормализации.

### 4.5 🟠 У кандидатов нет журнала изменений

«Потребность» получила полноценный аудит (кто, что, когда, старое/новое
значение). У `candidates` — таблицы с персональными данными и юридически
значимыми датами (`first_shift_at`) — журнала нет вообще. Если запись
изменили или архивировали ошибочно, восстановить прежнее значение и автора
невозможно.

Это инверсия приоритетов: аудит стоит там, где он менее нужен.

### 4.6 🟡 Нет ограничений длины у текстовых полей

`comment` в `staffing_demand_rows` защищён `check (char_length <= 2000)` —
правильно. Но `candidates.full_name`, `phone`, `comment`, `salary_card` и
`staffing_demand.city` — `text` без ограничений. Запись на 10 МБ в `full_name`
пройдёт: клиент пишет в PostgREST напрямую, серверной валидации нет.

### 4.7 🟡 Нет `updated_by`

`updated_at` поддерживается триггерами везде, где нужно. Кто именно изменил
запись — не хранится ни в одной таблице (кроме журнала потребности).

## 5. Безопасность

### 5.1 🔴 Модель авторизации отсутствует

Все политики на всех четырёх таблицах сводятся к «роль `authenticated` может
всё»:

```sql
create policy "authenticated_select_candidates"
  on public.candidates for select to authenticated using (true);
create policy "authenticated_update_candidates"
  on public.candidates for update to authenticated using (true) with check (true);
```

Комментарии в миграциях объясняют, что `using (true)` безопасен, потому что
применяется к `authenticated`, а не к `anon`. **Это верно только для модели
«все сотрудники равнодоверенны».** Для коммерческого продукта это означает:

- рекрутер видит персональные данные всех кандидатов всех проектов;
- любой сотрудник может удалить всю потребность одним запросом (`delete` на
  `staffing_demand` разрешён `authenticated` без условий);
- любой может переименовать/деактивировать справочники;
- нет разделения «свои кандидаты / чужие», хотя поля `recruiter`, `manager`,
  `coordinator` для этого уже есть.

Первая миграция сама указывает верное направление, которое так и не было
реализовано:

> `Consider row-level scoping by recruiter/manager/coordinator if staff should
> only see their own candidates.`

### 5.2 🔴 `enable_signup = true` в конфигурации Supabase

`supabase/config.toml`:

```toml
[auth]
enable_signup = true
[auth.email]
enable_signup = true
enable_confirmations = false
```

Вся документация продукта утверждает: «учётные записи заводятся вручную,
самостоятельной регистрации нет». Конфигурация утверждает обратное.

Оговорка: `config.toml` управляет локальным стеком (`supabase start`);
настройки размещённого проекта задаются отдельно в Dashboard. Но:

1. современные версии CLI умеют пушить конфиг в удалённый проект;
2. **нужно отдельно проверить, что на боевом проекте регистрация выключена** —
   по репозиторию это не подтверждается;
3. в сочетании с §5.1 цена ошибки максимальная: регистрация + `using (true)` =
   полный доступ к базе персональных данных для любого желающего.

Сопутствующее в том же файле: `minimum_password_length = 6` (страница смены
пароля требует 8 — но только на клиенте), `enable_confirmations = false`
(email не подтверждается), `secure_password_change = false` (смена пароля не
требует повторной аутентификации), MFA не включён.

### 5.3 🟠 Нет заголовков безопасности

`next.config.ts` пуст:

```ts
const nextConfig: NextConfig = {
  /* config options here */
};
```

Нет `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`,
`Strict-Transport-Security`, `Referrer-Policy`, `X-Content-Type-Options`.
Портал с персональными данными можно поместить в `<iframe>` на чужом сайте.

### 5.4 🟠 Вся запись идёт из браузера напрямую в PostgREST

Между пользователем и базой нет серверного слоя. Ни одного Route Handler, ни
одного Server Action — репозитории вызывают `createClient()` из
`lib/supabase/client.ts` (браузерный).

Следствия:

- клиентские проверки (`isValidPlannedCount`, `normalizeComment`,
  `isCommentTooLong`) — **рекомендательные**. Единственная реальная защита —
  `CHECK`-ограничения, которых мало (§4.6);
- нет прикладного rate limiting: скрипт с валидной сессией может писать в базу
  с любой скоростью;
- бизнес-правила нельзя изменить без деплоя клиента.

### 5.5 🟡 Сырые ошибки Supabase показываются пользователю

Паттерн повторяется во всём `PortalContext`:

```ts
pushToast(e instanceof Error ? e.message : "Не удалось сохранить", "error");
```

В тост попадает текст ошибки PostgREST — имена ограничений, колонок, иногда
фрагменты SQL. Это и утечка структуры схемы, и плохой UX (пользователь видит
`duplicate key value violates unique constraint "staffing_demand_project_city..."`).

### 5.6 🟡 Middleware ходит в Supabase на каждый запрос

`updateSession` вызывает `supabase.auth.getUser()` — сетевой запрос к Supabase
Auth — при каждом запросе, подпадающем под matcher. Это и задержка на каждой
навигации, и жёсткая зависимость: недоступен Supabase Auth → недоступен весь
портал, включая страницу входа.

### 5.7 🟡 Нет автовыхода по бездействию

`jwt_expiry = 3600` с ротацией refresh-токена означает, что сессия живёт,
пока пользователь возвращается. Для системы с персональными данными на
разделяемом рабочем месте нужен явный таймаут бездействия.

### 5.8 🟡 Нет журнала чтения персональных данных

Кто и когда открыл карточку кандидата и увидел телефон — не фиксируется.
Для 152-ФЗ и для разбора инцидентов это обычно требуется.

### 5.9 ✅ Что сделано правильно

- `service_role` не используется нигде в коде — только publishable-ключ + RLS.
- `.env*` в `.gitignore`, `.env.local` не в индексе git, `supabase/.temp` тоже.
- Восстановление пароля не раскрывает существование email — и на уровне
  Supabase API, и в тексте сообщения («Если такой email зарегистрирован…»).
  Классификация ошибок в `forgot-password/page.tsx` сделана аккуратно.
- Редирект в middleware сохраняет обновлённые auth-cookie (`redirectTo`
  копирует cookie из `supabaseResponse`) — типичная ошибка, которой здесь нет.
- `/update-password` намеренно оставлен доступным для авторизованной
  recovery-сессии — тонкий момент, обработан верно и объяснён комментарием.
- Журнал потребности защищён от подделки клиентом (`SECURITY DEFINER` +
  отсутствие `INSERT`-политики).

## 6. Производительность

### 6.1 🟠 326 КБ справочника вакансий грузятся всем и всегда

`src/lib/portal/vacancyData.ts` — 5870 строк, 326 КБ. Он импортируется
`VacanciesSection`, который статически импортирован в `PortalApp`. Поскольку
портал — один роут без разделения кода, **эти данные попадают в бандл каждому
пользователю на первой загрузке**, даже если он никогда не откроет раздел
«Описание вакансий».

Подтверждено: строка `sourceSheet` найдена в чанке на 406 КБ. Всего
клиентского JS — 1 274 КБ.

Это статический справочник, идеальный кандидат либо на серверный компонент,
либо на динамический импорт, либо на перенос в БД.

### 6.2 🟠 Матрица потребности рендерится целиком, без виртуализации

Окно по умолчанию — 60 дней (`−14/+45`, `demandWindow.ts`). Каждая ячейка —
компонент `DemandCell` с четырьмя `useState`, двумя `useRef` и `useEffect`.
При 12 проектах × ~10 городов это порядка **7 200 ячеек**, каждая со своим
состоянием, плюс `DemandCellMenu` в каждой заполненной.

Ни `React.memo` на `DemandCityRow`/`DemandCell`, ни виртуализации нет. В
сочетании с §3.1 (перерисовка всего дерева на каждый тост) это главный
источник тормозов интерфейса.

### 6.3 🟠 Кандидаты грузятся целиком и фильтруются в браузере

```ts
export async function listCandidates(): Promise<Candidate[]> {
  const { data, error } = await supabase
    .from("candidates").select("*").order("created_at", { ascending: false });
```

Ни `range()`, ни `limit()`, ни серверных фильтров. Поиск, фильтрация по
проекту/стадии и подсчёт метрик выполняются в JavaScript над полным массивом.
На 10 000 кандидатов это мегабайты персональных данных по сети при каждом
монтировании провайдера.

Отдельно обидно: **GIN trigram-индекс по `full_name` построен и не
используется ни одним запросом** — поиск по имени идёт через
`haystack.includes(q)` в `candidateFilters.ts`. Индекс сейчас только замедляет
запись.

То же касается `listStaffingDemandRowsMeta()` — все метаданные строк без
ограничений.

### 6.4 🟡 Шрифты Google загружаются и не используются

`layout.tsx` подключает `Geist` и `Geist_Mono` и вешает переменные на `<html>`.
`globals.css` пробрасывает их в тему Tailwind. Но портал рисуется внутри
`.portal-root`, где:

```css
.portal-root { font-family: var(--portal-font); }
```

а `--portal-font` — системный стек (`-apple-system, ... Segoe UI, Roboto…`).
`body` в `globals.css` вообще задаёт `Arial`. Итог: два веб-шрифта скачиваются
на каждой загрузке и **не отрисовывают ни одного символа портала**.

### 6.5 🟡 Синхронизация URL срабатывает на каждый символ

В `DemandSection` эффект синхронизации вызывает `router.replace(...)` при
изменении любого фильтра, включая `search`. Каждое нажатие клавиши в поиске —
новая запись в history API и полный ре-рендер раздела. Дебаунса нет.

### 6.6 ⚪ Роут `/` полностью динамический

`page.tsx` вызывает `getUser()`, поэтому `/` помечен `ƒ (Dynamic)` — никакого
статического кеша. Само по себе оправданно, но в сумме с §5.6 (ещё один
`getUser()` в middleware) каждая загрузка портала стоит **двух** обращений к
Supabase Auth.

## 7. UX и доступность

### 7.1 🔴 Выдуманные данные в продуктовом интерфейсе

Наиболее опасная для продаж проблема — не техническая.

| Раздел | Что показывается |
|--------|------------------|
| Обзор | Все 8 плиток — константы в TSX: «Общая потребность 214», «Фактические выходы 141», «Выполнение плана 84%». Блок «Проекты в зоне риска» — вымышленный массив `RISKS` |
| Аналитика | Работает на `generateCandidates()` / `generateDemand()` |
| Маркетинг | Константа `CHANNELS` с выдуманными бюджетами |
| Настройки → Профиль | Захардкожено «Дмитрий Кузнецов», «dmitry@vkr.pro». Кнопка «Сохранить изменения» показывает тост и ничего не сохраняет |
| Настройки → Команда | Статический массив из 5 человек, выпадающий список ролей ни на что не влияет |
| Настройки → Интеграции | Четыре несуществующие интеграции с работающими переключателями и тостами «Интеграция подключена» |

Отдельно: в mock-данных фигурируют проекты **X5 Group, ВкусВилл, Ozon Fresh**,
которых нет в enum `candidate_project`. Пользователь видит на «Обзоре» риски
по проектам, которых нет в его базе.

Переключатель, который делает вид, что подключил интеграцию с 1С, — это не
«заглушка», это ложное утверждение в интерфейсе платного продукта.

### 7.2 🟠 Доступность: модальные окна и таблицы

- **`Modal`**: нет `role="dialog"`, нет `aria-modal`, нет ловушки фокуса, нет
  возврата фокуса на триггер при закрытии. Фокус остаётся на фоне — с
  клавиатуры можно «уйти» за модалку.
- **`Drawer`**: то же самое (есть только `aria-label`), плюс `aria-label`
  жёстко зашит как «Карточка кандидата» — а дровер переиспользуется для
  истории изменений потребности.
- **Строки таблицы кандидатов**: `<tr onClick={...}>` без `tabIndex`, без
  `role`, без обработчика клавиатуры. **Открыть карточку кандидата с
  клавиатуры невозможно.**
- **Матрица потребности**: `<td tabIndex={0}>` — редактирование с клавиатуры
  работает, но нет навигации стрелками между ячейками, что для таблицы-сетки
  на 7 000 ячеек критично.
- Иконочные кнопки в `Topbar` частично без `aria-label` (кнопка профиля).

### 7.3 🟠 Нет тёмной темы

`portal-tokens.css` определяет только светлую палитру. При этом в
`globals.css` остался boilerplate Next.js:

```css
@media (prefers-color-scheme: dark) {
  :root { --background: #0a0a0a; --foreground: #ededed; }
}
```

`body` получает тёмный фон, а `.portal-root` перекрывает его светлым `--bg`.
Для HR-специалиста, работающего в системе весь день, отсутствие тёмной темы —
реальная жалоба, а не украшение.

### 7.4 🟡 Конкурентное редактирование теряет данные

Два координатора, открывшие матрицу одновременно, пишут в одну ячейку через
`upsert` без проверки версии. Побеждает последний, первый не узнает, что его
значение перезаписано. Данные в `demandRows` обновляются только при ручном
`refreshDemand()` — real-time подписок Supabase нет.

То же для карточки кандидата: `saveRealCandidate` отправляет весь черновик
целиком, затирая правки, сделанные другим сотрудником за время редактирования.

### 7.5 🟡 Архивирование кандидата — в один клик, без подтверждения

Кнопка «Отметить как вышедшего» сразу пишет в БД. Отмена возможна (кнопка
«Восстановить»), но подтверждения нет, а формулировка кнопки не совпадает с
терминологией остального интерфейса («архив» в фильтрах против «вышел» в
карточке и «(вышел)» в таблице).

### 7.6 🟡 Тосты — единственный канал обратной связи

Все ошибки показываются тостом на 2 800 мс и исчезают. Если пользователь
отвлёкся — сообщение об ошибке сохранения потеряно навсегда, при этом данные
не сохранены. Нет центра уведомлений об ошибках, нет повторной попытки.

### 7.7 🟡 Таблица кандидатов бедна для реестра

Нет сортировки по колонкам, нет массовых действий, нет сохранённых фильтров,
нет выбора видимых колонок. Пагинация — только «Показать ещё» по 20. Экспорт
CSV выгружает фиксированный набор из 14 полей.

### 7.8 ⚪ Командная палитра ищет по mock-данным

См. §3.3 — `⌘K` не находит реальных кандидатов.

### 7.9 ⚪ Разное

- `PageHead` на «Обзоре» содержит зашитую дату: «Понедельник, 20 июля 2026».
- Мобильная версия: 60 колонок матрицы на телефоне нечитаемы даже с
  горизонтальным скроллом; режимы «Неделя»/«Месяц» не реализованы.
- Нет структуры i18n (весь текст зашит по-русски). Приемлемо для RU-only, но
  при выходе за пределы РФ придётся переписывать всё.

## 8. Качество и процессы

### 8.1 🟠 Нет CI

`.github/workflows` отсутствует. `tsc`, `lint`, `test` и `build` запускаются
только вручную. При деплое на Vercel по push в `main` единственный барьер —
сборка; упавшие тесты не остановят выкладку.

### 8.2 🟠 Тесты покрывают только чистую логику

121 тест — все на `.ts`-файлы без React. Нет:

- тестов компонентов (ни одного `@testing-library/react`);
- E2E-сценариев (вход, создание кандидата, редактирование ячейки);
- **тестов RLS-политик** — самой критичной части системы безопасности.
  Проверить, что рекрутер не видит чужих кандидатов, сейчас нечем.

### 8.3 🟡 Нет мониторинга и логирования

Ни Sentry, ни аналога. Ошибка у пользователя не оставляет следа нигде:
`console.log`/`console.error` в коде тоже нет (что чисто, но означает полную
слепоту в проде).

### 8.4 ⚪ README не соответствует проекту

`README.md` — стоковый текст `create-next-app`: «Проект на Next.js с App
Router, TypeScript и Tailwind CSS», структура `src/app/`, `public/`. Он
противоречит `CLAUDE.md` (где Tailwind явно ограничен app-оболочкой) и не
упоминает ни Supabase, ни разделы портала, ни `npm run test`.

### 8.5 ⚪ Нет скрипта проверки типов

`package.json` не содержит `typecheck`; документация вынуждена писать
`npx tsc --noEmit`. Мелочь, но она же попадёт в CI.
