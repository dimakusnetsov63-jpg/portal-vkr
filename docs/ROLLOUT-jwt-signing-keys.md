## Чем этот выкат принципиально отличается от C-3/C-4

В C-3/C-4 старый и новый путь могли жить одновременно (`anon` и
`portal_auth_caller` — оба валидны, пока `anon` не отозван отдельным
шагом) — это давало мягкое окно перехода без единой точки, где всё
ломается разом.

**Здесь так не получится.** Алгоритм и `kid` — атомарная пара внутри
одного токена: он либо ES256 с конкретным `kid`, либо HS256 старым
секретом. Гибридного пути в коде нет и не должно быть (см. Definition of
Done — «`SUPABASE_JWT_SECRET` больше нигде не используется», без временных
флагов). Значит **вся подготовка на стороне Supabase и Vercel обязана
завершиться до деплоя кода**, а не параллельно с ним.

**Режим отказа тоже другой.** В C-3/C-4 поломка означала «нельзя войти».
Здесь вход по-прежнему проверяет пароль сам портал (это не зависит от
JWT) — сломается **следующий шаг**: `resolveSession`/`portal_session_context`
и любой запрос к данным начнут получать отказ от PostgREST, потому что
токен подписан ключом, которого PostgREST не знает. Пользователь увидит:
вход как будто прошёл, а дальше — пустые разделы или цикл на `/login`.

Код не трогается. Старый HS256-путь продолжает работать всё это время.

### A.1. Мигрировать легаси-секрет

Dashboard → Project Settings → API → **JWT Signing Keys** → **Migrate JWT
secret**.

- [x] Выполнено — но по факту не нашей рукой: на момент проверки Dashboard
      уже показывал `CURRENT` ECC-ключ и `PREVIOUS` HS256-секрет — миграция

      этой задачи. Не помешало и не потребовало действий: `PREVIOUS`

      требовалось на этом шаге.
- ⚠️ Этот шаг может автоматически создать **свой** асимметричный ключ
      (сгенерированный самим Supabase) в состоянии `standby`. **Его
      приватная половина недоступна нам** — не пытаться использовать этот
      ключ для подписи, он не для этого. Наш собственный ключ — отдельный,
      следующим шагом. Подтверждено по факту: публичный JWKS этого ключа
      содержит только `"key_ops": ["verify"]`.

### A.2. Сгенерировать собственный ключ ES256

Локально, не в проекте (ключ не коммитится):

```bash
supabase gen signing-key --algorithm ES256
```

- [x] Вывод (JWK, включая `kid`) сохранён во временном защищённом месте —
      он понадобится на шаге A.3 (импорт в Dashboard) и A.4 (переменная
      Vercel) и **больше нигде не будет показан** (Supabase не отдаёт
      приватный ключ обратно после импорта).

### A.3. Импортировать публичную часть в Dashboard

JWT Signing Keys → **Import key** (или аналогичный пункт) → вставить JWK
из шага A.2.

- [x] Ключ появился в списке, статус `standby`. UI Dashboard в момент
      выполнения не показывал отдельного пункта импорта в основном
      диалоге создания ключа (только автогенерацию по алгоритму) — путь
      нашёлся через чекбокс «Import an existing private key» в том же
      диалоге, после чего вставка JWK и импорт прошли штатно.
- [x] Записан `kid` этого ключа: `9b5f6ba2-c210-467c-98f9-b427acca804f` —
      совпадает со значением внутри JWK из A.2 (там же и хранится, отдельно
      не генерировался).

**Важный технический нюанс, который проверяется фактически, а не
предполагается:** по документации Supabase, ключ в состоянии `standby`
уже публикуется в JWKS (то есть уже доверен для **проверки** подписи) —
кнопка **Rotate keys** переключает только то, каким ключом **GoTrue**
подписывает *новые* токены, что порталу не важно вообще (GoTrue не
используется). Это значит промотировать ключ через «Rotate keys» скорее
всего не требуется. Явного прямого подтверждения в документации для
случая «сторонний потребитель, не GoTrue» нет — поэтому это не
принимается на веру, а **проверяется первым же действием в фазе B**
(B.2), с готовым откатом, если предположение не подтвердится.

### B.2. Первая проверка — сразу после деплоя, автоматически

Как только деплой готов (Vercel), сразу, до любых действий пользователя:
запрос с заведомо неверным паролем к `/api/auth/login`.

- Ожидается **обычная** бизнес-ошибка: `401 {"error":"Неверный логин или
  пароль"}` — это доказывает, что `signPortalServiceJwt()` подписал ES256-
  токен, PostgREST его принял, и `portal_login` реально выполнился (пароль
  проверен и отвергнут).
- Если вместо этого `502 {"error":"Сервис авторизации недоступен..."}` —
  значит `session.ts`/`login()` поймал ошибку на уровне вызова RPC:
  PostgREST не принял токен (неверный `kid`, ключ не в `standby`/не
  импортирован, либо `SUPABASE_JWT_PRIVATE_JWK` не долетел до Vercel).
  **Это сигнал к немедленному откату** — см. раздел «Откат», шаг 1,
  выполнить сразу, разбираться потом.

Это тот же принцип, что использовался при верификации C-3/C-4: сначала
дешёвая автоматическая проверка, потом дорогая ручная.

## Ротация (для будущего использования, не выполняется сейчас)

1. `supabase gen signing-key --algorithm ES256` — новая пара.
2. Импортировать в Dashboard как ещё один `standby`-ключ.
3. Задеплоить код с новым `SUPABASE_JWT_PRIVATE_JWK` — старый ключ
   остаётся доверенным, уже выпущенные токены (TTL 15 и 5 минут) не рвутся.
4. Подождать окно перекрытия — с учётом коротких TTL портала достаточно
   20–30 минут (не «час+15 минут» из примера документации Supabase,
   рассчитанного на часовые токены Auth).
5. Отозвать старый ключ в Dashboard.
6. Убедиться, что портал по-прежнему работает (тот же B.2+B.3 набор).

## Откат

Тот же принцип, что в `ROLLOUT-login-rate-limit.md`: **не отзывать старый
ключ, пока новая схема не отработала контролируемое время.** Пока legacy
HS256-секрет не отозван в Dashboard, откат бесплатен.

1. **Откатить деплой в Vercel** (Deployments → предыдущий → Promote to
   Production). Работает мгновенно, если легаси-секрет ещё не отозван —
   старый код снова читает `SUPABASE_JWT_SECRET` и подписывает HS256,
   который PostgREST всё ещё принимает.
2. Если легаси-секрет **уже отозван**, а откат всё равно нужен —
   реактивировать его в Dashboard (Supabase хранит отозванный ключ, не
   удаляет физически) — только затем откатывать деплой.
3. Отзыв ES256-ключа в Dashboard — последний шаг, а не первый: только
   когда откат подтверждён рабочим, чтобы не остаться без единого
   доверенного ключа посередине инцидента.
