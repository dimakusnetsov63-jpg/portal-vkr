# Перенос проекта на другой компьютер

Пошаговая инструкция: как поднять портал ВКР на новой машине с нуля.
Практический workflow после установки — [`DEVELOPMENT.md`](DEVELOPMENT.md).

Главное в двух строках: **код едет через Git, а не копированием папки**.
Руками переносятся только секреты (`.env.local`) и, при желании, локальные
настройки инструментов. `node_modules`, `.next`, `.vercel` копировать нельзя
— они пересоздаются на новой машине.

---

## 1. Что переносим, а что нет

| Объект | Как переносится | Почему |
|---|---|---|
| Исходный код, документация, миграции | `git clone` | Единственный источник истины — репозиторий |
| `.env.local` (секреты) | **вручную**, вне git и вне чатов | В `.gitignore`; в репозиторий не попадает никогда |
| `node_modules/` | не переносить, ставится `npm ci` | Бинарные зависимости привязаны к ОС/платформе |
| `.next/`, `tsconfig.tsbuildinfo` | не переносить | Кэш сборки, пересоздаётся |
| `.vercel/` | не переносить, при нужде `vercel link` | Привязка к проекту Vercel, восстанавливается командой |
| `.claude/settings.local.json` | по желанию, вручную | Локальные настройки Claude Code, не в git |
| Незакоммиченные рабочие файлы | вручную или коммитом | См. шаг 2 |

---

## 2. Что сделать на **старом** компьютере (до переезда)

1. Убедиться, что нет несохранённой работы:

```bash
git status --short
```

2. Убедиться, что всё запушено (команда должна вывести пустоту):

```bash
git log --oneline origin/main..HEAD
```

Если что-то есть — закоммитить и запушить, иначе эти изменения на новой
машине просто не появятся.

3. Скопировать содержимое `.env.local` в надёжное место — менеджер паролей
   или защищённый носитель. **Не отправлять в мессенджер, не коммитить, не
   вставлять в чат с AI.** Файл содержит приватный ключ подписи токенов.

4. Отдельно решить судьбу незакоммиченных файлов вне git (сейчас в корне
   лежит `vacancy-import-preview.json` — это разовый результат импорта
   вакансий, а не часть проекта; нужен — скопировать вручную).

## 3. Что установить на **новом** компьютере

| Инструмент | Версия | Обязателен | Зачем |
|---|---|---|---|
| **Node.js** | 24.x (см. `.nvmrc`, `engines` в `package.json`) | да | Сборка и запуск |
| **npm** | идёт с Node (11.x) | да | Зависимости |
| **Git** | любая свежая | да | Клонирование, коммиты |
| Редактор (VS Code) + Claude Code | — | по желанию | Разработка |
| **Docker Desktop** | — | нет | Только для `npm run test:rls` (эфемерный Supabase) |
| Vercel CLI (`npm i -g vercel`) | — | нет | `vercel env pull`, привязка к проекту |

Supabase CLI отдельно ставить не нужно — он в `devDependencies`,
вызывается через `npx supabase ...`.

Проверка после установки:

```bash
node -v && npm -v && git --version
```

`node -v` должен показать `v24.*`. Если стоит другая версия — поставить 24
(на Windows удобно через [nvm-windows](https://github.com/coreybutler/nvm-windows):
`nvm install 24 && nvm use 24`).

## 4. Клонирование

Каталог лучше выбрать короткий и **не внутри OneDrive/Яндекс.Диска** —
синхронизация папок с сотнями тысяч файлов ломает сборку и тормозит
`npm ci`. На старой машине проект лежал в `C:\dev\portal-vkr`.

```bash
git clone https://github.com/dimakusnetsov63-jpg/portal-vkr.git C:/dev/portal-vkr
```

Затем:

```bash
cd C:/dev/portal-vkr && npm ci
```

`npm ci` (а не `npm install`) ставит ровно те версии, что зафиксированы в
`package-lock.json`, — без «тихого» обновления зависимостей.

Настроить подпись коммитов, если это новая машина:

```bash
git config user.name "Имя Фамилия" && git config user.email "you@example.com"
```

## 5. Файл `.env.local`

Создать в корне проекта файл `.env.local` (в `.gitignore`, коммитить
нельзя) с тремя обязательными переменными:

```
NEXT_PUBLIC_SUPABASE_URL=<URL проекта Supabase>
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable-ключ>
SUPABASE_JWT_PRIVATE_JWK=<приватный ключ ES256 в формате JWK, одной строкой>
```

Откуда брать значения:

- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` —
  Supabase Dashboard → Project Settings → API. Восстанавливаются в любой
  момент.
- `SUPABASE_JWT_PRIVATE_JWK` — **из Dashboard не восстанавливается**:
  Supabase хранит только публичную половину ключа (Project Settings → API →
  JWT Signing Keys), приватная есть только у портала. Взять её со старого
  компьютера (шаг 2) либо из переменных окружения Vercel:

```bash
vercel env pull .env.local
```

  Если приватный ключ утерян — придётся выпускать новую пару ключей по
  процедуре из [`ROLLOUT-jwt-signing-keys.md`](ROLLOUT-jwt-signing-keys.md),
  а не подбирать значение.

`VERCEL_OIDC_TOKEN`, если он есть в старом файле, переносить не нужно — его
создаёт `vercel env pull` / `vercel dev`, он короткоживущий и для
`npm run dev` не требуется.

Почему это важно понимать заранее: без переменных Supabase приложение
падает с понятной ошибкой `Missing environment variable…`, а вот без
корректного `SUPABASE_JWT_PRIVATE_JWK` симптом другой и обманчивый — **вход
проходит, а данные не грузятся** (`/api/auth/token` → 500, запросы к
Supabase → 401).

## 6. Проверка, что всё поднялось

По порядку, каждая команда должна завершиться без ошибок:

```bash
npm run typecheck
```

```bash
npm run lint
```

```bash
npm test
```

```bash
npm run build
```

Затем dev-сервер:

```bash
npm run dev
```

Открыть `http://localhost:3000`, войти существующей учётной записью и
убедиться, что данные в разделах «Кандидаты» / «Потребность» / «Адреса»
действительно загрузились (пустой список при успешном входе — типичный
признак проблемы с `SUPABASE_JWT_PRIVATE_JWK`, а не «нет данных»).

Отдельная база на новой машине не нужна: проект работает с тем же облачным
Supabase, что и раньше. Никаких миграций при переезде применять не надо.

## 7. Необязательные шаги

- **Vercel**: привязать локальную папку к проекту хостинга —

```bash
vercel link
```

  Нужен только для `vercel env pull` и ручных деплоев; автодеплой из `main`
  работает и без него.

- **Supabase CLI**: понадобится при регенерации типов
  (`npx supabase gen types typescript`) — потребует логина
  (`npx supabase login`).

- **RLS-тесты** (`npm run test:rls`): требуют запущенного Docker Desktop и
  локального Supabase (`npx supabase start`). Без Docker этот набор тестов
  просто не запускается; на обязательные проверки из §6 он не влияет.

- **Claude Code**: скопировать `.claude/settings.local.json` со старого
  компьютера, если там были настроенные разрешения. `.claude/launch.json`
  уже в репозитории.

## 9. Типичные проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| `Missing environment variable: NEXT_PUBLIC_SUPABASE_*` | Нет `.env.local` или опечатка в имени | Проверить имена переменных дословно (§5) |
| Вход прошёл, но все разделы пустые; в консоли 401 | Неверный или отсутствующий `SUPABASE_JWT_PRIVATE_JWK` | Перенести приватный ключ; проверить, что публичная половина с тем же `kid` есть в Supabase |
| `EADDRINUSE :3000` | Порт занят другим процессом | Закрыть процесс или `npm run dev -- -p 3001` |
| `npm ci` падает на нативных пакетах | Не та версия Node | Перейти на Node 24 (`nvm use 24`), удалить `node_modules`, повторить |
| Сборка тормозит, файлы «пропадают» | Проект внутри OneDrive/облачной папки | Перенести в локальный путь вроде `C:\dev\portal-vkr` |
| `supabase` команда не найдена | CLI стоит локально, не глобально | Вызывать через `npx supabase ...` |
