# Бэкенд

Всё, что между интерфейсом и Postgres. Схема данных — [`../database/schema.md`](../database/schema.md),
политики доступа — [`../database/policies.md`](../database/policies.md).

## Главное, что нужно понять сразу

**Бэкенда почти нет.** Данные браузер читает и пишет у PostgREST (Supabase)
напрямую, защита данных — RLS на стороне Postgres. Единственное исключение —
три маршрута авторизации в `src/app/api/auth/`: они существуют только потому,
что токен сессии обязан лежать в httpOnly-cookie, а секрет подписи JWT не
должен уезжать в браузер. Ни один маршрут не проксирует данные.

Из этого следуют два практических правила:

1. **Любая проверка, написанная в React, — не защита, а удобство.** Валидацию,
   на которую вы полагаетесь, нужно дублировать `CHECK`-ограничением в схеме.
   Так сделано, например, с длиной комментария (2000 символов — и в
   `demandRowMeta.ts`, и в `CHECK` таблицы).
2. **Ключ, лежащий в браузере, публичный по определению.** Поэтому в коде
   используется только publishable-ключ, а `service_role` не применяется
   нигде — см. [`ADR-002-auth.md`](decisions/ADR-002-auth.md).

## Слои

```
Компонент раздела
  └─ usePortal()                    ← единственная точка входа для данных
       └─ lib/supabase/*Repo.ts     ← весь SQL-подобный код здесь
            └─ lib/supabase/client.ts (браузер) | server.ts (сервер)
                 └─ PostgREST → Postgres (RLS + триггеры)
```

Компонент не обращается к Supabase напрямую — никогда. Репозиторий не знает
про React. Контекст склеивает одно с другим и держит клиентский кэш.

Единственное осознанное исключение: `DemandHistoryDrawer` вызывает репозиторий
напрямую, потому что история грузится лениво при открытии и класть её в
глобальный контекст незачем.

## Клиенты Supabase

| Файл | Где работает | Особенности |
|---|---|---|
| `client.ts` → `createClient()` | браузер | данные, типизирован `Database`. Токен берётся из `accessToken.ts` |
| `client.ts` → `createPortalAuthClient()` | браузер | RPC управления пользователями, типизирован `PortalAuthDatabase` |
| `lib/auth/session.ts` | сервер и middleware | клиент без сессии (роль `anon`) для `portal_login` / `portal_session_context` / `portal_logout` |

Отдельного `server.ts` больше нет: Server Components данных не читают —
`page.tsx` спрашивает только текущую сессию.

Переменные окружения читаются **только через статический `process.env.X`**
(`env.ts`). Динамический доступ `process.env[name]` Turbopack не инлайнит в
клиентский бандл, и переменная окажется `undefined` в браузере — это уже
случалось, поэтому в `env.ts` стоит соответствующий комментарий.

## Репозитории

Правила:

1. Один файл на таблицу: `<table>Repo.ts`.
2. Функция возвращает типы из `*.types.ts`, выведенные из `database.types.ts`.
3. Ошибка Supabase — `throw error`; ловит и показывает её контекст, не репозиторий.
4. `onConflict` в `upsert` обязан **буквально** совпадать с составом
   unique-ограничения. При изменении ограничения миграцией — правится и здесь.
   Рассинхронизация не ловится ни типами, ни тестами и проявится только в рантайме.

Текущий состав: `candidatesRepo`, `candidateListOptionsRepo`,
`staffingDemandRepo`, `staffingDemandRowsRepo`, `staffingDemandHistoryRepo`,
`portalUsersRepo`.

`portalUsersRepo` — исключение из правила «один файл на таблицу»: он работает
не с таблицей, а с набором `SECURITY DEFINER` функций, потому что
`portal_users` закрыта RLS полностью.

## Аутентификация и защита роутов

Supabase Auth не используется — портал ведёт пользователей сам, решение и его
цена в [`ADR-004`](decisions/ADR-004-portal-auth.md).

### Два токена

Не путать: их действительно два, у каждого своя работа.

| | Токен сессии | Токен доступа (JWT) |
|---|---|---|
| Где живёт | httpOnly-cookie `portal_session` | память вкладки (`accessToken.ts`) |
| Кто выдал | `portal_login` (случайные 32 байта) | портал, подпись `SUPABASE_JWT_SECRET` |
| Что в базе | только sha256 | ничего, проверяется подписью |
| Срок | скользящие 12 часов | 15 минут |
| Зачем | доказать, что пользователь вошёл | чтобы PostgREST принял запрос как `authenticated` |

Браузерный JS видит только второй. Первый ему недоступен вообще.

### Маршруты

| Маршрут | Что делает |
|---|---|
| `POST /api/auth/login` | зовёт `portal_login`, ставит cookie. Пароль не логируется и не возвращается |
| `POST /api/auth/logout` | отзывает сессию, чистит cookie |
| `GET /api/auth/token` | выдаёт 15-минутный JWT под действующую сессию |

### Middleware

`src/proxy.ts` (в Next.js 16 middleware-файл называется `proxy`) вызывает
`guardRequest` из `lib/auth/middleware.ts` на каждом запросе, кроме статики
и `/api/auth/*` (эти проверяют себя сами — иначе вход был бы невозможен). Он:

- проверяет сессию через `portal_session_context` (заодно продлевает её);
- уводит неавторизованного на `/login`, попутно удаляя протухшую cookie —
  иначе отключённый пользователь ходил бы по кругу `/login` → `/` → `/login`;
- уводит авторизованного с `/login` на `/`;
- проверяет право на запрошенный раздел (`/?section=…`) и уводит на `/403`.

**Цена этой схемы:** проверка сессии — запрос в базу на каждом запросе,
включая RSC-навигации. Та же цена, что была у `getUser()` раньше.

### Почему смена роли действует сразу

Роль и активность нигде не кэшируются: `portal_can()` в RLS и
`portal_session_context()` в middleware читают их из `portal_users` на каждом
запросе. JWT несёт только `sub` и `sid`; claim `portal_role` в нём —
диагностический, прав по нему база не выдаёт.

## Аудит изменений

Два независимых журнала:

- **`staffing_demand_history`** — изменения «Потребности», пишется триггерами;
- **`portal_audit_log`** — действия администратора над учётными записями и
  события входа, пишется функциями `portal_login` / `portal_admin_*`.

Общий принцип у обоих: пишет база, приложение не может ни пропустить запись,
ни подделать автора. Паролей в журнале нет ни в каком виде — только факт
смены.

`staffing_demand` и `staffing_demand_rows` пишут историю в
`staffing_demand_history` через два триггера `SECURITY DEFINER` с
`set search_path = public`.

Почему именно так, а не записью из приложения: клиент физически не может
пропустить или подделать запись — включая поле `changed_by`, которое
заполняется из `auth.uid()` внутри функции. Приложение не имеет
insert-политики на эту таблицу вовсе.

Что важно помнить при массовых операциях: **каждая изменённая строка порождает
ещё одну строку в истории**, в той же транзакции. Массовое добавление на
несколько тысяч ячеек — это удвоенный объём записи плюс обновление индексов,
при `statement_timeout = 8s` у роли `authenticated`.

## Конкурентная запись

Оптимистичной блокировки нет. Все обновления — last-write-wins:

- ячейка потребности перезаписывается целиком;
- статус и комментарий строки читаются, сливаются в приложении
  (`mergeRowMetaPatch`) и записываются обратно — то есть read-modify-write
  без проверки версии.

При одновременной работе нескольких координаторов изменения теряются молча.
Единственное, что есть сейчас, — возможность увидеть постфактум в истории,
что произошло. Полноценное решение (сверка по `updated_at` + Realtime)
зафиксировано в бэклоге.

## Чего в бэкенде нет

- API-роутов и серверных экшенов **для данных** (есть только три маршрута
  авторизации);
- серверной валидации за пределами `CHECK`-ограничений и проверок внутри
  `portal_*` функций;
- фоновых задач, очередей, расписаний;
- логирования и мониторинга;
- рейт-лимитинга на уровне приложения.
