# Бэкенд

Всё, что между интерфейсом и Postgres. Схема данных — [`../database/schema.md`](../database/schema.md),
политики доступа — [`../database/policies.md`](../database/policies.md).

## Главное, что нужно понять сразу

**Собственного бэкенда у проекта нет.** Нет API-роутов, нет серверных экшенов,
нет отдельного сервиса. Браузер обращается к PostgREST (Supabase) напрямую,
а единственная защита данных — RLS на стороне Postgres.

Из этого следуют два практических правила:

1. **Любая проверка, написанная в React, — не защита, а удобство.** Валидацию,
   на которую вы полагаетесь, нужно дублировать `CHECK`-ограничением в схеме.
   Так сделано, например, с длиной комментария (2000 символов — и в
   `demandRowMeta.ts`, и в `CHECK` таблицы).
2. **Ключ, лежащий в браузере, публичный по определению.** Поэтому в коде
   используется только publishable-ключ, а `service_role` не применяется
   нигде — см. [`ADR-002-auth.md`](decisions/ADR-002-auth.md).

## Слои

```
Компонент раздела
  └─ usePortal()                    ← единственная точка входа для данных
       └─ lib/supabase/*Repo.ts     ← весь SQL-подобный код здесь
            └─ lib/supabase/client.ts (браузер) | server.ts (сервер)
                 └─ PostgREST → Postgres (RLS + триггеры)
```

Компонент не обращается к Supabase напрямую — никогда. Репозиторий не знает
про React. Контекст склеивает одно с другим и держит клиентский кэш.

Единственное осознанное исключение: `DemandHistoryDrawer` вызывает репозиторий
напрямую, потому что история грузится лениво при открытии и класть её в
глобальный контекст незачем.

## Клиенты Supabase

| Файл | Где работает | Особенности |
|---|---|---|
| `client.ts` | браузер | `createBrowserClient`, новый инстанс на вызов, cookie-синхронизация внутри `@supabase/ssr` |
| `server.ts` | Server Components | `createServerClient`, читает cookie через `next/headers`, создаётся заново на каждый запрос |
| `middleware.ts` | `proxy.ts` | обновляет сессию и решает вопрос доступа к роуту |

Переменные окружения читаются **только через статический `process.env.X`**
(`env.ts`). Динамический доступ `process.env[name]` Turbopack не инлайнит в
клиентский бандл, и переменная окажется `undefined` в браузере — это уже
случалось, поэтому в `env.ts` стоит соответствующий комментарий.

## Репозитории

Правила:

1. Один файл на таблицу: `<table>Repo.ts`.
2. Функция возвращает типы из `*.types.ts`, выведенные из `database.types.ts`.
3. Ошибка Supabase — `throw error`; ловит и показывает её контекст, не репозиторий.
4. `onConflict` в `upsert` обязан **буквально** совпадать с составом
   unique-ограничения. При изменении ограничения миграцией — правится и здесь.
   Рассинхронизация не ловится ни типами, ни тестами и проявится только в рантайме.

Текущий состав: `candidatesRepo`, `candidateListOptionsRepo`,
`staffingDemandRepo`, `staffingDemandRowsRepo`, `staffingDemandHistoryRepo`.

## Аутентификация и защита роутов

`src/proxy.ts` (в Next.js 16 middleware-файл называется `proxy`) вызывает
`updateSession` из `lib/supabase/middleware.ts` на каждом запросе, кроме
статики. Он:

- обновляет cookie сессии Supabase;
- уводит неавторизованного на `/login`;
- уводит авторизованного с `/login` на `/`;
- сохраняет `/update-password` доступным даже для сессии восстановления —
  иначе пользователь застрянет в середине смены пароля.

При редиректе cookie переносятся вручную на новый ответ: обычный
`NextResponse.redirect` потерял бы обновлённые токены и разлогинил
пользователя в момент ротации.

**Цена этой схемы:** `supabase.auth.getUser()` — сетевой вызов, и он
происходит на каждом запросе, включая RSC-навигации. Под нагрузкой это
заметная задержка и риск упереться в лимиты Supabase Auth. Зафиксировано
в [`../tasks/backlog.md`](../tasks/backlog.md).

## Аудит изменений

`staffing_demand` и `staffing_demand_rows` пишут историю в
`staffing_demand_history` через два триггера `SECURITY DEFINER` с
`set search_path = public`.

Почему именно так, а не записью из приложения: клиент физически не может
пропустить или подделать запись — включая поле `changed_by`, которое
заполняется из `auth.uid()` внутри функции. Приложение не имеет
insert-политики на эту таблицу вовсе.

Что важно помнить при массовых операциях: **каждая изменённая строка порождает
ещё одну строку в истории**, в той же транзакции. Массовое добавление на
несколько тысяч ячеек — это удвоенный объём записи плюс обновление индексов,
при `statement_timeout = 8s` у роли `authenticated`.

## Конкурентная запись

Оптимистичной блокировки нет. Все обновления — last-write-wins:

- ячейка потребности перезаписывается целиком;
- статус и комментарий строки читаются, сливаются в приложении
  (`mergeRowMetaPatch`) и записываются обратно — то есть read-modify-write
  без проверки версии.

При одновременной работе нескольких координаторов изменения теряются молча.
Единственное, что есть сейчас, — возможность увидеть постфактум в истории,
что произошло. Полноценное решение (сверка по `updated_at` + Realtime)
зафиксировано в бэклоге.

## Чего в бэкенде нет

- API-роутов и серверных экшенов;
- серверной валидации за пределами `CHECK`-ограничений;
- фоновых задач, очередей, расписаний;
- логирования и мониторинга;
- рейт-лимитинга на уровне приложения.
