# ADR-003. Единый React Context вместо библиотеки состояния

**Статус:** принято, действует; **пересмотр при росте матрицы**
**Дата:** июль 2026

## Context

Порталу нужно общее клиентское состояние: данные кандидатов и потребности,
справочники, активный раздел, тосты, уведомления, выбранные карточки. Разделы
переключаются клиентски внутри одного роута `/`, поэтому состояние живёт всё
время работы пользователя.

Варианты: Redux Toolkit, Zustand, Jotai, TanStack Query — или встроенный
React Context.

## Decision

Взят **один `PortalContext`** на базе `useState` / `useCallback` / `useMemo`.
Внешние библиотеки состояния и серверного кэша не добавлялись.

- Единая точка входа для компонентов — хук `usePortal()`.
- Загрузка данных — `useEffect` при монтировании провайдера, обновление —
  ручное через `refresh*`-функции.
- Кэш ответов сервера — обычный `useState` внутри контекста; после мутации
  локальный массив правится вручную, повторный запрос не делается.
- Защита от гонок — функциональная форма `setState(prev => …)` плюс
  `useRef`-множество ключей «сохранение уже идёт» для метаданных строки.

## Consequences

### Плюсы

- Ноль дополнительных зависимостей: `package.json` содержит только Next, React
  и Supabase.
- Нет слоя абстракции, который нужно изучать перед первой правкой: любой
  React-разработчик читает контекст сразу.
- Публичный API стабилен: `usePortal()` скрывает внутреннее устройство, и
  разделы не переписываются при изменении внутренностей.
- Оптимистичное обновление списков даёт мгновенный отклик интерфейса без
  библиотеки кэширования.

### Минусы и принятая цена

Цена стала заметной после того, как матрица потребности получила третье
измерение (должности), и её нужно назвать честно:

- **Контекст превратился в «божественный объект»:** около 60 значений в одном
  `value`, `useMemo` с 60 зависимостями.
- **Любое изменение ре-рендерит всех потребителей.** Появление тоста, его
  автоисчезновение через 2.8 секунды, отметка уведомления — каждое такое
  событие пересоздаёт `value` и перерисовывает всё дерево, включая каждую
  ячейку матрицы.
- **`React.memo` не используется нигде**, поэтому каскад ре-рендеров ничем
  не останавливается.
- **Нет инвалидации кэша.** Данные, загруженные при монтировании, устаревают
  молча: изменения другого пользователя видны только после перезагрузки
  страницы.
- **Ручная синхронизация после мутаций** дублирует логику: одно и то же
  правило («обновить существующую строку или добавить новую») повторяется
  в каждой мутирующей функции.
- **Read-modify-write из устаревшего замыкания.** `updateDemandRowMeta`
  читает состояние на момент рендера — при одновременной правке статуса и
  комментария одно изменение теряется.

### Когда пересматривать

Триггеры для пересмотра, в порядке вероятности:

1. Матрица начинает заметно тормозить при вводе — значит каскад ре-рендеров
   стал дороже пользы от простоты.
2. Появляется требование видеть изменения коллег без перезагрузки — нужен
   слой подписок и инвалидации.
3. Число значений в контексте продолжает расти.

### Направление пересмотра

Не «переписать на Redux», а поэтапно:

1. Разделить контекст по доменам: `DemandContext`, `CandidatesContext`,
   `UiContext` (тосты, навигация). Быстро меняющееся уводится от медленно
   меняющегося.
2. Обернуть листовые компоненты матрицы в `React.memo`.
3. Только если этого мало — вводить TanStack Query для серверного кэша,
   инвалидации и дедупликации запросов.

Сохраняя при этом `usePortal()` как публичный API, чтобы разделы не
переписывались. Отслеживается в [`../../tasks/backlog.md`](../../tasks/backlog.md).
