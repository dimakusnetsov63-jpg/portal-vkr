# ADR-001. Supabase Postgres как единственное хранилище

**Статус:** принято, действует
**Дата:** июль 2026

## Context

Порталу нужно хранилище для кандидатов, потребности в персонале и справочников,
а также аутентификация сотрудников. Команда разработки маленькая, выделенных
DevOps и DBA нет, хостинг — Vercel.

Требовалось решить: поднимать ли собственный бэкенд с ORM и своей базой, или
взять управляемое решение.

## Decision

Взят **Supabase (управляемый Postgres)** с прямым обращением из браузера через
PostgREST. Собственный бэкенд-слой не создаётся.

Ключевые решения внутри:

1. **Источник истины схемы — SQL-миграции** в `supabase/migrations/`. Не ORM,
   не декларативная схема, не ручные правки через Dashboard.
2. **Типы генерируются из базы** (`supabase gen types typescript`), а не
   пишутся руками. `database.types.ts` — генерируемый файл.
3. **Доступ к данным только через репозитории** `lib/supabase/*Repo.ts`.
   Компоненты не обращаются к Supabase напрямую.
4. **Soft-delete по умолчанию**: `archived_at` у кандидатов, `is_active`
   у справочников. Единственное исключение — `staffing_demand`, где очистка
   ячейки это физический `DELETE` (значение потребности не несёт исторической
   ценности после снятия, а история изменений всё равно пишется отдельно).
5. **Обычные `unique`-ограничения вместо частичных индексов** там, где
   используется `upsert`: связка `.upsert().onConflict()` в Supabase-JS
   работает предсказуемо с обычным ограничением и не гарантирует поведения
   с partial unique index через PostgREST.
6. **Справочники вместо enum там, где список растёт**: города, рекрутёры,
   должности живут в `candidate_list_options` и пополняются из интерфейса
   без миграции. Enum остались только у проектов и стадий, где список задан
   бизнесом и меняется редко.

## Consequences

### Плюсы

- Нулевые затраты на эксплуатацию базы: бэкапы, обновления, масштабирование
  вертикально — на стороне Supabase.
- Миграции в git дают воспроизводимую и ревьюируемую историю схемы.
- Генерация типов исключает целый класс ошибок: рассинхронизацию типов
  TypeScript со схемой поймает компилятор.
- Отсутствие бэкенда резко сокращает объём кода и время на новую функцию:
  новое поле — это миграция, регенерация типов и правка UI.
- Добавление новой должности или города не требует ни миграции, ни релиза.

### Минусы и принятая цена

- **Вся защита данных держится на RLS.** Ошибка в политике — это немедленная
  утечка или потеря данных, промежуточного слоя, который бы её перехватил,
  нет.
- **Валидацию приходится дублировать**: в приложении для удобства и в
  `CHECK`-ограничении для надёжности. Расхождение между ними — реальный риск.
- **Клиент видит форму базы.** Названия таблиц и колонок фактически стали
  публичным API; переименование колонки ломает клиент.
- **Нет места для сложной логики.** Транзакции с несколькими таблицами,
  фоновые задачи и агрегации либо пишутся как функции Postgres, либо
  не пишутся вовсе.
- **Один контур на всё.** Отдельного dev-стенда нет, поэтому миграции
  применяются к боевой базе и только по прямой команде.
- **`statement_timeout = 8s`** для роли `authenticated` — жёсткая граница
  для массовых операций, которую нельзя обойти со стороны клиента.

### Что пересмотреть при росте

Если появится потребность в сложных транзакциях, интеграциях с внешними
системами или серверных агрегациях — добавлять серверный слой (Route Handlers
или отдельный сервис) с `service_role`-ключом, оставив клиенту только чтение.
Это не отменяет данное решение, а надстраивается над ним.
