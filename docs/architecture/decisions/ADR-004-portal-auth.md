# ADR-004. Собственная авторизация портала вместо Supabase Auth

**Статус:** принято
**Дата:** 28 июля 2026
**Заменяет:** [`ADR-002-auth.md`](ADR-002-auth.md)

## Context

Портал рассчитан примерно на 100 сотрудников. Все учётные записи заводит
администратор — самостоятельной регистрации нет и не будет.

Схема из ADR-002 (Supabase Auth + ручное создание пользователей в Dashboard)
не подошла по двум причинам:

1. **Организационная.** Заводить сотрудника в чужой панели — не тот процесс,
   который можно отдать руководителю подбора. Управление людьми должно жить
   там же, где работа с ними: в разделе «Настройки → Команда и роли».
2. **Техническая.** Ролей не было вовсе: любой вошедший мог изменить или
   удалить что угодно. Это было зафиксировано как главный долг до 1.0.

Требование задачи: источник истины по пользователям — база портала, Supabase
остаётся базой данных и API.

## Decision

### 1. Пользователи и сессии — свои таблицы

`portal_users`, `portal_sessions`, `portal_audit_log`. Пароль хранится
bcrypt-хешем (`pgcrypto`, `crypt`/`gen_salt('bf', 10)`), открытого пароля не
существует нигде — ни в базе, ни в логах, ни в ответах API.

Таблицы закрыты полностью: RLS включён, политик нет, гранты отозваны.
Единственный путь к ним — `SECURITY DEFINER` функции (`portal_login`,
`portal_session_context`, `portal_admin_*`), которые сами проверяют право
вызывающего. Поэтому `password_hash` физически не может уехать клиенту:
маршрута, который бы его вернул, не существует.

### 2. Сессия — непрозрачный токен в httpOnly-cookie

`portal_login` возвращает случайный токен; в базе лежит только его sha256.
Токен кладётся в httpOnly-cookie серверным маршрутом `/api/auth/login`.
Браузерный JS его не видит — украсть через XSS нечего.

Срок жизни скользящий: 12 часов от последней активности, продление пишется в
базу не чаще раза в 5 минут.

### 3. Доступ к данным — JWT, подписанный порталом

Ключевое решение. Данные браузер по-прежнему читает у PostgREST напрямую —
переписывать все репозитории на серверный прокси было бы месяцем работы.
Значит, запросу нужен токен, подпись которого Supabase признаёт.

Портал подписывает JWT сам, секретом проекта (`SUPABASE_JWT_SECRET`), с
`role: authenticated` и `sub` = id пользователя портала. Токен живёт 15 минут
и молча обновляется через `/api/auth/token` — выдаётся только под действующую
сессию.

Что это даёт:

- существующие RLS-политики продолжают работать без переписывания;
- `auth.uid()` возвращает id пользователя портала, поэтому триггеры аудита
  «Потребности» пишут корректного автора — ни строки изменений в них;
- `service_role` по-прежнему нигде не используется.

### 4. Права — в базе, а не только в интерфейсе

Матрица «роль → разделы» продублирована в двух местах:
`public.portal_role_sections()` (SQL) и `src/lib/auth/roles.ts` (TS).

Политики данных теперь выглядят как `using (public.portal_can('demand'))`.
Функция читает роль и `is_active` **из таблицы**, а не из JWT. Отсюда два
следствия, ровно как требовалось в задаче: смена роли действует со
следующего запроса без повторного входа, а деактивация закрывает доступ
немедленно, не дожидаясь истечения токена.

### 5. Восстановления пароля нет

Забытый пароль задаёт заново администратор. Страницы `/forgot-password` и
`/update-password` удалены вместе с Supabase Auth.

## Consequences

### Плюсы

- Пользователи заводятся и отключаются из портала; Supabase Dashboard для
  ежедневной работы больше не нужен.
- Роли реально ограничивают данные, а не только прячут пункты меню: запрос к
  PostgREST мимо интерфейса упирается в ту же проверку.
- Отключение сотрудника обрывает его открытые сессии в тот же момент.
- Все действия администратора и события входа пишутся в журнал, которого
  приложение не может подделать.
- Схема расширяется без перестройки: 2FA, восстановление пароля, временная
  блокировка, индивидуальные права, история входов ложатся на существующие
  таблицы (для истории входов данные уже пишутся).

### Минусы и принятая цена

- **Появился собственный бэкенд.** Три маршрута в `src/app/api/auth/`. Раньше
  их не было вовсе — утверждение «у проекта нет API-роутов» больше неверно.
- **Зависимость от `SUPABASE_JWT_SECRET`.** Если секрет не задан или не
  совпадает с проектом, вход пройдёт, а данные не загрузятся (401 от
  PostgREST). Диагностируется по ответу `/api/auth/token`. Если проект
  Supabase переведён на асимметричные ключи подписи и legacy-секрет отозван,
  этот путь перестанет работать — тогда нужен переход на подпись тем ключом,
  который проект признаёт; изолировано в `src/lib/auth/jwt.ts`.
- **Матрица прав продублирована в SQL и TS.** Рассинхронизацию не поймают ни
  типы, ни тесты: она проявится как «раздел видно, а данные не грузятся».
  Оба места помечены комментариями.
- **Проверка сессии — запрос в базу на каждый защищённый маршрут.** Это та же
  цена, что была у `getUser()` в ADR-002, ни лучше, ни хуже.
- **`portal_login` доступен роли `anon`** — иначе форма входа не работала бы.
  Защита от перебора минимальная: 10 неудачных попыток на логин за 15 минут.
  Полноценная блокировка учётки — отдельная задача.
- **Разграничения по проектам нет.** Поле `projects` заполняется и
  отображается, но данные по нему не фильтруются.
- **Персональные данные кандидатов доступны всем ролям**, у которых есть
  раздел «Кандидаты», то есть всем четырём. Ограничение доступа к отдельным
  полям (телефон, `salary_card`) остаётся долгом.

## Что осталось от ADR-002

Ничего из механики: Supabase Auth, вход по email, `/forgot-password`,
`/update-password` и политики `using (true)` удалены. Сохранены два принципа:
в коде только publishable-ключ, авторство изменений проставляет база через
`auth.uid()`, а не клиент.
