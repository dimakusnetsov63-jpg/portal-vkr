# ADR-002. Supabase Auth, publishable-ключ и RLS без ролей

**Статус:** **заменено на [ADR-004](ADR-004-portal-auth.md)** (28 июля 2026)
**Дата:** июль 2026

> Решение отменено целиком: Supabase Auth больше не используется,
> пользователи создаются в портале, политики данных зависят от роли.
> Документ сохранён как есть — он объясняет, почему код какое-то время был
> устроен именно так, и чем это обошлось. Актуальная модель — в
> [ADR-004](ADR-004-portal-auth.md) и [`../../database/policies.md`](../../database/policies.md).

## Context

Портал внутренний: доступ только для сотрудников, самостоятельной регистрации
быть не должно. Учётных записей на старте — единицы, все сотрудники доверенные.

Нужно было выбрать механизм аутентификации и модель авторизации, не потратив
на это недели.

## Decision

1. **Аутентификация — Supabase Auth**, вход по email и паролю. Учётные записи
   заводятся вручную в Supabase Dashboard, регистрации в интерфейсе нет.
2. **В приложении используется только publishable-ключ** — и в браузере, и на
   сервере. `service_role` не применяется нигде.
3. **Авторизация — целиком на RLS.** Политики созданы только для роли
   `authenticated`, для `anon` политик нет ни на одной таблице.
4. **Все политики — `using (true)` / `with check (true)`.** Разграничения по
   пользователю, проекту или роли не вводится. Таблиц `profiles` и `roles`
   не существует.
5. **Защита роутов — в middleware** (`src/proxy.ts` → `lib/supabase/middleware.ts`):
   обновление сессии и редиректы на каждом запросе.
6. **Авторство изменений** фиксируется через `auth.uid()` внутри
   `SECURITY DEFINER`-триггеров аудита, а не приходит от клиента.

## Consequences

### Плюсы

- Рабочая аутентификация получена за часы, а не за недели: восстановление
  пароля, ротация токенов и хранение хешей — на стороне Supabase.
- Модель ключей корректна: в браузер уходит только публичный ключ, утечка
  `service_role` невозможна, потому что его в коде нет.
- Главный рубеж защиты работает: без входа не читается ничего, `anon` не имеет
  доступа ни к одной таблице.
- `changed_by` в истории изменений подделать нельзя — значение проставляет
  сама база.

### Минусы и принятая цена

Это самое «дорогое» из принятых решений, и его цену нужно назвать прямо:

- **Ролей нет — любой сотрудник администратор данных.** Вошедший пользователь
  может изменить или удалить что угодно.
- **Любой сотрудник может удалить всю потребность целиком.** Политика
  `authenticated_delete_staffing_demand` ничем не ограничена, кроме факта
  авторизации.
- **Вся персональная информация доступна всем.** ФИО, телефоны, telegram,
  `salary_card` кандидатов читает любой вошедший. Для 152-ФЗ это требует
  внимания до расширения круга пользователей.
- **Нет разграничения по проектам.** Координатор одного проекта работает с
  данными всех остальных.
- **`getUser()` на каждом запросе** — сетевой вызов к Supabase Auth, включая
  RSC-навигации. Под нагрузкой это задержка на каждом переходе и риск
  упереться в лимиты.
- **Нет автовыхода по бездействию** и журнала доступа к персональным данным.

Пока пользователей единицы и все доверенные, это приемлемо. При росте команды
модель перестаёт быть приемлемой — не постепенно, а сразу.

## Что нужно сделать до 1.0

Решение помечено как требующее пересмотра. Минимальный объём:

1. Таблица `profiles`, связанная с `auth.users`, и перечисление ролей
   (администратор, координатор, руководитель).
2. Переписать политики: `select` по принадлежности к проекту, `delete` —
   только администратору.
3. Убрать право удаления потребности у рядовых пользователей.
4. Ограничить доступ к полям с персональными данными.
5. Проверить и отключить `enable_signup` в конфигурации Supabase.

Детали и оценки — в [`../../AUDIT-2026-07.md`](../../AUDIT-2026-07.md) (§5.1, §5.2)
и [`../../tasks/backlog.md`](../../tasks/backlog.md).
