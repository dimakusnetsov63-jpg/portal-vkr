# ADR-005. Права разделов в базе: VISIBLE / VIEW / EDIT

**Статус:** принято, реализована фаза A (не применено к боевой базе)
**Дата:** 11 августа 2026
**Дополняет:** [`ADR-004-portal-auth.md`](ADR-004-portal-auth.md) — модель
пользователей и сессий не меняется

## Context

Модель доступа из ADR-004 отвечает на один вопрос: есть ли у роли раздел.
Плоский список прав, продублированный руками в двух местах —
`ROLE_PERMISSIONS` в `src/lib/auth/roles.ts` и `case` внутри
`public.portal_role_sections()`. Три ограничения этой модели упёрлись в
требования новой задачи:

1. **Нет разделения чтения и записи.** Там, где оно фактически понадобилось,
   его собирали вручную из двух разделов: запись в `vacancy_*` требует
   `portal_can('vacancies') and portal_can('settings')`, запись в
   `candidate_list_options` — `portal_can('settings')` при чтении по
   `portal_can('candidates')`. Приём рабочий, но он не масштабируется и
   читается как загадка: «редактирование вакансий» выражено через
   «настройки».
2. **Права меняются только правкой кода.** Чтобы отобрать у менеджера
   раздел, нужны миграция, деплой и синхронная правка двух матриц.
   Требование задачи — управлять этим из «Настройки → Доступы».
3. **Дубль TS/SQL ничем не проверяется.** Об этом прямо написано в
   комментарии самого `roles.ts`: рассинхронизацию не поймают ни типы, ни
   тесты, она проявится как «раздел видно, а данные не грузятся».

Отдельно: `portal_users.projects` (H-6) умеет «эти проекты», но не умеет
«все проекты, включая будущие» ни для кого, кроме роли `head`, у которой
bypass зашит в функцию.

## Decision

### 1. Модель — `role → section → visible / view / edit`

Три независимых флага вместо одного булева «раздел доступен»:

| Флаг | Значение | Кто проверяет |
|---|---|---|
| `visible` | показывать пункт в меню | только интерфейс |
| `can_view` | открыть раздел и читать данные | `select`-политики RLS |
| `can_edit` | изменять данные | `insert`/`update`/`delete` |

Связаны инвариантом `can_edit => can_view => visible`, закреплённым
`check`-ограничениями **в базе**, а не только в UI: невалидное состояние не
создать ни ручным `UPDATE` из SQL Editor, ни ошибкой в будущем интерфейсе.

**`visible` — не механизм безопасности.** Скрытый пункт меню экономит
пользователю внимание, и только. Прямой заход по URL обязан упереться в
`can_view` (middleware) и в RLS (данные) — ровно так же, как если бы пункт
был на месте.

Права выдаются **роли**, не пользователю. Персональных исключений в модели
нет: они превращают отладку прав в археологию, а требование задачи —
«Права ролей», а не «права пользователя».

### 2. Источник истины — база

`public.portal_section_permissions` (44 строки: 4 роли × 11 прав). Матрица
перестаёт быть кодом и становится данными: её можно поменять из интерфейса,
не выкладывая релиз.

Таблица закрыта так же, как `portal_users`: RLS включён, политик нет, гранты
отозваны. Читать и править её можно только через `SECURITY DEFINER`-функции.
Пользователь не может выдать себе право ни при каком стечении обстоятельств —
даже прямым запросом к PostgREST мимо портала.

Проверки читают роль и `is_active` **из `portal_users` в момент запроса**, а
не из claim'ов JWT. Свойство унаследовано от `portal_can` и сохранено
сознательно: отзыв права и деактивация действуют со следующего же запроса,
без перевыпуска токена. Класть права в JWT — значит завести окно, в котором
уволенный сотрудник ещё 15 минут работает с прежними правами.

### 3. `portal_can()` остаётся — как синоним VIEW

`portal_can(section)` вызывается из десятков действующих политик. Ломать их
разом ради переименования — риск без выгоды, поэтому функция сохранена и
делегирует в `portal_can_view_section`. Новые политики пишутся на явных
`portal_can_view_section` / `portal_can_edit_section`; старые переезжают
по одной таблице за раз (фаза C).

`portal_role_sections(role)` тоже сохранена: имя, аргумент, тип возврата и
**порядок элементов** прежние, изменилась только реализация — читает таблицу
вместо `case`. Два вынужденных отступления, оба documented:

- волатильность `immutable` → `stable`: функция теперь читает таблицу и не
  вправе обещать неизменность результата. Ни один индекс и ни одно
  ограничение на неё не опираются, где `immutable` было бы обязательным;
- добавлен `security definer`: без него функция вернула бы пустой массив
  всем, кроме владельца, — таблица закрыта RLS.

### 4. Проекты: `text[]` остаётся, добавляется `all_projects`

`portal_users.projects` **не переводится** в нормализованную
`portal_user_projects`. H-6 работает, семь таблиц фильтруются через
`portal_has_project()`, и переписывание рабочей проектной изоляции ради
формы хранения — риск, не оплаченный ни одним требованием.

Вместо этого — `portal_users.all_projects boolean not null default false`.
Он даёт третий вариант ответа на «какие проекты видны»: перечисленные, все,
или все потому что `head`. Без него чекбокс «Все проекты» пришлось бы
имитировать перечислением всех проектов руками, дописывая каждый новый.

**Bypass роли `head` сохранён хардкодом** внутри `portal_has_project()` и
намеренно не переведён на `all_projects`: иначе руководителя можно было бы
случайно отрезать от данных, сняв галочку в его карточке.

### 5. Project-specific overrides: место есть, реализации нет

У `portal_section_permissions` с самого начала есть nullable `project`:
`NULL` — правило для всех проектов роли, ненулевое — переопределение под
конкретный проект. **В первой версии создаются только `NULL`-строки**, и все
функции читают только их.

Колонка заведена сразу, потому что добавить её позже — значит мигрировать
всю матрицу и переписать уникальность (уже сделанную двумя частичными
индексами именно под nullable `project`). Сценарий «в Бургер Кинге
редактирует, в Самокате только смотрит» архитектурой не блокируется, но и не
реализуется, пока за ним нет живой потребности.

### 6. Фаза A аддитивна

Выкат разбит на фазы; фаза A **не меняет наблюдаемое поведение ни для одной
роли**:

- политики RLS не переписаны — ни одна;
- `roles.ts`, middleware, `PortalContext`, фронтенд, payload'ы auth-RPC и
  JWT не тронуты;
- baseline seed воспроизводит прежнюю матрицу один в один, включая
  неочевидную ячейку `vacancies` у `manager`/`recruiter` (`can_view = true`,
  `can_edit = false` — потому что запись и сегодня требует `vacancies` **и**
  `settings`);
- `all_projects = false` у всех существующих учёток, то есть новая ветка
  `portal_has_project()` пока ни для кого не срабатывает.

Порядок остальных фаз: B — сверка baseline на реальной базе; C — перевод
политик на `view`/`edit`; D — permission layer и RPC; E — интерфейс
(«Настройки → Доступы», чекбокс «Все проекты»).

## Consequences

### Плюсы

- Права редактируются из интерфейса, без миграции и деплоя.
- Разделение чтения и записи выражается напрямую, а не через `and
  portal_can('settings')`.
- SQL-сторона дубля TS/SQL ликвидирована; расхождение с `roles.ts` ловит
  `sectionPermissionsSeed.test.ts` на каждом прогоне тестов.
- Инвариант прав нельзя нарушить в обход интерфейса.

### Минусы и принятые риски

- **Гранулярность «роль × раздел» покрывает не всё.** «Адреса» редактируют
  все четыре роли, а импорт и историю внутри того же раздела — только
  head/coordinator. Одним `can_edit('addresses')` это не выражается, поэтому
  у пяти таблиц связка «раздел + `settings`» в фазе C сохраняется. Список —
  в [`policies.md`](../../database/policies.md).
- **`portal_can` стал join'ом вместо одиночного `exists`.** Таблица на 44
  строки и проиндексирована, но это горячий путь RLS — перед фазой C нужен
  `EXPLAIN ANALYZE`.
- **`check (cardinality(projects) > 0)` конфликтует с «Все проекты»:**
  учётке с `all_projects = true` всё равно нужен хотя бы один проект в
  массиве. Ограничение сознательно не тронуто в фазе A, решать в фазе D/E.
- **Матрицу по-прежнему можно прочитать от имени `anon`** через
  `portal_role_sections(role)` — так было и до изменения, новой утечки нет,
  но решение осознанное, а не недосмотр.
- **Права ролей теперь можно испортить из интерфейса.** Раньше для этого
  нужен был доступ к репозиторию. Отсюда требование фазы D: любое изменение
  прав пишется в `portal_audit_log`.

## Проверено и не проверено

Фаза A **code-complete, но не проверена на базе**: миграции не применялись ни
к боевому Supabase, ни к локальному Postgres (на машине разработки нет
Docker), `npm run test:rls` не запускался. Прошли только статические
проверки — `typecheck`, `lint`, `test` (381 тест, из них 23 новых на
эквивалентность матрицы), `build`.

`src/testing/rls/sectionPermissions.rls-test.ts` написан и сверяет настоящие
SQL-функции с матрицей из `roles.ts`, но тоже ни разу не выполнялся.
