# Стратегия тестирования

Что именно тестируется автоматически, что — руками, и почему граница проведена
именно так. Чек-лист ручной проверки — [`checklist.md`](checklist.md).

## Текущее состояние (честно)

| Слой | Покрытие | Инструмент |
|---|---|---|
| Чистая логика (`.ts` без React) | **есть, хорошее** | Vitest |
| React-компоненты | **отсутствует** | — |
| Интеграция с Supabase | **отсутствует** | — |
| E2E | **отсутствует** | — |
| CI | **отсутствует** | — |

На момент написания: 16 файлов тестов, 186 проверок, все проходят.

Это осознанный компромисс, а не забывчивость: чистая логика даёт наибольший
возврат на вложенное время, а компонентные тесты потребовали бы jsdom +
Testing Library и поддержки моков Supabase. Но **важно понимать цену**:
зелёные тесты здесь означают «бизнес-правила посчитаны верно», а **не**
«интерфейс работает». Ни один тест не поймает сломанную вёрстку, битый
запрос к базе или неверно переданный проп.

## Что тестируется

Только модули без React, JSX и обращений к Supabase:

- `demandAggregate.ts` — сборка матрицы, список видимых строк, bulk-строки,
  фильтрация групп по предикату ячейки;
- `demandMetrics.ts` — итоги по должности / городу / проекту / колонке / периоду;
- `demandFilters.ts`, `candidateFilters.ts`, `addressFilters.ts`,
  `rateFilters.ts` — фильтрация (`rateFilters.ts` — над уже соединённым
  `RateWithCard[]`);
- `candidateMetrics.ts`, `addressMetrics.ts`, `rateMetrics.ts` — метрики
  выборки (`rateMetrics.ts` — ещё и join `rates`+`rate_cards`, вычисляемый
  доход за смену/неделю/месяц);
- `demandRowMeta.ts` — статусы, слияние патчей, композитные ключи;
- `demandQueryParams.ts` — сериализация состояния в URL;
- `demandCellEdit.ts` — решение о том, что делать с введённым значением;
- `demandCopy.ts` — цели копирования по датам;
- `demandHistory.ts` — форматирование записей аудита;
- `lib/auth/roles.ts` — матрица прав ролей и стартовый раздел роли;
- `settings/userForm.ts` — валидация формы учётной записи.

Отдельно про права: тест проверяет **клиентскую** половину матрицы. Её
SQL-двойник (`portal_role_sections`) не покрыт ничем — автотесты RLS-политик
остаются в бэклоге, и рассинхронизацию двух матриц зелёные тесты не поймают.

## Правила написания тестов

1. Тест живёт рядом с модулем: `demandMetrics.ts` → `demandMetrics.test.ts`.
2. Тестируется **поведение и бизнес-правило**, а не реализация.
3. Название теста — утверждение на английском о правиле, а не «works correctly».
4. Фикстуры строятся фабрикой (`makeRow`, `makeCandidate`) с частичным
   переопределением — при добавлении поля в схему правится одна фабрика.
5. Обязательно покрываются: пустой ввод, граничные значения, отсутствие
   мутации входных данных.
6. Композитные ключи проверяются на **коллизии** — тест
   `demandRowMetaKey("AB","C","D") !== demandRowMetaKey("A","BC","D")`
   существует не для красоты: он фиксирует, почему ключ строится через
   `JSON.stringify`, а не склейкой через разделитель.

## Запуск

```bash
npm run test         # разово
npm run test:watch   # в режиме наблюдения
```

## Обязательный набор проверок перед завершением задачи

```bash
npm run test
npx tsc --noEmit
npm run lint
npm run build
```

Порядок именно такой: тесты быстрее всего, сборка дольше всего. Ни одна из
четырёх команд не проверяет интерфейс — после них обязательна ручная проверка
по [`checklist.md`](checklist.md).

## Куда развивать (не сделано)

По убыванию пользы:

1. **CI на GitHub Actions** — те же четыре команды на каждый push. Сейчас
   ничто не мешает влить в `main` код, ломающий сборку.
2. **Компонентные тесты** для сложных интерактивных узлов: инлайн-редактирование
   ячейки, модалка массового добавления, drawer кандидата.
3. **Тесты репозиториев** против тестового Supabase-проекта — поймали бы
   рассинхронизацию `onConflict` со схемой.
4. **E2E** на ключевой сценарий: вход → потребность → правка ячейки → проверка
   сохранения.

Отслеживается в [`../tasks/backlog.md`](../tasks/backlog.md).
