# Стратегия тестирования

Что именно тестируется автоматически, что — руками, и почему граница проведена
именно так. Чек-лист ручной проверки — [`checklist.md`](checklist.md).

## Текущее состояние (честно)

| Слой | Покрытие | Инструмент |
|---|---|---|
| Чистая логика (`.ts` без React) | **есть, хорошее** | Vitest |
| RLS-политики (проектный доступ, H-13) | **есть, минимальное** — 13 тестов | Vitest против эфемерного локального Supabase, только в CI |
| React-компоненты | **отсутствует** | — |
| Интеграция с Supabase (репозитории, `onConflict`) | **отсутствует** | — |
| E2E | **отсутствует** | — |
| CI | **есть** (H-12) | GitHub Actions |

На момент написания: 21 файл чистых тестов, 232 проверки в `npm test`, плюс
отдельно 3 файла RLS-тестов (`npm run test:rls`, только в CI — см. ниже),
всё зелёное.

Это осознанный компромисс, а не забывчивость: чистая логика даёт наибольший
возврат на вложенное время, а компонентные тесты потребовали бы jsdom +
Testing Library и поддержки моков Supabase. Но **важно понимать цену**:
зелёные тесты здесь означают «бизнес-правила посчитаны верно», а **не**
«интерфейс работает». Ни один тест не поймает сломанную вёрстку, битый
запрос к базе или неверно переданный проп.

## Что тестируется

Только модули без React, JSX и обращений к Supabase:

- `demandAggregate.ts` — сборка матрицы, список видимых строк, bulk-строки,
  фильтрация групп по предикату ячейки;
- `demandMetrics.ts` — итоги по должности / городу / проекту / колонке / периоду;
- `demandFilters.ts`, `candidateFilters.ts`, `addressFilters.ts`,
  `rateFilters.ts` — фильтрация (`rateFilters.ts` — над уже соединённым
  `RateWithCard[]`);
- `candidateMetrics.ts`, `addressMetrics.ts`, `rateMetrics.ts` — метрики
  выборки (`rateMetrics.ts` — ещё и join `rates`+`rate_cards`, вычисляемый
  доход за смену/неделю/месяц);
- `demandRowMeta.ts` — статусы, слияние патчей, композитные ключи;
- `demandQueryParams.ts` — сериализация состояния в URL;
- `demandCellEdit.ts` — решение о том, что делать с введённым значением;
- `demandCopy.ts` — цели копирования по датам;
- `demandHistory.ts` — форматирование записей аудита;
- `lib/auth/roles.ts` — матрица прав ролей и стартовый раздел роли;
- `settings/userForm.ts` — валидация формы учётной записи;
- `settings/auditText.ts` — текст строки журнала действий: `details` пишут
  семь разных SQL-функций, и форма поля меняется миграциями без оглядки на
  интерфейс;
- `quality/qualityScore.ts` — расчёт процентов по блокам и итога проверки
  качества, разбор номера лида;
- `quality/qualityReport.ts` — свод пяти KPI из строк серверного агрегата;
- `quality/reviewSnapshot.ts` — сборка карточки по снимку ответов;
- `quality/reviewForm.ts` — валидация шапки проверки;
- `quality/qualityFilters.ts` — состояние фильтров реестра, готовые периоды
  и перевод в запрос;
- `quality/reviewColumns.ts` — состав колонок реестра и разбор сохранённой
  настройки;
- `quality/checklistDraft.ts` — черновик редактора шаблонов: перестановки,
  правки, проверка, сборка payload;
- `quality/checklistCoverage.ts` — кто каким шаблоном пользуется: свой,
  общий или никакого;
- `quality/qualitySummary.ts` — сборка сводки по сотрудникам из двух
  серверных агрегатов: взвешивание процентов и группировка блоков по
  названию, а не по идентификатору;
- `quality/summaryChart.ts` — подготовка графиков сводки: блоки, рейтинг
  сотрудников, проекты, динамика, распределение, возражения кандидатов
  (доля от всех названных, а не от числа проверок); взвешивание средних,
  сравнение с командой, русские склонения, а также геометрия сглаженной
  кривой — она не должна выдумывать пиков за пределами данных.

**Отдельно про `qualityScore.test.ts`.** Он единственный сверяет расчёт не с
придуманными примерами, а с рабочими файлами: двадцать реальных строк из
«Чек-листы по проектам» и «Самоотказы КЦ» вместе с процентами, которые
посчитал сам Excel (`qualityScore.fixtures.ts` — сгенерирован из файлов, не
перепечатан). Это цена решения из ADR-006: формула живёт и в TypeScript, и в
SQL, и разойтись они не должны молча — вторую половину сверки держит тест
паритета в `quality.rls-test.ts`, гоняющий один набор входов через RPC и
через `calculateReviewScore`. Ошибка в расчёте здесь — не косметика: по этой
цифре разговаривают с сотрудником.

**Отдельно про `qualityFilters.test.ts`.** Хук реестра
(`useQualityReviews`) тестами не покрыт: в проекте нет ни jsdom, ни Testing
Library, и заводить их ради одного хука — отдельное решение. Поэтому всё,
что решается без React, вынесено рядом и покрыто: правила «какая вкладка что
показывает» ломаются тихо — перепутанный флаг превращает «Аудиотеку» в общий
список. Тест на период по умолчанию сразу же поймал BUG-07 аудита: местная
полночь, пропущенная через `toISOString()`, давала вчерашний день.

Отдельно про права: этот раздел тестов проверяет только **клиентскую**
половину матрицы разделов (`roles.ts`). Её SQL-двойник (`portal_role_sections`)
по-прежнему не покрыт ничем — рассинхронизацию этих двух матриц зелёные
тесты не поймают. Но с H-13 покрыта смежная, более узкая вещь —
**строчный** проектный доступ (`portal_has_project`/`portal_has_rate_card_project`,
H-6) — см. раздел «RLS-тесты» ниже, отдельный слой, не расширение этого.

## Правила написания тестов

1. Тест живёт рядом с модулем: `demandMetrics.ts` → `demandMetrics.test.ts`.
2. Тестируется **поведение и бизнес-правило**, а не реализация.
3. Название теста — утверждение на английском о правиле, а не «works correctly».
4. Фикстуры строятся фабрикой (`makeRow`, `makeCandidate`) с частичным
   переопределением — при добавлении поля в схему правится одна фабрика.
5. Обязательно покрываются: пустой ввод, граничные значения, отсутствие
   мутации входных данных.
6. Композитные ключи проверяются на **коллизии** — тест
   `demandRowMetaKey("AB","C","D") !== demandRowMetaKey("A","BC","D")`
   существует не для красоты: он фиксирует, почему ключ строится через
   `JSON.stringify`, а не склейкой через разделитель.

## Запуск

```bash
npm run test         # разово
npm run test:watch   # в режиме наблюдения
```

## RLS-тесты (H-13)

Отдельный слой, отдельный конфиг (`vitest.rls.config.ts`), отдельная команда:

```bash
npm run test:rls
```

Требует Docker (`supabase start` поднимает эфемерный локальный Postgres) —
**не входит** в обязательный набор перед завершением задачи ниже и **не**
запускается вместе с `npm test`. В CI — отдельный job `rls-tests`, не
блокирующий `verify`. Подробности, архитектура и почему не против боевого
проекта — [`../ROLLOUT-rls-tests.md`](../ROLLOUT-rls-tests.md),
[`../../src/testing/rls/README.md`](../../src/testing/rls/README.md).

### Контроль качества (TASK-013)

`quality.rls-test.ts` — 49 сценариев: чтение чужого проекта, рекрутёр
без раздела, прямые INSERT/UPDATE в обход RPC, менеджер без права записи,
создание в чужом проекте, регресс на SEC-01 (обновление чужой проверки по
известному id, с проверкой что строка не изменилась), запрет завершить
незаполненную проверку, черновик с пропусками, выключенный блок, подмена
`kind`, игнорирование присланного `total_score`, пункт чужого шаблона,
правка шаблона менеджером, превышение длины, снимок формулировок, проверка
версии при одновременном редактировании, архивация и её невидимость для обеих
сводок, записи в журнал действий, паритет SQL-расчёта с TypeScript,
обнуление итога по нарушению и его снятие, а также редактор шаблонов:
создание, проверка версии, шаблон чужого проекта по известному id, удаление
неоценённого пункта против архивации оценённого, отказ по пустому названию,
неизвестной шкале, нулевому весу, выдуманному виду проверки и попытке
завести второй действующий шаблон на ту же пару «вид + проект», а также
обмен названиями двух блоков — действие, которое до 21 августа было
невозможно.

Последний сценарий появился после разбора красной джобы: четыре теста
редактора упали на первом же вызове RPC, потому что каждый заводил шаблон на
один и тот же проект, а на пару «вид + проект» стоит уникальный индекс.
Отрицательные сценарии рядом при этом были зелёными — они ждут отказа и
получают его по любой причине. **Тест, ожидающий провала, ничего не
говорит о том, что функция вообще работает**; нужен хотя бы один, который
ждёт успеха.

Именно этот набор дважды поймал то, что проверка «функция создана и содержит
нужные строки» пропустила: тело plpgsql типизируется при вызове, а не при
создании. Ручной осмотр после применения миграции доказывает наличие
функции, а не её работоспособность — доказательство даёт только вызов.

## Обязательный набор проверок перед завершением задачи

```bash
npm run test
npx tsc --noEmit
npm run lint
npm run build
```

Порядок именно такой: тесты быстрее всего, сборка дольше всего. Ни одна из
четырёх команд не проверяет интерфейс — после них обязательна ручная проверка
по [`checklist.md`](checklist.md).
