# Требования: Адреса

Централизованное управление объектами найма (дарксторы, магазины, склады,
ПВЗ, рестораны, производства, офисы и т. д.). Реализовано на реальных
данных Supabase.

Техническое описание раздела —
[`src/components/portal/sections/addresses/README.md`](../../src/components/portal/sections/addresses/README.md),
схема таблицы — [`../database/schema.md`](../database/schema.md).

## Задача раздела

Координатор должен видеть и вести всю информацию по одному объекту подбора
из одного места: потребность, статус набора, характеристики, контакты,
комментарии и (в следующей задаче) историю изменений.

## Общая концепция

**Один адрес = одна карточка.** В отличие от «Потребности» (где строка —
это проект+город+должность+дата), у адреса нет отдельных карточек по
должностям: специализация — одно из полей карточки, а не измерение матрицы.

Раздел видят **все четыре роли** (руководитель, координатор, менеджер,
рекрутер) — вместе с «Уведомлениями» это единственные разделы с таким
охватом.

## Активные и архив

Не отдельные страницы — **сегментированный переключатель** «Активные /
Архив» поверх одной и той же таблицы, переключение мгновенное. Технически —
soft delete через `archived_at` (как у кандидатов), в UI — переключатель в
строке и в карточке.

При переводе в архив:

- адрес пропадает из вкладки «Активные»;
- не участвует в расчёте KPI дашборда (ни при каком выборе фильтров);
- документы, комментарии и служебная информация полностью сохраняются;
- восстанавливается одним нажатием, без потери данных.

## Дашборд

Восемь агрегированных карточек: Всего адресов, Активных, Архивных, Общая
потребность, Закрыто вакансий, Незакрытая потребность, Критичных адресов,
Средняя укомплектованность.

**Всего/Активных/Архивных** считаются по **полному** набору данных,
независимо от текущих фильтров — это глобальные счётчики. Остальные пять
KPI считаются по **отфильтрованной** выборке **без архивных записей**,
даже если открыта вкладка «Архив» — архив никогда не входит в KPI.

## Вычисляемые показатели — не хранятся

**Дефицит и укомплектованность никогда не пишутся в базу** — только
`required_count`/`staffed_count` и производные от них считаются на клиенте
при каждом рендере (`addressMetrics.ts`):

- `Дефицит = Требуется − Есть сотрудников` (может быть отрицательным при
  переукомплектованности — это допустимо, не ошибка);
- `Укомплектованность % = Есть / Требуется × 100`, но **при `Требуется = 0`
  результат явно `100%`**, а не `0%` — осознанное исключение из общего
  правила «пустая выборка/деление на ноль → 0», принятое отдельно для этого
  раздела;
- «Незакрытая потребность» (агрегат дашборда) = сумма дефицитов, каждый
  предварительно ограниченный снизу нулём (переукомплектованные адреса не
  уменьшают общую цифру);
- «Закрыто вакансий» = сумма `staffed_count`;
- «Критичных адресов» = количество адресов с приоритетом «Критический» (5).

Так исключается рассинхронизация данных между хранимым и отображаемым
значением.

## Специализация — общий справочник с «Потребностью»

Поле называется `position` (не `specialization`) намеренно: это **тот же
справочник**, что используют «Потребность» и «Кандидаты» —
`candidate_list_options` (`list_type = position`). Добавленное там значение
сразу доступно во всех трёх разделах, без миграции. Город и координатор —
тоже общие справочники (`city`, `coordinator`).

Район и станция метро своего справочника не имеют — варианты для фильтра
строятся из уже загруженных данных.

## Статус набора

Пять фиксированных значений:

| Значение | Смысл |
|---|---|
| 🟥 Стоп (никого) | Подбор полностью остановлен |
| 🟨 Резерв | Подбор только в резерв, ожидание выхода ≈ неделя |
| 🟦 Найм (на всякий случай) | Без срочной необходимости, кандидатов направлять при наличии |
| 🟩 Любых берём | Максимальный приоритет, отправлять всех подходящих |
| 🟢 Без ограничений | Обычный режим подбора (значение по умолчанию для нового адреса) |

Хранится как `text` + `CHECK`, не enum — список проще расширить одной
миграцией, без двухфазного `ALTER TYPE ... ADD VALUE` (тот же приём, что
`staffing_demand_rows.status`).

## Приоритет

Пятиуровневая шкала звёздами: ★★★★★ Критический … ★ Минимальный. Хранится
как целое число 1–5, звёзды — только представление.

## Графики, смены, оплата

- График работы: 2/2, 3/3, 5/2, 6/1, 7/0, Гибкий, Подработка.
- Смены: День, Ночь, Смешанные.
- Время выхода: одно или несколько значений (`shift_times`, массив строк
  `HH:MM`).
- Оплата: тип (почасовая / за смену / за заказ) + размер.

Все — необязательные поля, заполняются после создания карточки.

## Контакты и комментарии

Координатор (общий справочник, как в «Кандидатах») с телефоном и Telegram;
руководитель объекта — **свободный текст**, не тот же справочник, что
`manager` у кандидатов: это разные роли (руководитель физического объекта, а
не рекрутинговый менеджер).

Комментарий координатора — большое текстовое поле для особенностей объекта
(«берём только мужчин», «есть бесплатное питание» и т. п.), до 4000
символов.

## Особенности объекта

Двенадцать чекбоксов (бесплатное питание, форма, обучение, раздевалка, душ,
парковка, медкнижка обязательна, можно без опыта, можно иностранцам,
еженедельные выплаты, проживание, компенсация проезда) — хранятся как
массив слагов (`features`), подписи только на клиенте: новый чекбокс не
требует миграции.

## Документы — только внешние ссылки

**В проекте нет Supabase Storage** — ни бакета, ни политик загрузки. Вместо
прикрепления файлов карточка хранит список **ссылок** на внешние файлы
(Google/Яндекс Диск и т. п.): `{id, title, url, type}` в `document_links`
(jsonb). Реальная загрузка файлов на сервер — осознанно отложена, см.
«Известные ограничения» ниже.

## Служебная информация карточки

Без полноценной истории изменений (см. ниже) карточка всё равно показывает:
дату и автора создания, дату и автора последнего изменения, текущий статус
и состояние (активен/архив) — снимок «кто/когда», а не построчный аудит.
Автор резолвится в читаемый логин на сервере (триггером), не через клиентский
`join` — таблица пользователей закрыта RLS.

## Фильтрация и поиск

Фильтры: проект, город, специализация, район, метро, тип объекта, статус,
приоритет, координатор, плюс сегментированный переключатель
активные/архив. Поиск — свободный текст, ищет одновременно по полному
адресу, метро, району, городу, координатору и руководителю объекта, без
выбора конкретного поля.

Все вычисления (фильтрация, поиск, KPI) — на уже загруженных данных в
браузере; повторный запрос к серверу происходит только после
создания/редактирования/архивирования/восстановления/дублирования записи.

## Быстрые действия

Открыть карточку (клик по строке), редактировать (та же карточка —
Drawer, не отдельная страница), перевести в архив/восстановить
(переключатель в строке), дублировать адрес.

**Дублирование** очищает `id`, даты и поля авторства (проставляются заново
при вставке), добавляет суффикс `" (копия)"` к адресу и **сразу открывает
карточку копии** для редактирования.

## Импорт потребности из Excel

Кнопка **«Загрузить потребность»** в тулбаре раздела — видна только
head/coordinator (`can('settings')`, тот же гейт, что у редактирования
«Описания вакансии»), в отличие от остального раздела, доступного всем
четырём ролям. Модуль реализации — `src/lib/imports/`, UI — `ImportDemandModal.tsx`,
история — панель «История импортов потребности» в Настройках
(`ImportHistoryPanel.tsx`, видна только руководителю).

**Результат импорта — карточки этого раздела, а не строки «Потребности».**
Один объект = одна карточка `public.addresses` на ключ
`project + city + full_address + position`, у которой заполняется
`required_count` — сколько людей нужно на этот объект. Один открытый тикет
в выгрузке = один требуемый человек, поэтому несколько тикетов на один
объект и должность складываются в одно число (`addressPlan.ts`, шаг
агрегации). Дата тикета в ключ **не входит**: у карточки адреса нет
измерения по датам (в отличие от матрицы «Потребность»), поэтому тикеты
одного объекта за разные дни — это по-прежнему один объект.

**Модель.** У каждого проекта — свой формат Excel и свой парсер, подключаемый
через `project_import_configs` (project → parser_key → column_mapping),
не хардкодом в коде. Единый внутренний формат (`DemandImportRow`):
проект, город, должность, дата, потребность, адрес. Для карточки адреса
адрес **обязателен** — строка без адреса отклоняется с ошибкой (карточку
не из чего создавать), в отличие от строки матрицы «Потребность», где
адрес был необязателен.

**Сопоставление с существующими карточками** делается в приложении, а не
уникальным индексом БД: в `public.addresses` уже могут быть заведённые
руками карточки с совпадающим ключом, и добавление constraint'а сломало бы
миграцию на боевых данных. Импорт читает активные карточки проекта и
матчит по ключу в памяти, регистронезависимо (чтобы «МСК Снежная 20» и
«мск снежная 20» не стали двумя карточками). Совпало — обновляется
`required_count`; не совпало — создаётся новая карточка. Повторный импорт
того же файла поэтому не плодит дубликаты.

**Условия работы.** Если выгрузка проекта содержит их, импорт заполняет и
условия на объекте: станцию метро (`metro`), график (`schedule_type`),
дневная/ночная смена (`shift_type`) и чекбоксы особенностей (`features`).
Колонки необязательные — файл без них по-прежнему создаёт карточки, просто
с пустыми полями. Приведение значений к тому, что допускает схема, — в
`src/lib/imports/mapping/normalizeConditions.ts`.

**Импорт не затирает ручные правки.** У уже существующей карточки условия
дописываются только в **пустые** поля: если координатор уточнил метро или
поменял график, повторная загрузка это сохранит. Особенности не заменяются,
а дополняются — проставленные руками чекбоксы остаются. Исключение —
`required_count`: это то число, ради которого делается импорт, и оно
подчиняется выбранному режиму.

**Поля новой карточки.** Из файла приходят `project`/`city`/`full_address`/
`position`/`required_count` плюс условия выше. Район, тип объекта, статус,
приоритет, укомплектованность остаются пустыми/дефолтными — координатор
дозаполняет их вручную в карточке адреса (`AddressDrawer`).

**Для проекта «Лавка» реализован специализированный парсер.** Остальные
проекты временно используют generic-парсер. После получения образцов Excel
для каждого проекта будут реализованы собственные `parser_*.ts` без
изменения архитектуры импорта.

«Лавка» — разговорное сокращение; значение в справочнике проектов
(`candidate_list_options`, `list_type = 'project'`) и в `project_import_configs.project`
буквально — **«Яндекс Лавка»** (список выбора проекта в модалке строится из
этого справочника, поиск конфигурации импорта — по точному совпадению
строки). Аналогично «БК» в этом разделе — это «Бургер кинг Россия», «Газпром» —
«Газпромнефть»; «Купер» совпадает буквально.

Она — первый проект с реальным файлом на входе (выгрузка тикетов из
Yandex Tracker, не плоская таблица) и первый со своим `DemandParser`
(`src/lib/imports/parsers/parser_lavka.ts`, `parser_key = 'lavka_v1'`): город
и адрес разбираются из колонки «Задача», должность — из «Теги»,
потребность считается по тикетам не в статусе «Закрыт» (один тикет = одна
открытая позиция, колонка «Количество вакансий» в реальном файле не
заполняется). В файле есть своя колонка с датой («Обновлено») — она
разбирается, но **не используется**: дата потребности всегда та, что
пользователь ввёл в форме импорта (см. ниже), одна на весь файл.

Проверено на реальной выгрузке (`МСК_31.07.xlsx`, 2090 строк): 1930
тикетов в статусе «Закрыт» отсекаются, из оставшихся получается **102
карточки адресов** с суммарной потребностью 151 человек (например, 10
открытых тикетов «Кладовщик» на «МСК Алтуфьевское шоссе, 8 (супермаркет
10)» дают одну карточку с `required_count = 10`). Заполняемость условий на
том же файле: метро — 100% объектов, смена — 99%, график — 81% (остальные
записаны как `3/1`, `вахта`, `ежедневно` — вне списка, допустимого схемой),
разгрузка — 53%.

**Режимы импорта:**

- **«Заменить»** — `required_count` совпавших карточек перезаписывается
  числом из файла. Карточки, которых в файле нет, не меняются.
- **«Добавить»** — число из файла прибавляется к текущему `required_count`.
  Карточки, которых в файле нет, не меняются.
- **«Синхронизировать»** — как «Заменить», плюс обнуляет `required_count`
  у карточек проекта, которых в файле нет.

**Зачем нужен третий режим.** Выгрузка тикетов показывает только открытые
позиции: когда объект укомплектовали, он из файла просто исчезает. В
режимах «Заменить»/«Добавить» такая карточка навсегда сохраняет старое
«Требуется: 10» — данные тихо устаревают. «Синхронизировать» считает файл
источником истины по проекту и приводит остальные объекты к нулю.

Обнуляется именно `required_count`, а не архивируется и не удаляется
карточка: объект физически существует и, скорее всего, вернётся в следующей
выгрузке — вместе со всем, что координатор заполнил руками. **Карточки,
заведённые вручную (`source = 'manual'`), не обнуляются** — файл им не
источник истины; их количество показывается в отчёте отдельным
предупреждением. Также не трогаются карточки без специализации (они не
участвуют в сопоставлении) и те, у которых `required_count` уже 0.

**Область синхронизации — только выбранный в форме проект, никогда вся
база.** Это гарантировано на двух независимых уровнях: сначала SQL-запрос
(`listActiveAddressesForProject`) читает из базы только карточки этого
проекта — карточки «Самокат»/«Магнит»/«Ozon» и т. д. в память вообще не
попадают; затем сама функция `planAddressWrites` (`src/lib/imports/
addressPlan.ts`) защитно проверяет `card.project === project` перед тем,
как решить обнулять карточку — на случай, если её вызовут с
неотфильтрованным списком. Обе проверки покрыты тестами
(`addressPlan.test.ts`).

## Дата потребности и история по датам

Форма импорта требует **дату потребности** — вводится вручную (`<input
type="date">`, по умолчанию сегодня), одна дата на весь файл. **Не
читается из Excel**, даже если у парсера проекта есть своя колонка с
датой (как «Обновлено» у «Лавки») — та колонка разбирается парсером, но
для этой цели игнорируется.

На эту дату пишется снимок в `public.address_demand_history` — один снимок
на (адрес, дата), по каждой карточке, которую коснулся импорт (создание,
обновление, обнуление в режиме «Синхронизировать»). Повторный импорт на ту
же дату обновляет существующий снимок, не плодит новый (уникальный ключ
`(address_id, demand_date)`). Хранится бессрочно, без автоматического
удаления/архивирования — это журнал, не рабочая таблица.

**Раздел «Потребность» показывает вычисленную сумму там, где она есть.**
Для комбинации проект+город+должность+дата, у которой есть снимки в
истории, отображается `SUM(required_count)` по подходящим адресам —
такие ячейки залочены (иконка замка, клик не открывает редактирование) и
подписаны «Значение рассчитано автоматически из импорта адресов». Для
всех остальных комбинаций (23 из 24 проектов без Excel-импорта) раздел
работает как раньше — ручной ввод, без изменений. Вычисление происходит
на каждом чтении через SQL-функцию `staffing_demand_effective(from, to)`,
не хранится отдельно и не может «устареть»; подробности архитектуры,
почему функция, а не `VIEW`, разбор индексов и масштабируемость — в
[`../database/schema.md`](../database/schema.md) и
[`demand.md`](demand.md#потребность-из-импорта-адресов).

**Откат импорта** дополнительно удаляет снимки истории по `import_id` —
никакого отдельного пересчёта не требуется, функция сама покажет
правильную сумму (или обычную ручную строку, если снимков не осталось) на
следующем чтении.

Перед реальной записью — кнопка «Проверить» (dry-run): та же валидация и
тот же отчёт, но без записи в базу — можно повторять сколько угодно раз.
**Отчёт с пометкой «Это проверка — данные не записаны в базу» означает, что
импорт ещё не выполнен**; чтобы записать, нужно нажать «Импортировать».
Для «Синхронизировать» это особенно важно: dry-run показывает, сколько
объектов будет обнулено, до того как это произойдёт.

**Предпросмотр строк.** Отчёт показывает не только счётчики, но и таблицу
самих объектов: действие (новый/обновление/обнуление), город, должность,
адрес, «было → станет» — по одной строке на карточку `public.addresses`
(`ImportPreviewRow` в `src/lib/imports/preview.ts`, собирается внутри
`planAddressWrites`). Это тот же список для dry-run и для реального
импорта — на dry-run таблица показывает, что *будет* записано, на реальном
импорте — что было записано.

**Ошибки строк** (неверный формат, нет обязательных столбцов, пустая
строка, некорректная дата, отрицательная потребность, неизвестный
город/должность, отсутствие адреса) не блокируют весь импорт — ошибочные
строки просто не импортируются и попадают в журнал ошибок отчёта.
Неизвестная должность — самая частая причина отклонения: справочник
должностей курируется в «Настройки → Списки», и значения из тикетов
(например, «КГЕ», «Мобильный КГЕ») отклоняются, пока их туда не добавят.

**История импортов** (`staffing_demand_imports`) хранит не только сводку,
но и полный `error_log`/`warnings`, кто/когда/каким парсером загружал,
сколько карточек создано/обновлено/обнулено, длительность. Для последнего
импорта доступна отмена («Отменить импорт») — удаляет карточки адресов,
созданные этим импортом.

### Известные ограничения импорта

- **Реальные парсеры БК/Газпром/Купер не реализованы.** Эти три проекта
  временно указывают в `project_import_configs` на один и тот же
  универсальный `genericColumnParser` с одинаковым маппингом колонок
  (`Город`/`Адрес`/`Должность`/`Потребность`/`Дата`) — нет образцов
  реальных файлов. «Лавка» (первый внедряемый проект) на этот generic-парсер
  больше не завязана — у неё свой `parser_lavka.ts`. Подключение настоящего
  формата каждого из оставшихся проектов — отдельная задача: либо новая
  строка в `project_import_configs` (если структура файла остаётся
  «плоской»), либо новая реализация `DemandParser` в
  `src/lib/imports/parsers/`, без изменения остального модуля.
- **Время смены не импортируется.** Колонка «Время смены» есть в выгрузке,
  но записана 84 разными способами (`15:00-00:00`, `15.00-00.00`, `15-00`,
  `12-00,15-00,10-22`) — надёжно разобрать её в `shift_times` пока нечем,
  поле остаётся пустым.
- **У объекта хранится один график.** `schedule_type` — одно значение, а в
  файле встречается `«2/2,5/2»`: берётся первый распознанный, остальные
  теряются. Хранить список графиков — отдельное решение по модели данных.
- **Нет уникального индекса на ключ карточки.** Совпадения ищутся в
  приложении: `public.addresses` может уже содержать заведённые руками
  дубликаты по (project, city, full_address, position), и constraint не
  накатился бы на боевые данные. Как следствие, два одновременных импорта
  одного файла теоретически могут создать дубли — на практике импорт
  выполняет один человек вручную.
- **Формат `.xls` (старый бинарный Excel) не читается.** Библиотека
  `exceljs` поддерживает только `.xlsx`; проверка расширения на клиенте не
  ограничивает, но реальный парсинг `.xls`-файла завершится ошибкой формата.
- **Откат импорта — не полноценный undo.** Безопасно (без потери данных)
  отменяются только импорты, которые ничего не меняли у существующих
  карточек, а лишь создали новые (`updated_rows = 0` и `zeroed_rows = 0`) —
  они просто удаляются по `import_id`. Если импорт перезаписал или обнулил
  `required_count` уже существующей карточки, вернуть прежнее значение
  нельзя: «до»-снимок не хранится. Кнопка отмены в UI скрыта для таких
  импортов (`canRevertImport`). Практически это означает, что импорт в
  режиме «Синхронизировать» почти всегда неотменяем — тем важнее сначала
  прогнать «Проверить».
  **`canRevertImport` смотрит только на сам отменяемый импорт**, а не на то,
  трогал ли карточку, которую он создал, какой-то ДРУГОЙ, более поздний
  импорт. Если импорт A только создал карточку X (значит, формально
  отменяем), а следующий импорт B позже обновил X (`updated_rows` у B — не
  у A), «Отменить» всё равно доступна для A: она удалит X целиком, включая
  всё, что записал B, — а с `address_demand_history` это ещё и каскадом
  удалит **всю** историю карточки X по всем датам, не только снимок,
  который писал сам A (`on delete cascade` от `addresses`, см. описание
  политики хранения при таблице `address_demand_history` в
  [`../database/schema.md`](../database/schema.md)). Раньше (до истории)
  тот же откат просто терял актуальное `required_count`; теперь он вместе с
  ним теряет и журнал. Известный, непроверенный автоматически риск —
  требует либо явной проверки «карточку не трогал никто после создателя»,
  либо запрета отмены импортов старше N часов; в объём этой задачи не
  входит.
- **Обнуление не различает «объект закрыли» и «выгрузку сделали не по всем
  городам».** «Синхронизировать» считает, что файл описывает проект
  целиком. Если загрузить выгрузку только по Москве, объекты других
  городов этого проекта обнулятся. Файл на часть проекта нужно грузить
  режимом «Заменить».
- **Массовые операции «Потребности» не проверяют залоченные даты.**
  «Добавить потребность» и «Повторить неделю» пишут прямо в
  `staffing_demand` и не смотрят, есть ли для этой даты снимок в истории.
  Отображаемое значение это не искажает — `staffing_demand_effective()`
  всё равно покажет сумму из истории, история побеждает при коллизии — но
  лишняя строка в `staffing_demand` останется мёртвым весом. Известное
  ограничение, чинить отдельной задачей (нужен либо другой ключ, либо
  проверка на сервере, которую JS-клиент Supabase не выражает как
  условный upsert).
- **Колонки `address`/`source`/`import_id` в `staffing_demand`** (миграция
  `20260805110000`) остались от первой версии импорта, которая писала
  туда напрямую; сейчас в саму таблицу их заполняет только ручной ввод
  (`source = 'manual'`, `address = null`) — то, что видит раздел
  «Потребность», может отличаться (см. выше про `staffing_demand_effective`).
  Удаление этих колонок из базовой таблицы — отдельная задача, они ничего
  не ломают.

## Известные ограничения

Формулируются явно, чтобы не считались багом:

- **Полной истории изменений по полям нет.** Есть только снимок «кто/когда
  создал/изменил» в самой строке — не построчный аудит, как у
  `staffing_demand_history`. Полноценная история (с записью старого/нового
  значения по каждому полю и вкладкой «История» в карточке) —
  зафиксированная следующая задача.
- **Документы — только ссылки**, реальной загрузки файлов нет: в проекте
  нет Supabase Storage, заводить его в рамках этой задачи не стали.
- **Нет подтверждения перед архивированием** — действие мгновенное, с
  тостом, без модалки-подтверждения (как сейчас и у кандидатов).
- **Нет серверной пагинации** — весь список грузится в браузер целиком, как
  у кандидатов и потребности.
- **Разграничения данных по проектам нет** — как и везде в портале,
  координатор одного проекта видит адреса всех проектов.

## Чего нет и не планируется в этой версии

- Отображение адресов на карте (задел есть — `latitude`/`longitude` отдельными
  полями).
- Комментарии нескольких пользователей к одному адресу.
- Уведомления по конкретным адресам.
- Связь адреса с конкретными вакансиями/кандидатами.
