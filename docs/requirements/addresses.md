# Требования: Адреса

Централизованное управление объектами найма (дарксторы, магазины, склады,
ПВЗ, рестораны, производства, офисы и т. д.). Реализовано на реальных
данных Supabase.

Техническое описание раздела —
[`src/components/portal/sections/addresses/README.md`](../../src/components/portal/sections/addresses/README.md),
схема таблицы — [`../database/schema.md`](../database/schema.md).

## Задача раздела

Координатор должен видеть и вести всю информацию по одному объекту подбора
из одного места: потребность, статус набора, характеристики, контакты,
комментарии и (в следующей задаче) историю изменений.

## Общая концепция

**Один адрес = одна карточка.** В отличие от «Потребности» (где строка —
это проект+город+должность+дата), у адреса нет отдельных карточек по
должностям: специализация — одно из полей карточки, а не измерение матрицы.

Раздел видят **все четыре роли** (руководитель, координатор, менеджер,
рекрутер) — вместе с «Уведомлениями» это единственные разделы с таким
охватом.

## Активные и архив

Не отдельные страницы — **сегментированный переключатель** «Активные /
Архив» поверх одной и той же таблицы, переключение мгновенное. Технически —
soft delete через `archived_at` (как у кандидатов), в UI — переключатель в
строке и в карточке.

При переводе в архив:

- адрес пропадает из вкладки «Активные»;
- не участвует в расчёте KPI дашборда (ни при каком выборе фильтров);
- документы, комментарии и служебная информация полностью сохраняются;
- восстанавливается одним нажатием, без потери данных.

## Дашборд

Восемь агрегированных карточек: Всего адресов, Активных, Архивных, Общая
потребность, Закрыто вакансий, Незакрытая потребность, Критичных адресов,
Средняя укомплектованность.

**Всего/Активных/Архивных** считаются по **полному** набору данных,
независимо от текущих фильтров — это глобальные счётчики. Остальные пять
KPI считаются по **отфильтрованной** выборке **без архивных записей**,
даже если открыта вкладка «Архив» — архив никогда не входит в KPI.

## Вычисляемые показатели — не хранятся

**Дефицит и укомплектованность никогда не пишутся в базу** — только
`required_count`/`staffed_count` и производные от них считаются на клиенте
при каждом рендере (`addressMetrics.ts`):

- `Дефицит = Требуется − Есть сотрудников` (может быть отрицательным при
  переукомплектованности — это допустимо, не ошибка);
- `Укомплектованность % = Есть / Требуется × 100`, но **при `Требуется = 0`
  результат явно `100%`**, а не `0%` — осознанное исключение из общего
  правила «пустая выборка/деление на ноль → 0», принятое отдельно для этого
  раздела;
- «Незакрытая потребность» (агрегат дашборда) = сумма дефицитов, каждый
  предварительно ограниченный снизу нулём (переукомплектованные адреса не
  уменьшают общую цифру);
- «Закрыто вакансий» = сумма `staffed_count`;
- «Критичных адресов» = количество адресов с приоритетом «Критический» (5).

Так исключается рассинхронизация данных между хранимым и отображаемым
значением.

## Специализация — общий справочник с «Потребностью»

Поле называется `position` (не `specialization`) намеренно: это **тот же
справочник**, что используют «Потребность» и «Кандидаты» —
`candidate_list_options` (`list_type = position`). Добавленное там значение
сразу доступно во всех трёх разделах, без миграции. Город и координатор —
тоже общие справочники (`city`, `coordinator`).

Район и станция метро своего справочника не имеют — варианты для фильтра
строятся из уже загруженных данных.

## Статус набора

Пять фиксированных значений:

| Значение | Смысл |
|---|---|
| 🟥 Стоп (никого) | Подбор полностью остановлен |
| 🟨 Резерв | Подбор только в резерв, ожидание выхода ≈ неделя |
| 🟦 Найм (на всякий случай) | Без срочной необходимости, кандидатов направлять при наличии |
| 🟩 Любых берём | Максимальный приоритет, отправлять всех подходящих |
| 🟢 Без ограничений | Обычный режим подбора (значение по умолчанию для нового адреса) |

Хранится как `text` + `CHECK`, не enum — список проще расширить одной
миграцией, без двухфазного `ALTER TYPE ... ADD VALUE` (тот же приём, что
`staffing_demand_rows.status`).

## Приоритет

Пятиуровневая шкала звёздами: ★★★★★ Критический … ★ Минимальный. Хранится
как целое число 1–5, звёзды — только представление.

## Графики, смены, оплата

- График работы: 2/2, 3/3, 5/2, 6/1, 7/0, Гибкий, Подработка.
- Смены: День, Ночь, Смешанные.
- Время выхода: одно или несколько значений (`shift_times`, массив строк
  `HH:MM`).
- Оплата: тип (почасовая / за смену / за заказ) + размер.

Все — необязательные поля, заполняются после создания карточки.

## Контакты и комментарии

Координатор (общий справочник, как в «Кандидатах») с телефоном и Telegram;
руководитель объекта — **свободный текст**, не тот же справочник, что
`manager` у кандидатов: это разные роли (руководитель физического объекта, а
не рекрутинговый менеджер).

Комментарий координатора — большое текстовое поле для особенностей объекта
(«берём только мужчин», «есть бесплатное питание» и т. п.), до 4000
символов.

## Особенности объекта

Двенадцать чекбоксов (бесплатное питание, форма, обучение, раздевалка, душ,
парковка, медкнижка обязательна, можно без опыта, можно иностранцам,
еженедельные выплаты, проживание, компенсация проезда) — хранятся как
массив слагов (`features`), подписи только на клиенте: новый чекбокс не
требует миграции.

## Документы — только внешние ссылки

**В проекте нет Supabase Storage** — ни бакета, ни политик загрузки. Вместо
прикрепления файлов карточка хранит список **ссылок** на внешние файлы
(Google/Яндекс Диск и т. п.): `{id, title, url, type}` в `document_links`
(jsonb). Реальная загрузка файлов на сервер — осознанно отложена, см.
«Известные ограничения» ниже.

## Служебная информация карточки

Без полноценной истории изменений (см. ниже) карточка всё равно показывает:
дату и автора создания, дату и автора последнего изменения, текущий статус
и состояние (активен/архив) — снимок «кто/когда», а не построчный аудит.
Автор резолвится в читаемый логин на сервере (триггером), не через клиентский
`join` — таблица пользователей закрыта RLS.

## Фильтрация и поиск

Фильтры: проект, город, специализация, район, метро, тип объекта, статус,
приоритет, координатор, плюс сегментированный переключатель
активные/архив. Поиск — свободный текст, ищет одновременно по полному
адресу, метро, району, городу, координатору и руководителю объекта, без
выбора конкретного поля.

Все вычисления (фильтрация, поиск, KPI) — на уже загруженных данных в
браузере; повторный запрос к серверу происходит только после
создания/редактирования/архивирования/восстановления/дублирования записи.

## Быстрые действия

Открыть карточку (клик по строке), редактировать (та же карточка —
Drawer, не отдельная страница), перевести в архив/восстановить
(переключатель в строке), дублировать адрес.

**Дублирование** очищает `id`, даты и поля авторства (проставляются заново
при вставке), добавляет суффикс `" (копия)"` к адресу и **сразу открывает
карточку копии** для редактирования.

## Импорт потребности из Excel

Кнопка **«Загрузить потребность»** в тулбаре раздела — видна только
head/coordinator (`can('settings')`, тот же гейт, что у редактирования
«Описания вакансии»), в отличие от остального раздела, доступного всем
четырём ролям. Модуль реализации — `src/lib/imports/`, UI — `ImportDemandModal.tsx`,
история — панель «История импортов потребности» в Настройках
(`ImportHistoryPanel.tsx`, видна только руководителю).

**Модель.** У каждого проекта — свой формат Excel и свой парсер, подключаемый
через `project_import_configs` (project → parser_key → column_mapping),
не хардкодом в коде. Единый внутренний формат (`DemandImportRow`):
проект, город, должность, дата, потребность, адрес (адрес — опционально,
`null` = потребность не привязана к конкретному объекту). Ключ
уникальности строки потребности — `project + city + position + demand_date + address`
(колонки `address`/`source` добавлены в `staffing_demand`, см.
`docs/database/schema.md`).

**Для проекта «Лавка» реализован специализированный парсер.** Остальные
проекты временно используют generic-парсер. После получения образцов Excel
для каждого проекта будут реализованы собственные `parser_*.ts` без
изменения архитектуры импорта.

«Лавка» — разговорное сокращение; значение в справочнике проектов
(`candidate_list_options`, `list_type = 'project'`) и в `project_import_configs.project`
буквально — **«Яндекс Лавка»** (список выбора проекта в модалке строится из
этого справочника, поиск конфигурации импорта — по точному совпадению
строки). Аналогично «БК» в этом разделе — это «Бургер кинг Россия», «Газпром» —
«Газпромнефть»; «Купер» совпадает буквально.

Она — первый проект с реальным файлом на входе (выгрузка тикетов из
Yandex Tracker, не плоская таблица) и первый со своим `DemandParser`
(`src/lib/imports/parsers/parser_lavka.ts`, `parser_key = 'lavka_v1'`): город
и адрес разбираются из колонки «Задача», должность — из «Теги», дата
потребности — из «Обновлено» (в файле нет отдельной колонки с датой
потребности — это ограничение источника, не единой модели), потребность
считается по тикетам не в статусе «Закрыт» (один тикет = одна открытая
позиция, колонка «Количество вакансий» в реальном файле не заполняется).
Несколько тикетов на одном ключе (город+должность+дата+адрес) суммируются
перед записью (`importDemand.ts`, шаг агрегации по ключу) — иначе upsert с
повторяющимся ключом в одном запросе завершился бы ошибкой Postgres.

**Режимы импорта:** «Заменить» (значение перезаписывается) и «Добавить»
(новое значение прибавляется к существующему). Перед реальной записью —
кнопка «Проверить» (dry-run): та же валидация и тот же отчёт, но без записи
в базу — можно повторять сколько угодно раз.

**Ошибки строк** (неверный формат, нет обязательных столбцов, пустая
строка, некорректная дата, отрицательная потребность, неизвестный
город/должность) не блокируют весь импорт — ошибочные строки просто не
импортируются и попадают в журнал ошибок отчёта.

**История импортов** (`staffing_demand_imports`) хранит не только сводку,
но и полный `error_log`/`warnings`, кто/когда/каким парсером загружал,
сколько строк новых/обновлено, длительность. Для последнего импорта
доступна отмена («Отменить импорт») — удаляет строки `staffing_demand`,
созданные этим импортом.

### Известные ограничения импорта

- **Реальные парсеры БК/Газпром/Купер не реализованы.** Эти три проекта
  временно указывают в `project_import_configs` на один и тот же
  универсальный `genericColumnParser` с одинаковым маппингом колонок
  (`Город`/`Адрес`/`Должность`/`Потребность`/`Дата`) — нет образцов
  реальных файлов. «Лавка» (первый внедряемый проект) на этот generic-парсер
  больше не завязана — у неё свой `parser_lavka.ts`. Подключение настоящего
  формата каждого из оставшихся проектов — отдельная задача: либо новая
  строка в `project_import_configs` (если структура файла остаётся
  «плоской»), либо новая реализация `DemandParser` в
  `src/lib/imports/parsers/`, без изменения остального модуля.
- **У «Лавки» дата потребности — заменитель.** В реальном файле нет
  колонки с датой, на которую нужен человек — используется дата последней
  актуализации тикета («Обновлено»). Если это не соответствует ожиданиям
  бизнеса, нужно уточнить у источника данных (Yandex Tracker) более точное
  поле или согласовать другое допущение — это ограничение исходных данных,
  не архитектуры импорта.
- **Формат `.xls` (старый бинарный Excel) не читается.** Библиотека
  `exceljs` поддерживает только `.xlsx`; проверка расширения на клиенте не
  ограничивает, но реальный парсинг `.xls`-файла завершится ошибкой формата.
- **Откат импорта — не полноценный undo.** Безопасно (без потери данных)
  отменяются только импорты в режиме «Заменить» или те, что создали
  исключительно новые строки. Если импорт в режиме «Добавить» обновил уже
  существующие строки, отменить его без потери прежнего значения нельзя —
  «до»-снимок значений не хранится. Кнопка отмены в UI скрыта для таких
  импортов (`canRevertImport`).
- **Матрица «Потребность» не показывает адрес.** Строки, пришедшие из
  Excel с непустым `address`, участвуют в агрегации по
  `project+city+position+date` наравне со строками без адреса — если для
  одной и той же даты есть и ручная запись, и несколько адресных из
  импорта, в текущем UI матрицы это может выглядеть как несколько
  отдельных ячеек с одним и тем же ключом без адреса; полноценная
  адресная детализация в самой матрице — вне рамок этой задачи.

## Известные ограничения

Формулируются явно, чтобы не считались багом:

- **Полной истории изменений по полям нет.** Есть только снимок «кто/когда
  создал/изменил» в самой строке — не построчный аудит, как у
  `staffing_demand_history`. Полноценная история (с записью старого/нового
  значения по каждому полю и вкладкой «История» в карточке) —
  зафиксированная следующая задача.
- **Документы — только ссылки**, реальной загрузки файлов нет: в проекте
  нет Supabase Storage, заводить его в рамках этой задачи не стали.
- **Нет подтверждения перед архивированием** — действие мгновенное, с
  тостом, без модалки-подтверждения (как сейчас и у кандидатов).
- **Нет серверной пагинации** — весь список грузится в браузер целиком, как
  у кандидатов и потребности.
- **Разграничения данных по проектам нет** — как и везде в портале,
  координатор одного проекта видит адреса всех проектов.

## Чего нет и не планируется в этой версии

- Отображение адресов на карте (задел есть — `latitude`/`longitude` отдельными
  полями).
- Комментарии нескольких пользователей к одному адресу.
- Уведомления по конкретным адресам.
- Связь адреса с конкретными вакансиями/кандидатами.
