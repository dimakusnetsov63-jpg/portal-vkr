# Portal VKR — требования

## Проект

**ВКР — Ваш кадровый ресурс** (Portal VKR).

## Назначение

Внутренняя система управления процессом массового подбора и аутсорсинга
линейного персонала. Закрывает планирование потребности в людях, ведение
кандидатов от отклика до выхода на смену и связанные кадровые процессы.

Доступ только для сотрудников компании. Самостоятельной регистрации нет:
учётные записи заводятся вручную в Supabase Dashboard.

## Основные разделы

| Раздел | Назначение | Источник данных |
|---|---|---|
| **Обзор** | Сводка по ключевым показателям | mock |
| **Потребность** | Планирование численности по проектам, городам, должностям и датам | **Supabase** |
| **Кандидаты** | Реестр кандидатов, стадии, карточка, архив | **Supabase** |
| **Описание вакансий** | Справочник условий по вакансиям | статические данные из Excel |
| **Маркетинг** | Каналы привлечения, стоимость отклика | mock |
| **Аналитика** | План/факт, воронка, эффективность | mock |
| **Уведомления** | Лента событий | mock |
| **Настройки** | Управление справочниками (города, рекрутёры, должности…) | **Supabase** |

На реальные данные переведены **Потребность**, **Кандидаты** и **справочники
в Настройках**. Остальные разделы работают на сгенерированных данных — цифры
там демонстрационные и не отражают реального положения дел. Это важно помнить
при показе портала заказчику.

## Пользовательские роли

> **Важно:** роли описаны как **бизнес-модель**, но **технически не реализованы**.
> В базе нет таблиц `profiles` и `roles`, все RLS-политики одинаковы для любого
> авторизованного пользователя. Фактически сегодня каждый сотрудник обладает
> правами администратора данных. См. [`ADR-002-auth.md`](../architecture/decisions/ADR-002-auth.md).

### Администратор

Отвечает за настройку системы и справочники.

- Управляет справочниками: города, рекрутёры, менеджеры, координаторы, должности.
- Заводит и отключает учётные записи сотрудников.
- Имеет полный доступ ко всем проектам и всем данным.
- Единственный, кто должен иметь право на удаление данных.

### Координатор

Ведёт оперативную работу по своим проектам.

- Заполняет и корректирует потребность по своим проектам и городам.
- Ставит статус строки и комментарий (например, «город на паузе»).
- Ведёт кандидатов: создаёт, обновляет стадии, переводит в архив.
- Не должен видеть и менять данные чужих проектов.

### Руководитель

Смотрит на картину целиком, данные не правит.

- Видит потребность и кандидатов по всем проектам в режиме чтения.
- Пользуется аналитикой и выгрузками.
- Не редактирует данные и не управляет справочниками.

## Основные бизнес-процессы

### 1. Создание потребности

Координатор планирует, сколько людей и на какой должности нужно в конкретном
городе конкретного проекта на каждый день.

1. Открывает раздел «Потребность» — матрица Проект → Город → Должность × даты.
2. Массово заводит новую строку через «Добавить потребность»: проект, один или
   несколько городов, одна или несколько должностей, период и количество.
3. Далее корректирует отдельные ячейки прямо в таблице.
4. При необходимости копирует значения на следующие дни или повторяет неделю.
5. Помечает строку статусом (активна / на паузе / закрыта) и комментарием.

Правило: строка появляется в матрице только если по ней есть хотя бы одна
запись за видимый период. Пустая ячейка означает «потребность не выставлена»
и отличается от явного нуля.

### 2. Работа с вакансиями

Условия по вакансиям (обязанности, требования, оплата, график) ведутся в
справочнике «Описание вакансий» и используются как опорная информация при
общении с кандидатом.

Сейчас данные статические, выгружены из Excel. Редактирования из интерфейса
нет — см. [`vacancies.md`](vacancies.md).

### 3. Работа с кандидатами

1. Рекрутёр создаёт кандидата: ФИО обязательно, остальное можно позже.
2. В карточке заполняются контакты, должность, город, медкнижка, даты.
3. По мере продвижения меняется стадия: прибыл на проект → отработал 1 смену →
   отработал 10 смен → завершил вахту.
4. Ключевая веха — дата первой смены: именно она означает успешный выход.
5. Завершившие работу переводятся в архив (не удаляются).

Метрики считаются по **текущей отфильтрованной выборке**, а не по всей базе —
это сознательное правило, см. [`candidates.md`](candidates.md).

### 4. Аналитика результатов

Руководитель оценивает выполнение плана: сопоставление потребности с
фактическими выходами, воронка по стадиям, эффективность рекрутёров и каналов.

Сейчас раздел работает на сгенерированных данных и с реальной потребностью
не связан — см. [`analytics.md`](analytics.md).

## Границы системы

Чего портал **не делает** и не планирует в ближайших версиях:

- не считает зарплату и не формирует выплаты;
- не ведёт табель учёта рабочего времени;
- не хранит сканы документов;
- не интегрирован с внешними job-площадками;
- не рассылает уведомления по email и в мессенджеры.
