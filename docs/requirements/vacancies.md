# Требования: Описание вакансий

> **Статус реализации:** TASK-010, редактируемый раздел на реальных данных
> Supabase. Миграции написаны, **не применены к боевой БД** (см.
> `docs/database/migrations.md`) — до применения раздел работать не будет.

## Задача раздела

Дать рекрутёру и координатору быстрый доступ к условиям по вакансии во время
разговора с кандидатом: что за работа, какие требования, сколько платят, какой
график. Голову и координатору — возможность редактировать эти условия прямо в
портале, без релиза.

Раздел отвечает на вопрос «что я могу пообещать кандидату», и по нему не
принимаются решения о численности — это задача раздела «Потребность».

## Структура

Вакансия — не жёсткий набор из десяти фиксированных карточек, а дерево из
трёх уровней:

- **Вакансия** (`vacancy_projects`) — название, категория (управляемый
  справочник, «Настройки → Списки → Категории вакансий»), архив.
- **Разделы** (`vacancy_sections`) — полностью произвольные: рекрутёр/
  координатор может переименовать, удалить, добавить свой («Обучение»,
  «FAQ», «Памятка координатору») без релиза. Единственное исключение —
  системный раздел **«Общая информация»**: создаётся один раз при создании
  вакансии с полями-затравками (Профиль, Должность в Битрикс, Регион
  работы, Период работы, Подробное описание, Дополнительное описание),
  всегда первый, всегда развёрнут, не удаляется и не архивируется.
- **Поля** (`vacancy_fields`) — пары «подпись → значение» внутри раздела.
  Типы поля: обычный текст, многострочный текст, форматированный текст
  (`rich_text` — облегчённое подмножество Markdown: **жирный**, *курсив*,
  списки, ссылки — не полноценный WYSIWYG-редактор), ссылка, число, дата,
  да/нет. Тип `select` (выбор из списка) зарезервирован в схеме, но
  редактор для него пока не построен — нужен отдельный источник вариантов.

Разбор приложенного к задаче Excel «Описание вакансий» (44 листа) показал:
единая табличная структура в исходнике отсутствует, только пары «подпись →
текст» с опечатками и расхождениями в написании одного и того же поля.
Частотный анализ подтвердил устойчивое ядро полей — оно используется только
как затравка для новой вакансии, не как ограничение схемы.

**Вложения** (`vacancy_attachments`, только внешние ссылки — в проекте нет
Supabase Storage) привязаны к вакансии, с необязательной привязкой к
конкретному разделу: можно прикрепить документ прямо к «Оформлению», а
можно оставить общим для всей вакансии.

## Права

- **Чтение** — все четыре роли (head/coordinator/manager/recruiter), как
  раньше.
- **Редактирование** (создание/правка/архивация вакансий, разделов, полей,
  вложений) — только `head` и `coordinator`. Решение принято в обсуждении
  задачи: раздел ближе к контенту компании, чем к операционным данным,
  которые правит любая роль (в отличие от «Адресов»/«Ставок»).

## Возможности редактора

- **Черновик**: «Редактировать» копирует загруженное дерево в память,
  «Отменить» — сбрасывает без обращения к серверу, «Сохранить» — один
  атомарный вызов (`portal_save_vacancy_project_tree`).
- **Оптимистическая блокировка**: при открытии вакансии запоминается
  `version`; если кто-то другой сохранил раньше — сохранение отклоняется с
  понятной ошибкой вместо тихой перезаписи, дальше нужно обновить данные и
  внести правки заново (без слияния черновиков).
- **Порядок**: разделы и поля переставляются стрелками ↑/↓ (drag-and-drop
  в проекте не используется — нет соответствующей библиотеки).
- **Поиск**: два независимых вида — мгновенная подсветка совпадений внутри
  уже открытой вакансии, и отдельный поиск по всем вакансиям сразу (по
  названию проекта, раздела, подписи или значению поля — RPC
  `search_vacancy_projects`).
- **Дублирование**: «Дублировать» копирует вакансию целиком (все разделы,
  поля, вложения) под новым названием — быстрый способ завести похожий
  проект.
- **История**: панель «История» показывает «кто/когда/что» по каждому
  изменению проекта/раздела/поля/вложения — снимки старой/новой строки, не
  построчный diff-viewer.

## Ограничения текущей реализации

- **Миграции не применены** — раздел не работает до выката (см.
  `docs/database/migrations.md`, `docs/tasks/TASK-010-vacancy-projects.md`).
- **`rich_text` — облегчённое подмножество Markdown**, не полноценный
  WYSIWYG-редактор (в проекте нет такой библиотеки).
- **Тип поля `select` зарезервирован, но не реализован** — нужен отдельный
  источник вариантов.
- **Сохранение дерева не полностью транзакционно на клиенте** — сам вызов
  `portal_save_vacancy_project_tree` атомарен на стороне базы (одна
  функция, одна транзакция), но это единственная операция такого рода в
  разделе; архивация вакансии — отдельный, более простой вызов.
- **Нет визуального diff в «Истории»** — только снимки old/new и краткое
  описание.
- **Нет библиотеки шаблонов вакансий** — есть только один встроенный
  шаблон-затравка («Общая информация» + рекомендованный список типовых
  разделов). Полноценные шаблоны (сохранить как шаблон, выбрать из
  нескольких при создании) — следующий этап, если бизнес будет регулярно
  заводить новые проекты.
- **Excel — только разовый источник переноса**
  (`scripts/import-vacancy-data.mjs`), не постоянный генератор: изменение
  условий по вакансии больше не требует релиза, а делается прямо в
  портале.
