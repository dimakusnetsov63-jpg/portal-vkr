# Требования: Потребность

Планирование численности персонала. Реализовано на реальных данных Supabase.

Техническое описание раздела —
[`src/components/portal/sections/demand/README.md`](../../src/components/portal/sections/demand/README.md),
схема таблиц — [`../database/schema.md`](../database/schema.md).

## Задача раздела

Координатор должен видеть и планировать, **сколько людей какой должности нужно
в каком городе какого проекта на каждый конкретный день**.

Единица планирования — ячейка на пересечении строки
(проект + город + должность) и даты.

## Структура матрицы

Три уровня группировки, каждый со своим итогом за период:

```
Проект                          ← итог по всем городам проекта
  └─ Город                      ← итог по всем должностям города
       └─ Должность             ← ячейки по датам + итог по строке
```

Проекты и города сворачиваются **независимо друг от друга**: свернуть один
город не должно влиять ни на соседние города, ни на проект целиком.

## Ключевые бизнес-правила

1. **Строка видна, только если по ней есть хотя бы одна запись** за видимый
   период. Полное перекрёстное произведение проектов × городов × должностей
   не строится — иначе матрица была бы нечитаемой.
2. **Новая строка заводится только через «Добавить потребность».** Правкой
   пустой матрицы новую комбинацию создать нельзя.
3. **Пустая ячейка ≠ ноль.** Пусто означает «потребность не выставлена»
   (записи в базе нет), `0` — явное решение «люди не нужны». Разница важна
   для отчётности.
4. **Очистка ячейки удаляет запись физически.** Потребность не архивируется:
   снятое значение не несёт ценности, а факт изменения всё равно сохраняется
   в истории.
5. **Итоги считаются по текущей отфильтрованной выборке**, а не по всем данным.
5a. **Итог за период — средняя дневная потребность, а не сумма.** Значения
   по дням, где потребность выставлена, усредняются (не делятся на длину
   всего окна) — так `100` за один день и `200` за другой дают «Итого 150»,
   а не 300, независимо от того, показано ли окно на 7 дней, месяц или год
   (`positionPeriodTotal`/`cityPeriodTotal`/`projectPeriodTotal`/
   `grandPeriodTotal` в `demandMetrics.ts`). Единственное исключение — итог
   **по столбцу** (одна дата, строка общего итога): там усреднять нечего,
   это сумма всех строк за один день, как и раньше.
6. **Статус и комментарий относятся к строке**, то есть к тройке
   (проект, город, должность), и **не привязаны к дате**. Отсутствие записи
   означает «активна, без комментария».
7. **Копирование значений не переносит статус и комментарий.** Ни копирование
   ячейки, ни повтор недели, ни массовое добавление их не затрагивают.
8. **Изменение одного поля не затирает другое**: правка статуса сохраняет
   комментарий и наоборот.

## Справочники

| Измерение | Источник | Расширяется |
|---|---|---|
| Проект | `candidate_list_options` (`project`) | из Настроек, без релиза |
| Город | `candidate_list_options` (`city`) | из Настроек, без релиза |
| Должность | `candidate_list_options` (`position`) | из Настроек, без релиза |

Должности **общие для всех проектов**: любая должность может использоваться на
любом проекте. Список плоский и намеренно смешивает типы работ (Курьер,
Кассир, Повар), виды транспорта (Авто, Вело, Пеший) и форматы занятости
(Универсал, Вахта) — так его задал бизнес.

Это тот же справочник, что используется в разделе «Кандидаты», — добавленная
должность сразу доступна в обоих разделах.

## Функциональные требования

### Просмотр

- Окно дат по умолчанию — от сегодня −14 до +45 дней.
- Навигация по неделям вперёд и назад, кнопка «Сегодня» с прокруткой к
  текущей дате.
- Текущий день и выходные визуально выделены.
- Цветовая индикация величины: пусто / ноль / обычная / повышенная / критичная.
- Липкие: шапка с датами, колонка со строками, колонка итогов, строка общего итога.
- Реализован **только режим «День»**. Неделя и Месяц не сделаны осознанно.

### Редактирование

- Правка ячейки на месте по клику: `Enter` сохраняет, `Escape` отменяет.
- Принимаются только целые числа ≥ 0.
- Во время сохранения ячейка показывает индикатор; при ошибке значение
  возвращается к прежнему.
- `Delete` / `Backspace` на выделенной ячейке очищает её.

### Массовые операции

- Добавление: проект + несколько городов + несколько должностей + период +
  количество. До сохранения показывается точное число затрагиваемых записей.
- При большом количестве записей — дополнительное подтверждение (защита от
  случайной перезаписи тысяч ячеек одним кликом).
- В той же форме можно сразу задать статус и комментарий для всех создаваемых
  строк.
- Копирование значения ячейки: на следующий день, на 7 дней, на всю неделю,
  до указанной даты.
- «Повторить строку на следующую неделю» — копирует значения текущей недели
  на следующую, только для своей должности.

### Фильтрация и поиск

- Фильтры: проект, город, должность, статус строки, «только заполненные».
- Поиск по проекту, городу и должности.
- Состояние фильтров и окна дат сохраняется в URL — ссылку можно передать
  коллеге, и он увидит тот же срез.

### История изменений

- Открывается из меню ячейки, грузится только по запросу.
- Показывает, что изменилось (было → стало), когда и кто изменил.
- Пишется автоматически на уровне базы, клиент не может её обойти или подделать.
- Исключение — ячейки, вычисленные из импорта «Адресов» (см. «Потребность
  из импорта адресов» ниже): они никогда не записываются в эту таблицу
  напрямую, поэтому триггер истории для них не срабатывает. Их история —
  `staffing_demand_imports`/`address_demand_history`, не эта.

## Потребность из импорта адресов

Раздел «Адреса» умеет загружать потребность из Excel на выбранную
пользователем дату (см. [`addresses.md`](addresses.md#дата-потребности-и-история-по-датам)).
Для комбинаций (проект, город, должность, дата), которые реально пришли
из такого импорта, эта матрица показывает **вычисленную сумму**, а не
ручную запись — правило 2 («новая строка только через «Добавить
потребность»») для них не действует, они появляются автоматически.

- Источник — не эта таблица (`public.staffing_demand`), а
  `public.address_demand_history` (снимки по адресам на дату). Значение
  вычисляется на каждое чтение функцией
  `staffing_demand_effective(from, to)`: там, где для ключа есть история —
  сумма из неё; иначе — обычная ручная строка, как всегда. Функция, а не
  `VIEW` или таблица-кэш — разбор архитектуры в `docs/database/schema.md`.
- Такие ячейки **залочены** — не кликаются, показывают замок и подсказку
  «Значение рассчитано автоматически из импорта адресов». Редактируются
  через карточку адреса, не здесь.
- **Не пишутся в историю изменений** (правило истории ниже, «пишется
  автоматически на уровне базы») — раз ячейка никогда не записывается в
  `staffing_demand` напрямую, аудит-триггер для неё не срабатывает.
  История именно этих данных — `staffing_demand_imports`/
  `address_demand_history`, отдельная от истории ручных правок.
- Затрагивает **не все проекты** — только те, для которых кто-то хоть раз
  загрузил файл через «Адреса» (на 07.08.2026 — только «Яндекс Лавка»).
  Остальные проекты видят и редактируют матрицу полностью как раньше.
- Массовые операции («Добавить потребность», «Повторить неделю») **не
  проверяют**, залочена ли дата — известное ограничение, см.
  `addresses.md`.

## Известные ограничения

Формулируются явно, чтобы не считались багом:

- **Данные не обновляются автоматически.** Изменения коллеги видны только
  после перезагрузки страницы.
- **Одновременное редактирование теряет данные.** При правке одной ячейки
  двумя людьми побеждает сохранивший последним; предупреждения нет. Увидеть,
  что произошло, можно только в истории изменений.
- **История статуса и комментария пишется, но не показывается** — экран для
  неё не сделан.
- **Объём данных растёт мультипликативно** (проекты × города × должности ×
  дни), а загружается окно целиком. Это первое узкое место раздела при росте;
  зафиксировано в [`../tasks/backlog.md`](../tasks/backlog.md). Данные из
  импорта адресов эту проблему не усугубляют: `staffing_demand_effective()`
  читает `address_demand_history` индексом по диапазону дат — стоимость
  зависит от размера окна, не от того, сколько лет накоплено истории (см.
  `docs/database/schema.md`) — но и не решают её для остального раздела:
  окно всё равно грузится в браузер целиком, как и раньше.

## Чего нет и не планируется в ближайшей версии

- Режимы «Неделя» и «Месяц».
- Факт выходов рядом с планом (план/факт в одной матрице).
- Связь строки потребности с конкретными кандидатами.
- Прямой импорт потребности из Excel **в этот раздел** — импорт есть
  (раздел «Адреса», см. «Потребность из импорта адресов» выше), но
  загружается через карточки адресов и дату потребности, не через файл с
  готовой матрицей проект+город+должность+дата.
