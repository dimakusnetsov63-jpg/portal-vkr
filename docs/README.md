# Portal VKR Documentation

Документация портала **«ВКР — Ваш кадровый ресурс»** — внутренней системы
управления массовым подбором и аутсорсингом линейного персонала.

Это **единственный источник актуального контекста по проекту**. Если что-то
расходится между кодом и документацией — правится документация, а не
замалчивается расхождение.

## С чего начать

**Новому разработчику или AI-инструменту** — читать в этом порядке:

1. [`requirements/overview.md`](requirements/overview.md) — что это за продукт,
   роли, бизнес-процессы
2. [`architecture/system.md`](architecture/system.md) — как устроена система
3. [`tasks/current.md`](tasks/current.md) — что делается прямо сейчас
4. [`../CLAUDE.md`](../CLAUDE.md) — правила работы с этим репозиторием

**Перед изменением кода** дополнительно: требования затрагиваемого раздела,
[`database/schema.md`](database/schema.md) — если задеты данные, и
[`testing/checklist.md`](testing/checklist.md) — перед тем как сказать
«работает».

## Стек

- **Next.js 16** (App Router, Turbopack) + **React 19** + **TypeScript** (strict)
- **Supabase** — Postgres, аутентификация, RLS. Собственного бэкенда нет
- **CSS Modules** для компонентов портала; **Tailwind 4** только в app-оболочке
- **Vitest** — тесты чистой логики
- **Vercel** — хостинг, автодеплой при пуше в `main`

## Текущее состояние проекта

Чтобы не создавать ложных ожиданий:

- На реальных данных Supabase работают **Потребность**, **Кандидаты** и
  справочники в **Настройках**.
- Разделы **Обзор**, **Маркетинг**, **Аналитика** работают на сгенерированных
  данных; **Описание вакансий** — на статических из Excel. Цифры там
  демонстрационные.
- Модель авторизации отсутствует: любой авторизованный сотрудник имеет полный
  доступ ко всем данным. Обязательно к закрытию до 1.0.
- Данные не обновляются в реальном времени: изменения коллеги видны только
  после перезагрузки.

## Правила обновления документации

1. **Документация обновляется вместе с кодом, в том же коммите.** Отдельный
   коммит «обновить доки потом» на практике не случается.
2. **Изменилось поведение — правится соответствующий `requirements/*.md`.**
3. **Изменилась схема — правятся `database/schema.md` и `migrations.md`.**
   Схема в документации должна соответствовать применённым миграциям.
4. **Принято значимое техническое решение — заводится новый ADR.**
   Существующие ADR не переписываются: если решение отменено, ставится статус
   «заменено на ADR-XXX».
5. **Не создавать файлы-заглушки.** Пустой раздел с заголовком хуже его
   отсутствия: он выглядит как документация, но контекста не даёт.
6. **Известные ограничения проговариваются явно.** Документ, который
   описывает только то, что работает, вводит в заблуждение и стоит дороже,
   чем его отсутствие.
7. **Завершённые задачи переносятся в `completed.md`, а не удаляются** — они
   объясняют, почему код устроен так, как устроен.
