## Блокирующее рост (сделать первым)

Эти задачи упираются не в количество пользователей, а в **объём данных**:
архитектура грузит все данные в браузер и фильтрует их там. Стена будет
достигнута по объёму задолго до роста аудитории.

### BLOCK-1. Серверная фильтрация и пагинация потребности

`listStaffingDemand` грузит всё окно дат целиком (`select("*")` без `limit`
и `range`), фильтры проекта, города и должности применяются в браузере.

После добавления должностей объём растёт мультипликативно: проекты × города ×
должности × дни. При 6 проектах, 10 городах, 6 должностях и окне 60 дней это
около 21 600 строк на каждую загрузку раздела. При `statement_timeout = 8s`
запрос начнёт отваливаться по таймауту.

**Решение:** фильтры на сервер (`.eq` / `.in`), обязательный `.range()`,
окно по умолчанию сузить с 60 до 7–14 дней, грузить только развёрнутые
проекты. **Оценка:** 2–3 дня.

### BLOCK-2. Серверная пагинация и поиск кандидатов

`listCandidates` грузит **всех** кандидатов при монтировании провайдера —
даже если пользователь в раздел не заходил. Пагинация в интерфейсе
косметическая: она режет только отрисовку.

Побочный эффект: вся персональная информация уезжает в браузер каждого
сотрудника.

**Решение:** серверная пагинация, серверные фильтры, полнотекстовый поиск
через уже существующий GIN-индекс `idx_candidates_full_name_trgm` (сейчас
не используется вовсе). **Оценка:** 3–4 дня.

### SEC-1. Разграничение доступа по проектам

Роли и доступ **по разделам** сделаны в TASK-004
([`TASK-004-portal-auth.md`](TASK-004-portal-auth.md)). Осталась вторая
половина: `portal_users.projects` заполняется, но ни одна политика по нему не
фильтрует — координатор одного проекта видит данные всех.

Туда же: ограничение доступа к персональным данным кандидатов (телефон,
telegram, `salary_card` доступны всем четырём ролям). Обязательно до 1.0.
**Оценка:** 3–4 дня.

### SEC-2. Очистка истёкших сессий

`portal_sessions` растёт без ограничений: отозванные и просроченные строки
не удаляются. При 100 сотрудниках это не проблема годами, но политика
хранения нужна. **Решение:** плановое удаление строк с
`expires_at < now() - interval '30 days'`. **Оценка:** 2 часа.

## Критичное

### CRIT-3. Ретенция и чанкование истории изменений

Каждое изменение потребности порождает строку в `staffing_demand_history`
через триггер. Массовое добавление на 3 600 ячеек — это 7 200 записей в одной
транзакции, с риском упереться в 8-секундный таймаут без частичного прогресса.

Таблица растёт безгранично: политики хранения и партиционирования нет.

**Решение:** чанкование массовых операций (по 500 строк), партиционирование
истории по месяцам, политика хранения. **Оценка:** 2 дня.

### CRIT-4. Bulk-запрос вместо N параллельных upsert'ов в `AddDemandModal`

Статус и комментарий при массовом добавлении сохраняются отдельным запросом
на каждую пару город × должность: 10 городов × 5 должностей = 50 параллельных
HTTP-запросов, 50 транзакций, 50 срабатываний триггера. При частичном сбое
состояние остаётся несогласованным.

**Решение:** один bulk-upsert в `staffing_demand_rows`. **Оценка:** 3–4 часа.
Дёшево, стоит сделать сразу.

### CRIT-5. Debounce синхронизации URL

`router.replace` вызывается на **каждый символ** в поиске потребности. Каждый
вызов — RSC-запрос → middleware → `portal_session_context()` → запрос в базу.
Debounce есть только в проверке логина при создании пользователя.

**Решение:** debounce 300–500 мс на запись URL; пересмотреть, нужно ли гонять
RSC-навигации через полную проверку сессии. **Оценка:** 4 часа. Очень дешёвая
задача с большим эффектом.

### CRIT-6. Разделение `PortalContext` и мемоизация матрицы

`useMemo` с 60 зависимостями: появление тоста или его автоисчезновение через
2.8 секунды перерисовывает всё дерево, включая каждую ячейку матрицы.
`React.memo` не используется в проекте нигде.

**Решение:** разделить контекст по доменам (demand / candidates / UI),
обернуть листовые компоненты матрицы в `React.memo`. См.
[`ADR-003`](../architecture/decisions/ADR-003-state-management.md).
**Оценка:** 4–5 дней.

### CRIT-7. Убрать forced reflow в `useHorizontalScrollSync`

Хук читает `scrollWidth` в эффекте **без массива зависимостей**, то есть после
каждого рендера обеих больших таблиц. Это принудительный синхронный пересчёт
layout; в связке с CRIT-6 даёт заметные подвисания интерфейса.

**Решение:** `ResizeObserver` вместо чтения на каждом рендере.
**Оценка:** 2–3 часа.

### CRIT-8. Защита от потери данных при одновременной работе

Оптимистичной блокировки нет: правки перезаписывают друг друга молча.
Статус и комментарий читаются, сливаются в приложении и пишутся целиком —
классический read-modify-write из устаревшего замыкания.

**Решение:** сверка по `updated_at` при сохранении с понятным сообщением о
конфликте; частичный `UPDATE` вместо перезаписи строки; Supabase Realtime на
`staffing_demand`, чтобы данные не устаревали молча. **Оценка:** 4–5 дней.

## Важное

### FEAT-1. Массовая очистка потребности

ТЗ готово — [`TASK-007-bulk-clear.md`](TASK-007-bulk-clear.md). Два режима
(«Очистить» / «Проставить 0») на разрез проект × город × должность × период,
с предпросмотром числа затронутых записей и отменой через `operation_id` в
`staffing_demand_history`. Попутно меняет поведение ввода `0` в одиночной
ячейке (сейчас удаляет строку, станет — сохранять ноль) — заметно для
пользователя, идёт в CHANGELOG.

Требует миграции (`operation_id`, право `demand_bulk` в обеих матрицах
прав) и регенерации `database.types.ts`. Массовые операции над адресами
сознательно не включены — у них нет истории изменений, сначала нужно
закрыть этот долг отдельной задачей. **Оценка:** 3–4 дня.

### INFRA-1. CI на GitHub Actions

Сейчас ничто не мешает влить в `main` код, ломающий сборку. Нужен прогон
`test` / `tsc` / `lint` / `build` на каждый push. **Оценка:** полдня.

### INFRA-2. Границы ошибок

`error.tsx` и `global-error.tsx` отсутствуют. Портал — SPA в одном роуте,
поэтому исключение в одной ячейке даёт белый экран на всё приложение.
**Оценка:** полдня.

### PERF-1. Code splitting

`next/dynamic`, `React.lazy` и `Suspense` не используются нигде. Все восемь
разделов, справочник вакансий (около 5 900 строк) и mock-генераторы попадают
в один бандл. Рекрутёр, работающий только с кандидатами, скачивает всё.
**Оценка:** 1 день.

### DB-1. Ревизия индексов после перехода на серверную фильтрацию

У `candidates` 17 индексов, а приложение делает `select *` с сортировкой по
дате — реально используется практически только `idx_candidates_created_at`.
Остальные создают стоимость записи, не давая выигрыша на чтении.

**Важно:** делать **после** BLOCK-1 и BLOCK-2 — при серверной фильтрации
большинство индексов станут нужны. Сейчас удалять нельзя.

### QA-1. Расширение тестов

Компонентные тесты для интерактивных узлов, тесты репозиториев против
тестового проекта Supabase, E2E на ключевой сценарий. См.
[`../testing/strategy.md`](../testing/strategy.md).

## Прочее

- Журнал изменений кандидатов и адресов (построчный аудит, как у
  «Потребности», есть только у неё). У адресов пока только снимок
  «кто/когда» в самой строке (`created_by`/`updated_by`) — не полноценная
  история, задел на будущее (см. TASK-005).
- Реальная загрузка документов адреса через Supabase Storage — сейчас
  только внешние ссылки (в проекте нет Storage вовсе).
- `updated_by` в `candidates`/`staffing_demand*` — известно *когда*, но не
  *кем* (у `addresses` уже решено).
- Нормализация городов (свободный текст допускает «Москва» и «москва»).
- Ограничения длины текстовых полей в схеме.
- Разбить `SettingsSection` (три компонента в одном файле).
- Общий `AuthShell` для страниц входа и восстановления пароля.
- Тёмная тема.
- Автовыход по бездействию.
- Перевод разделов Обзор, Маркетинг, Аналитика на реальные данные.
- Режимы «Неделя» и «Месяц» в потребности.
- Экран истории статуса и комментария (данные уже пишутся).
