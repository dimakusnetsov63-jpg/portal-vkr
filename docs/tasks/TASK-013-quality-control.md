# TASK-013 Раздел «Контроль качества»

## Цель

Раздел портала, в котором проверяющий открывает лид, ставит баллы по чек-листу
и сразу получает оценку по блокам и итог, а руководитель — сводку по
рекрутёрам, проектам и месяцам. Заменяет две рабочие таблицы Google Sheets /
Excel («Самоотказы КЦ», «Чек-листы по проектам») без потери ни одного
показателя, который в них считается сегодня.

## Контекст

Источник — два файла, разобранные целиком (все листы, формулы, выпадающие
списки) 18 августа 2026:

**«Самоотказы КЦ.xlsx»** — проверка лидов, закрытых самоотказом. Лист на
месяц, 4 критерия, шкала 0/1/2 → 0%/50%/100%: возражение отработано,
возражение отработано качественно, информативность комментария, причина
соответствует. Плюс метаданные лида (проект, рекрутер, должность, город,
возражение кандидата, целевой, скорость обработки, счётчик исходящих),
флаги «прослушен» и «кейс в аудиотеку». Заполнено: май 55, июнь 2765,
июль 219, август 0 строк. Справочник возражений — 24 значения в валидации.

**«Чек-листы по проектам.xlsx»** — оценка звонка целиком. Лист на проект
(Газпром, Бургер Кинг, Яндекс Лавка, Самокат вахта, Криспи, Самокат местный,
МД, Купер), 35–40 пунктов в 9 блоках, шкала 0/1/2, часть пунктов только 0/2.
Формулы дословно: блок = `сумма / (2 × число пунктов) × 100`, возражения =
`IF(«Возражение было?»="Да"; SUM(...)/8×100; "")`, итог =
`AVERAGE(<восемь блоков>)` — **блок «Возражения» в итог не входит**, это
записано в заголовке колонки. Заполнено: БК 163, Лавка 176, Самокат вахта 54,
Криспи 39, Самокат местный 12, МД 9, Купер 9, Газпром 0.

Почему уходим из таблиц — не «неудобно», а проверяемые дефекты:

1. **Колонки разъехались между листами.** «Общий процент» стоит в колонке 42
   («Самокат местный»), 43 (Газпром, БК), 44 (Криспи, МД, Самокат вахта),
   47 (Лавка, Купер). Любая сводная по фиксированному адресу уже неверна или
   сломается при следующей правке.
2. **У «Купера» один пункт вне блока** — в итог он не попадает вообще.
3. **Формула не дотянута.** В листе «База Август» общая формула колонки
   `% Возражение отработано` растянута на `N2:N140`, три соседние — на
   `:220`. Строки 141–220 посчитают три метрики из четырёх.
4. **`#DIV/0!` в «Сводной по рекрутерам»** у всех, у кого не было возражений.
5. **Пропуск неотличим от нуля.** Пустые пункты блока возражений `SUM`
   считает нулём, `AVERAGE` игнорирует; сегодня это работает случайно.
6. **Рекрутёры — свободный текст** с дублями и хвостовыми пробелами
   («Маслюкова Елизавета ») в 27 значениях, свой список в каждом листе.

## Допущения

Приняты по умолчанию, чтобы не блокировать работу. Меняются дёшево **до**
начала фазы 1, после — с переделкой миграций.

- **A1. Оба процесса на одном движке.** Самоотказы — частный случай
  чек-листа: шаблон из 4 пунктов без блоков. Различает поле `kind`
  (`refusal` / `call`). Два раздела означали бы два редактора, две сводные и
  две формулы расчёта.
- **A2. Раздел видят `head` и `coordinator` (чтение и запись), `manager` —
  только чтение, `recruiter` — не видит.** Это baseline-строка в
  `portal_section_permissions`, а не жёсткий код: с фазы E ADR-005 право
  переключается в «Настройки → Доступы» без деплоя. Доступ рекрутёра к
  **своим** проверкам в задачу не входит — см. «Не входит в задачу».
- **A3. История за май–август импортируется** из помесячных баз с
  **пересчётом** процентов из сырых баллов; сводные листы не импортируются —
  они выводятся.

## Бизнес-логика

### Шаблон

- Шаблон = вид (`call`/`refusal`) + проект. `project = null` — общий шаблон;
  при создании проверки берётся шаблон проекта, при его отсутствии — общий.
- Пункт имеет шкалу `0-1-2` (есть частичное выполнение), `0-2` (только да/нет)
  или `yes_no` — **пункт-переключатель**, который сам баллов не даёт, а
  включает или выключает свой блок («Возражение было?»).
- Пункты и блоки **не удаляются, а архивируются**: на них ссылаются прошлые
  проверки.
- Правка шаблона поднимает `version`. Прошлые проверки хранят
  `checklist_version` и собственный посчитанный итог — задним числом оценка
  не меняется никогда.

### Расчёт

- Блок: `Σ балл / (2 × Σ вес незачёркнутых пунктов) × 100`. Вес по умолчанию 1.
- Пункт «не применимо» **исключается из знаменателя**, а не считается нулём.
- Блок, где все пункты «н/д» или чей переключатель = «Нет», даёт `null`, а не
  `0`, и в итог не входит.
- Итог: **среднее по блокам** с `counts_in_total = true`. Блок «Возражения»
  заведён с `counts_in_total = false` и показывается отдельной цифрой — это
  воспроизводит текущую формулу один в один.
- Среднее по блокам, а не по пунктам, — сознательная совместимость с
  историей: блок «Работа с CRM» из одного пункта весит столько же, сколько
  «Сбор информации» из семи. Взвешивание по пунктам не делаем в этой задаче.
- Пустая проверка (ни одного пункта) — итог `null`, не `0` и не `NaN`.
- **Критическая ошибка**: флаг на пункте; балл `0` по такому пункту обнуляет
  итог всей проверки. В seed ни один пункт не критичный — иначе импорт
  истории даст цифры, отличные от Excel.

### Проверка

- Лид вводится номером (`3660718`) или ссылкой целиком — из ссылки номер
  разбирается. Хранится номер, ссылка собирается из настраиваемой базы URL.
- Повторная проверка того же лида **разрешена** (в файлах такие есть —
  например, лид 3605269), но форма предупреждает: «этот лид уже проверяли
  <дата>, <проверяющий>, <итог>».
- Черновик (`status = draft`) не попадает в сводки. В сводку идут только
  `completed` и далее.
- Итог и проценты по блокам считает **база** при сохранении и кладёт в
  `total_score`/`group_scores`. Клиент считает то же самое для живого превью
  в форме, но записанное значение приходит из RPC.

### Что не должно измениться

- Ни один существующий раздел, справочник и политика доступа.
- `candidate_list_options` пополняется новыми `list_type`, существующие типы
  не трогаются; проекты берутся из общего списка `list_type = project`
  (TASK-009) — свой список проектов не заводится.

Ключевые решения по схеме:

- `quality_reviews.total_score numeric(5,2)` и `group_scores jsonb` —
  **денормализация намеренная**: реестр на 3000 строк и сводка за год не
  должны пересобирать баллы по пунктам на каждый запрос, а прошлая оценка не
  должна меняться от правки шаблона.
- `quality_review_scores` — нормализованная таблица ответов (`pk (review_id,
  item_id)`), чтобы отчёт «какой пункт чаще всего проваливают» был обычным
  `group by`, а не разбором jsonb.
- FK на `quality_checklist_items` — `on delete restrict`: удалить пункт, на
  который ссылается проверка, нельзя даже вручную.
- `employee_user_id uuid null references portal_users` + `employee_name text
  not null`: у большинства проверяемых сотрудников КЦ учётки в портале нет.
  Имя нормализуется (trim, схлопывание пробелов) при импорте и при вводе.
- Индексы: `(review_date)`, `(project, review_date)`, `(employee_name,
  review_date)`, `(crm_lead_id)`.

**Backfill не требуется** — таблицы новые. `unique`-ограничений, влияющих на
существующие `onConflict`, не добавляется. **`database.types.ts`
регенерируется** после применения.

## Риски

- **Две реализации формулы расчёта** (TS для превью, SQL для записи) — риск
  расхождения. Смягчение: тест на одинаковых входах; записанное значение
  всегда из SQL, клиентское — только на экране. Решение оформляется отдельным
  ADR-006.
- **Импорт истории необратим по смыслу**: перенесённые строки станут
  «настоящими» проверками. Импорт выполняется скриптом с `--dry-run` по
  умолчанию (как `import-vacancy-data.mjs`), пишет `import_id` в каждую
  строку — откат = удаление по `import_id`.
- **Дрейф колонок в исходных листах** означает свой маппинг на каждый лист;
  ошибка маппинга даёт правдоподобные, но неверные баллы. Смягчение: импорт
  сверяет пересчитанный процент с процентом из файла и сообщает расхождения
  вместо молчаливой записи.
- **Объём.** 2765 проверок за месяц — верхняя оценка ~35 тыс. строк в год,
  для Postgres несущественно, но сводка за год без индексов будет
  `Seq Scan`. `EXPLAIN ANALYZE` на отчётном запросе — пункт приёмки.
- **Откат раздела** — новая миграция, убирающая `'quality'` из
  `portal_role_sections()` и строки из `portal_section_permissions`; таблицы
  остаются, остальной схеме они не мешают.

## Не входит в задачу

Проговорено явно, чтобы не выглядело недоделкой:

- **Доступ рекрутёра к своим проверкам.** Требует политики нового типа —
  «своя строка», тогда как в портале сейчас есть только изоляция по проектам
  (`portal_has_project`). Отдельная задача; вместе с ней — ознакомление и
  апелляция.
- **Интеграция с CRM.** Проект, рекрутёр, дата звонка, комментарий, город,
  должность, скорость обработки и счётчик звонков вводятся руками — это и
  есть основной расход времени проверяющего. Поля спроектированы под будущее
  автозаполнение по номеру лида, но запросов к Битриксу в этой задаче нет.
- **Хранение аудиозаписей.** Supabase Storage в проекте нет — «Аудиотека»
  оперирует ссылками на лид/запись.
- **План проверок** (N звонков на рекрутёра в месяц с прогрессом) —
  следующая итерация после того, как раздел наполнится данными.
- **Взвешивание итога по пунктам** вместо среднего по блокам.
