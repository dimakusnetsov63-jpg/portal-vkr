# TASK-010 Раздел «Описание вакансии» на Supabase

## Цель

Заменить статический read-only справочник «Описание вакансии»
(`src/lib/portal/vacancyData.ts`, собран вручную один раз из Excel) на
реальный, редактируемый в портале раздел: динамические разделы и поля вместо
плоской сетки, черновик/история/поиск/дублирование/вложения — без релиза на
каждое изменение условий по вакансии.

## Контекст

Пользователь попросил переработать интерфейс раздела, приложив
обновлённый Excel «Описание вакансий». В процессе обсуждения задача выросла
от «сделать Accordion» до полного переноса на Supabase с нормализованной,
полностью динамической структурой (не фиксированные 10 карточек), после
серии итераций пользователя над планом: нормализованные таблицы вместо
одного `jsonb`, атомарное RPC-сохранение, оптимистическая блокировка,
типы полей, вложения к разделу, глобальный поиск, дублирование, управляемый
справочник категорий. Полная история решений — в плане задачи (согласован
через `ExitPlanMode` перед реализацией).

## Бизнес-логика

- Раздел «Описание вакансии» отвечает на вопрос «что можно пообещать
  кандидату» — не про численность (это «Потребность»).
- Читают все 4 роли; редактируют только head/coordinator.
- Разделы вакансии — не фиксированный список: любой пользователь с правом
  редактирования создаёт свои. Единственное исключение — системный раздел
  «Общая информация» (не удаляется, не архивируется, всегда первый).
- Пустой раздел скрыт при чтении, но виден при редактировании (чтобы было
  куда добавить первое поле). Раздел с одним полем показывается всегда.
- Оптимистическая блокировка: сохранение отклоняется, если кто-то другой
  успел сохранить раньше (`vacancy_projects.version`), — без слияния
  черновиков, только честный отказ и предложение обновить данные.
- Полное описание — `docs/requirements/vacancies.md`.

## Технические изменения

### Frontend

Новая доменная папка `src/components/portal/sections/vacancies/`:
`VacanciesSection.tsx` (список+поиск+фильтр, глобальный поиск с debounce),
`VacancyDetail.tsx` (якорное меню + Accordion-разделы, черновик/сохранение,
история), `VacancySectionCard.tsx`, `VacancyFieldEditor.tsx`,
`VacancyAttachmentsList.tsx`, `VacancyHistoryPanel.tsx`, `FieldValueView.tsx`,
`AddVacancyProjectModal.tsx`, чистые `.ts`: `vacancyTreeDraft.ts`,
`renderFieldValue.ts`, `vacancyMarkdown.ts`, `vacancyOptions.ts` — все с
unit-тестами. Новый общий примитив `src/components/portal/ui/Accordion.tsx`
(такого компонента в проекте не было). Старые
`VacanciesSection.tsx`/`.module.css`/`src/lib/portal/vacancyData.ts` —
удалены.

### Backend

`src/lib/supabase/vacancyProjectsRepo.ts` + `vacancyProjects.types.ts` +
`vacancyHistoryRepo.ts`. Срез состояния в `PortalContext.tsx`
(`vacancyProjects`, CRUD-колбэки, `selectedVacancyProjectId`) — полное
дерево конкретной вакансии грузится лениво в `VacancyDetail`, не в
контексте.

### Database

5 новых таблиц (`vacancy_projects`, `vacancy_sections`, `vacancy_fields`,
`vacancy_attachments`, `vacancy_history`), новое значение
`candidate_list_type.vacancy_category`, 3 `SECURITY DEFINER` RPC-функции
(`portal_save_vacancy_project_tree`, `portal_duplicate_vacancy_project`,
`search_vacancy_projects`). Подробности — `docs/database/schema.md`,
`migrations.md`, `policies.md`.

- **Backfill не требуется** — новые таблицы, данные переносятся отдельным
  разовым скриптом (`scripts/import-vacancy-data.mjs`), не миграцией.
- **`unique`-ограничений, влияющих на `onConflict`, нет** — таблицы новые,
  конфликтов при первом заполнении не бывает.
- **Регенерация `database.types.ts` требуется** после применения всех
  миграций `20260805*` — до этого момента `src/lib/supabase/vacancyProjects.types.ts`
  и репозитории раздела не проходят проверку типов (см. комментарий в
  начале файла типов). Это ожидаемо, зафиксировано ниже.

## Acceptance Criteria

- [ ] Раздел «Описание вакансии» показывает вакансии из `vacancy_projects`
      вместо статического файла (после применения миграций).
- [ ] head/coordinator могут создать вакансию, добавить/переименовать/
      удалить/переупорядочить раздел и поле, сохранить дерево одним
      действием.
- [ ] manager/recruiter видят раздел и его содержимое, но не видят кнопок
      редактирования; прямой RPC-вызов от их имени отклоняется RLS.
- [ ] Повторное сохранение с устаревшей `version` отклоняется с понятной
      ошибкой, а не тихой перезаписью.
- [ ] Архивация/восстановление вакансии работает через простое `UPDATE`,
      не через RPC сохранения дерева.
- [ ] Поиск по всем вакансиям находит вакансию по слову внутри значения
      поля, не только по названию.
- [ ] Существующее поведение остальных разделов не изменилось: правки
      затронули только `vacancies`-раздел, матрицу прав (`roles.ts` +
      `portal_role_sections`) трогать не пришлось — `vacancies` уже был в
      обеих у всех четырёх ролей.

## Риски

- Миграции проекта применяются вручную через SQL Editor Supabase (прямой
  Postgres-протокол недоступен) — тот же порядок, что у предыдущих крупных
  миграций (`20260728120000` и др.). `20260805100700` (`ALTER TYPE ... ADD
  VALUE`) обязательно отдельным шагом от остальных — иначе применение
  упадёт (новое значение enum нельзя использовать в той же транзакции).
- `portal_save_vacancy_project_tree` — единственная операция в разделе,
  не защищённая полной клиентской транзакцией end-to-end (сама функция
  атомарна на стороне базы; сетевой сбой посередине запроса всё равно может
  оставить клиент в неопределённости о том, применились ли изменения — в
  этом случае повторное открытие вакансии покажет актуальное состояние).
- Откат — обычные `drop table`/`drop function` в обратном порядке
  миграций; данных для потери, кроме тестовых, на момент написания нет
  (раздел не был в проде).
