# TASK-007 Массовая очистка потребности

## Цель

Координатор должен уметь одним действием снять или обнулить потребность за
период — день, неделю или произвольный диапазон — в нужном разрезе (проект,
город, должность), увидев до применения точное число затрагиваемых записей и
имея возможность отменить операцию целиком.

## Контекст

Сейчас потребность снимается только по одной ячейке: клик → `Delete` или
пустое значение. Перепланировать неделю по городу — это десятки ручных
действий, ошибиться легко, а откатить нечем.

Обратная операция — массовое **добавление** — уже есть (`AddDemandModal`:
проект × города × должности × период × количество, с подсчётом записей и
подтверждением при большом объёме). Очистка должна быть её зеркалом и
переиспользовать те же паттерны.

## Что важно знать про текущую модель

Проверено по коду и миграциям, всё это ограничивает решение:

1. **Пусто ≠ 0.** Отсутствие строки в `staffing_demand` = «план не
   составлен». `planned_count = 0` = «людей не нужно» (праздник, объект
   закрыт). Различие описано в
   [`requirements/demand.md`](../requirements/demand.md) п. 3 и в комментарии
   к колонке в миграции.

2. **…но 0 сегодня недостижим из интерфейса.** `resolveCellCommit` при вводе
   `0` удаляет строку и никогда не сохраняет ноль
   ([demandCellEdit.ts](../../src/components/portal/sections/demand/demandCellEdit.ts),
   на это есть тест), а `AddDemandModal` требует количество > 0. Уровень
   `zero` в матрице (`.lvlZero`, `DemandCell.tsx`) не может возникнуть ни при
   каком сценарии — модель, требования и стили описывают состояние, которого
   в системе нет. Задача это чинит, см. «Ввод нуля в одиночной ячейке».

3. **История массовой операции пишется сама.** Триггер
   `log_staffing_demand_change()` — `for each row` на insert/update/delete,
   поэтому изменение 500 ячеек даст 500 записей в `staffing_demand_history`
   с `old_quantity`/`new_quantity`, полным ключом (project, city, position,
   demand_date), `changed_by` и `changed_at`. `changed_by` = `auth.uid()` =
   id пользователя портала (портал сам подписывает JWT, см.
   [`jwt.ts`](../../src/lib/auth/jwt.ts)). **Данные для отмены уже есть —
   не хватает только группировки пачки в одну операцию.**

4. **Права только на уровне раздела.** `portal_role_sections()` и
   [`roles.ts`](../../src/lib/auth/roles.ts) дают доступ к разделу целиком;
   отдельного права «может массово удалять» нет. Сегодня всё, что доступно в
   «Потребности», доступно и менеджеру.

5. **Массовые операции упираются в таймаут.** [`backlog.md`](backlog.md),
   CRIT-3: 3 600 ячеек → 7 200 строк истории в одной транзакции, риск
   8-секундного лимита без частичного прогресса. Очистка обязана чанковаться.

6. **Серверных задач в проекте нет.** Только три маршрута `/api/auth/*`,
   серверного Supabase-клиента для данных не существует.

## Бизнес-логика

### Два режима операции

| Режим | Что делает | Зачем |
|---|---|---|
| **Очистить** | физически удаляет строки `staffing_demand` | план на период отменён / составляется заново |
| **Проставить 0** | `planned_count = 0` для тех же ячеек | «людей не нужно»: праздник, объект закрыт |

Разница видна в матрице: после «Очистить» ячейка пустая (уровень `empty`),
после «Проставить 0» — с нулём (уровень `zero`). Именно ради этого различия
оно и заводилось в модели.

### Область действия

Определяется четырьмя параметрами:

| Параметр | Значения | По умолчанию |
|---|---|---|
| Период | конкретный день · неделя · произвольный диапазон | текущая видимая неделя |
| Проект | один или несколько; пусто = все видимые | из текущего фильтра |
| Город | несколько; пусто = все | из текущего фильтра |
| Должность | несколько; пусто = все | из текущего фильтра |

Быстрые пресеты периода: «Следующая неделя», «Текущая неделя», «Завтра»,
«Произвольный диапазон». «Следующая неделя» = ближайший понедельник–
воскресенье относительно сегодня, независимо от того, какое окно дат открыто
в матрице.

### Ключевое ограничение обоих режимов

**Операция работает только по уже существующим строкам матрицы** — то есть по
тройкам (проект, город, должность), у которых есть хотя бы одна запись.
Новых строк она не заводит.

Для «Очистить» это следует из смысла. Для «Проставить 0» это осознанное
ограничение: иначе обнуление недели по всем проектам создало бы записи на
полное перекрёстное произведение проектов × городов × должностей × дней и
завалило бы матрицу строками, которых там никогда не было. Соответствует
п. 1–2 требований: строка видна, только если по ней есть запись, а заводится
она только через «Добавить потребность».

Практическое следствие: чтобы отметить «1 января людей не нужно» по строке,
которой ещё нет, нужно сначала завести строку через «Добавить потребность».

### Чего операция не делает

- не трогает `staffing_demand_rows` (статус и комментарий строки) — они не
  привязаны к дате, и снятие чисел не означает, что строка закрыта.
  Симметрично п. 7 требований: копирование значений не переносит статус и
  комментарий, здесь удаление значений его не снимает;
- не трогает адреса и кандидатов.

### Граничные случаи

- **Пустое пересечение** — в предпросмотре `0 записей`, кнопка применения
  заблокирована. Не ошибка.
- **Даты в прошлом.** По умолчанию в диапазон **не попадают дни раньше
  сегодняшнего**: прошлое — это отчётность. Чтобы захватить прошлое, нужен
  явный переключатель «Включая прошедшие даты», сбрасываемый при каждом
  открытии модалки.
- **«Очистить» по ячейкам со значением 0** — удаляет их наравне с
  остальными: 0 тоже выставленный план.
- **«Проставить 0» по ячейке, где уже 0** — no-op, в счётчик затрагиваемых
  записей не попадает.
- **Частичный сбой при чанковании** — операция не откатывается целиком.
  Пользователю сообщается, сколько чанков применилось; применённое остаётся
  и доступно к отмене. Молчаливый «наполовину применён» недопустим.
- **Параллельная правка.** Между предпросмотром и применением коллега мог
  изменить ячейку. Операция идёт по ключу, а не по снимку, поэтому захватит и
  новое значение. Это то же «побеждает последний», что уже описано в
  ограничениях раздела; отдельной защиты не делаем, но фиксируем.

### Отмена операции

**Требование:** любую массовую операцию можно отменить целиком.

В `staffing_demand_history` добавляется `operation_id uuid null`, общий для
всех строк одной пачки. Отмена = прочитать записи с этим `operation_id` и
применить обратное действие:

| Записано в истории | Что делает отмена |
|---|---|
| `delete` | вставить строку с `old_quantity` |
| `update` | вернуть `old_quantity` |
| `insert` | удалить строку |

Такая схема покрывает оба режима сразу и в будущем ляжет на массовое
добавление без доработок.

Отмена доступна до конца сессии: кнопка в тосте сразу после операции. Сама
операция и её отмена видны в «Истории изменений» ячейки как обычные записи.
Отдельного экрана «Журнал массовых операций» в задачу не входит.

### Ввод нуля в одиночной ячейке (изменение существующего поведения)

Раз 0 становится достижимым значением, ввод в ячейке приводится к
однозначным правилам:

| Ввод | Было | Станет |
|---|---|---|
| пусто, `Delete`, `Backspace` | удалить строку | удалить строку (без изменений) |
| `0` поверх значения | **удалить строку** | **сохранить 0** |
| `0` поверх пустой ячейки | no-op | no-op (строка не заводится, см. ограничение выше) |
| отрицательные, дробные, текст | no-op | no-op (без изменений) |

Правится `resolveCellCommit` и его тест
(`«deletes when typing 0 over a non-zero value»` заменяется на обратное
утверждение). Это **заметное для пользователя изменение поведения** — идёт в
CHANGELOG.

`AddDemandModal` продолжает требовать количество > 0: эта форма заводит
потребность, а не отменяет её. Обнуление делается ячейкой или массовым
режимом «Проставить 0».

### Права

Массовая операция — не то же самое, что правка одной ячейки. Ограничивается
ролями **Руководитель и Координатор**.

Реализация без слома существующей модели: псевдо-раздел `demand_bulk`
добавляется в **обе** матрицы прав (`ROLE_PERMISSIONS` в `roles.ts` и
`portal_role_sections()` в SQL) и проверяется в RLS-политике на DELETE и на
массовый UPDATE. Менеджер сохраняет право чистить ячейки по одной, но не
периодами.

это единственный слой, покрытый тестами.

### Backend

`staffingDemandRepo.ts`:

- `bulkClearStaffingDemand(scope, mode, chunkSize = 500)` — чанками, по
  ключам (не `.in()` по огромному списку id), возвращает число затронутых
  строк и `operation_id`;
- `undoStaffingDemandOperation(operationId)` — обратное применение по
  таблице выше.

### Database

- Миграция: `alter table public.staffing_demand_history add column operation_id uuid`
  + частичный индекс по `operation_id is not null`. Backfill не нужен:
  у старых записей остаётся `null`.
- Миграция: `portal_role_sections()` получает `demand_bulk`; политики
  `staffing_demand` на DELETE и массовый UPDATE проверяют это право.
- Уникальные ограничения не меняются, `onConflict` в репозитории не трогаем.
- **Требуется регенерация `database.types.ts`.**

## Acceptance Criteria

- [ ] «Очистить период» → «Следующая неделя» + один город удаляет ровно
      ячейки понедельника–воскресенья следующей недели по этому городу и не
      трогает соседние города, другие должности и другие недели
- [ ] «Проставить 0» на том же разрезе оставляет строки на месте и
      показывает в них ноль, а не пустоту
- [ ] «Проставить 0» не создаёт новых строк матрицы
- [ ] Число в предпросмотре совпадает с числом фактически затронутых строк
- [ ] Даты раньше сегодняшнего дня не затрагиваются, пока не включён явный
      переключатель; переключатель сброшен при каждом открытии модалки
- [ ] Статус и комментарий строки после операции сохранились
- [ ] Отмена возвращает прежние значения ровно в те же ячейки — для обоих
      режимов
- [ ] Ввод `0` в одиночной ячейке сохраняет ноль; пустой ввод и `Delete`
      по-прежнему удаляют строку
- [ ] Операция на 3 000+ ячеек проходит без таймаута; при обрыве
      пользователь видит, сколько применилось
- [ ] Менеджер не видит кнопку и получает отказ на прямой запрос к API
- [ ] Каждая затронутая ячейка видна в «Истории изменений» с прежним
      значением и автором
- [ ] Не изменилось: копирование ячейки, повтор недели, массовое добавление,
      фильтры, URL-состояние

## Риски

- **Необратимая потеря плана** — главный риск. Снимается предпросмотром,
  подтверждением с явным числом и отменой. Без отмены задачу выпускать не
  стоит.
- **Смена поведения нуля** заденет тех, кто привык очищать ячейку вводом
  `0`. Пустой ввод и `Delete` продолжают работать, но об изменении нужно
  сказать в CHANGELOG явно.
- **Рост `staffing_demand_history`** — операция удваивает нагрузку на
  таблицу, которая и так растёт без ретенции (CRIT-3). Чанкование
  обязательно, ретенцию решать отдельной задачей.
- **Расхождение матриц прав** — новое право живёт в двух местах, ошибку не
  поймают ни типы, ни тесты.

## Что сознательно не входит

- **Массовые операции над адресами.** У `public.addresses` нет
  DELETE-политики (только `archived_at`) и, что важнее, **нет истории
  изменений** — только снимок `created_by`/`updated_by` в строке. Массовая
  правка адресов была бы неотменяемой и неаудируемой, в отличие от
  потребности. Сначала закрывается долг по истории адресов (записан в
  [`current.md`](current.md)), потом массовые операции.
- **Очистка по расписанию** (еженедельный автосброс). В проекте нет серверных
  задач и серверного Supabase-клиента для данных — отдельная
  инфраструктурная задача.
- **Экран «Журнал массовых операций».**
- **Массовая очистка кандидатов:** у них soft-delete и своя семантика
  архива, смешивать в одну задачу не нужно.
