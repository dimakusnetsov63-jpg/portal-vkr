## TASK-012 — Единая система управления доступами

**Статус:** `IN PROGRESS` — фаза A реализована, **не применена к БД**
**Решение:** [`ADR-005`](../architecture/decisions/ADR-005-access-control-v2.md)

Права разделов переезжают из кода в базу и получают три уровня вместо
одного булева «раздел доступен»: `visible` (пункт меню — только UX),
`can_view` (открыть и читать), `can_edit` (изменять). Инвариант
`can_edit => can_view => visible` закреплён `check`-ограничениями в базе.
Плюс доступ к проектам получает признак «все проекты» вместо перечисления
руками.

Выкат разбит на фазы, чтобы наблюдаемое поведение менялось не разом:

| Фаза | Что | Статус |
|---|---|---|
| A | Таблица `portal_section_permissions`, `all_projects`, функции `portal_can_view_section`/`portal_can_edit_section`, baseline seed | **готова, подтверждена CI** |
| B | Сверка baseline на реальной базе | **пройдена в CI** (11 августа 2026) |
| C | Перевод политик RLS на `view`/`edit` + закрытие project-gap у `project_import_configs`/`staffing_demand_imports` | **готова, к БД не применена** |
| D | Permission layer, RPC управления правами, аудит изменений | не начата |
| E | Интерфейс «Настройки → Доступы», чекбокс «Все проекты» | не начата |

### Фаза B — что подтвердил CI

Прогон на эфемерном Postgres (джоба `rls-tests`) подтвердил: все четыре
миграции фазы A применяются на чистую базу, baseline seed валиден,
`portal_role_sections()` работает через PostgREST и совпадает с `roles.ts`
для всех четырёх ролей включая порядок, `all_projects` работает, матрица
закрыта от пользовательского доступа. Расхождений не найдено. Локально
проверить было нечем — на машине разработки нет Docker.

### Фаза C — что сделано

Четыре миграции `20260811110000`…`20260811110300` (C1–C4), 50 политик и три
`SECURITY DEFINER`-функции. Подробности — в
[`../database/policies.md`](../database/policies.md) и
[`../database/migrations.md`](../database/migrations.md).

**Единственное изменение поведения** — `project_import_configs` и
`staffing_demand_imports` получили `portal_has_project(project)` (пробел
H-6 закрыт). Вынесено отдельной миграцией C4 и последней, чтобы
откатывалось независимо от C1–C3.

Негативные тесты добавлены: manager не пишет в `vacancy_*`, recruiter не
пишет в `candidate_list_options`, координатор не видит импорты чужого
проекта, и три CHECK-инварианта `portal_section_permissions` (последний
непроверенный кусок фазы A).

**Не проверено:** миграции C1–C4 не выполнялись ни на боевой базе, ни
локально; `npm run test:rls` не запускался. Фаза C — **code-complete,
DB-unverified**, до прогона CI.

### Фаза A — что сделано

## TASK-011 — Импорт потребности из Excel

**Статус:** `IN PROGRESS`

Кнопка «Загрузить потребность» в разделе «Адреса» (только head/coordinator):
проект+файл → предпросмотр/dry-run («Проверить») → режимы «Заменить»/
«Добавить» → **создание/обновление карточек этого же раздела**
(`public.addresses`, поля `source`/`import_id` из миграции
`20260807100000`): один объект = одна карточка на (проект, город, адрес,
должность) с заполненным `required_count`, один открытый тикет = один
требуемый человек. Каждый проект — свой
парсер, подключаемый через `project_import_configs`, без изменения кода.
История импортов с деталями (`error_log`/`warnings`) и отмена последнего
импорта — в Настройках (руководитель). Для проекта «Лавка» реализован
специализированный парсер (`parser_lavka.ts`, под реальную выгрузку тикетов
из Yandex Tracker); остальные проекты временно используют generic-парсер.
После получения образцов Excel для каждого проекта будут реализованы
собственные `parser_*.ts` без изменения архитектуры импорта. Подробности —
[`../requirements/addresses.md`](../requirements/addresses.md#импорт-потребности-из-excel).

UI полностью подключён: кнопка → модалка (проект+файл → «Проверить»/dry-run
→ отчёт со статистикой и журналом ошибок → «Импортировать» → повторный
отчёт) → после реального импорта `usePortal().refreshAddresses()` подтягивает
свежие карточки без перезагрузки страницы, обе ветки (успех/ошибка) идут через
`pushToast`. Код проверен `typecheck`/`lint`/`test` (303 теста)/`build`.
Пайплайн прогнан против реального файла (`МСК_31.07.xlsx`, 2090 строк):
1930 закрытых тикетов отсекаются, из оставшихся получается **102 карточки
адресов** с суммарной потребностью 151 человек.

Первая версия писала строки в `staffing_demand` (раздел «Потребность») —
после ручной проверки на реальных данных выяснилось, что нужен другой
результат: список объектов в «Адресах». Переделано, миграция
`20260807100000`.

**Расширение — дата потребности + история по адресам** (миграция
`20260807100300_address_demand_history.sql`, архитектурный план утверждён
до реализации, см. `docs/database/schema.md`). Форма импорта теперь
требует дату потребности (вручную, не из файла). Каждый импорт пишет
снимок «сколько людей требовалось на адресе на дату» в новую таблицу
`address_demand_history`; повторный импорт той же даты обновляет снимок,
не плодит дубликат. Раздел «Потребность» для комбинаций
проект+город+должность+дата, пришедших из такой истории, показывает
**вычисленную сумму** (функция `staffing_demand_effective(from, to)`,
`FULL OUTER JOIN` `staffing_demand`×агрегата истории — не `VIEW`, чтобы
гарантированно проталкивать фильтр по датам до соединения) — ячейка
залочена в UI, редактируется через карточку адреса. Остальные проекты без
импорта продолжают работать в «Потребности» как раньше. Заодно исправлена
подтверждённая ошибка «Итого» — теперь среднее по дням с данными, а не
сумма, для любого окна (`demandMetrics.ts`). Код, тесты
(`demandHistoryPlan.test.ts`, переписанный `demandMetrics.test.ts`) и
документация готовы; миграция **применена к боевой БД** (7 августа 2026 —
две правки понадобились по ходу применения, найдены только на реальном
Postgres, см. `docs/database/migrations.md`).

Осталось:

- [x] применить миграцию `20260807100000_addresses_import_source.sql`
      (SQL Editor Supabase) — без неё у `addresses` нет `source`/`import_id`
      и импорт упадёт на записи
- [ ] применить `20260807100100_lavka_conditions_mapping.sql` — без неё
      парсер не увидит колонки условий и карточки создадутся без метро,
      графика и смены (упасть не упадёт)
- [ ] применить `20260807100200_import_sync_mode.sql` — без неё режим
      «Синхронизировать» упадёт на записи истории (CHECK не пускает
      `mode = 'sync'`)
- [x] применить `20260807100300_address_demand_history.sql` — применена

- [ ] `EXPLAIN ANALYZE select * from staffing_demand_effective(...)` на

- [ ] регенерировать `database.types.ts` штатной командой и свериться с

- [ ] добавить в «Настройки → Списки → Должности» значения, которые

      «Мобильный КГЕ», «Кладовщик, auto_selfaccept_ping») — иначе эти строки
      продолжат отклоняться как «Неизвестная должность»
- [ ] проверить по [`../testing/checklist.md`](../testing/checklist.md)
      видимость кнопки под всеми четырьмя ролями

Не вошло в задачу и оставлено долгом:

- [ ] реальные парсеры БК/Газпром/Купер — нет образцов файлов, используется
