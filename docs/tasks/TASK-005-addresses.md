# TASK-005 Раздел «Адреса»

## Цель

Координатор получает единое рабочее место по каждому объекту найма
(даркстор/магазин/склад/ПВЗ/ресторан/…): потребность, статус набора,
характеристики, комментарии и архив — в одной карточке, без матрицы по
датам. Руководитель — дашборд с агрегированными KPI и фильтрами по проекту,
городу, специализации, статусу и приоритету.

## Контекст

Заказано отдельным ТЗ «Разработка раздела «Адреса» для Portal VKR» (полный
текст — в истории переписки, не хранится в репозитории). Раздел строится по
образцу уже реализованных «Потребность» и «Кандидаты»: реальные данные
Supabase, RLS через `portal_can()`, общий справочник специализаций.

Решения, согласованные до реализации:

1. Раздел видят все четыре роли (не только руководитель/координатор, как
   большинство разделов).
2. Документы — только внешние ссылки, без загрузки файлов: в проекте нет
   Supabase Storage, заводить его в этой задаче не стали.
3. Полная история изменений по каждому полю — вынесена в отдельную
   следующую задачу. В этой версии — только лёгкий снимок «кто/когда
   создал/изменил» в самой строке (`created_by`/`updated_by` + текстовый
   логин), заложенный так, чтобы полноценный построчный аудит потом не
   потребовал переделки схемы.
4. Специализация переименована из черновой `specialization` в `position` —
   единый нейминг с «Потребностью»/«Кандидатами», один и тот же справочник
   (`candidate_list_options`, `list_type = position`).
5. Координаты — сразу отдельные `latitude`/`longitude` (numeric), не одна
   строка: карта/маршруты/поиск ближайших адресов не потребуют миграции.

## Бизнес-логика

Подробно — [`../requirements/addresses.md`](../requirements/addresses.md).
Ключевое:

- Дефицит и % укомплектованности **не хранятся**, считаются на клиенте;
  при `required_count = 0` укомплектованность — явно `100%` (не `0%`).
- KPI «Всего/Активных/Архивных» — по полному набору данных; остальные пять
  KPI — по отфильтрованной выборке без архивных записей, независимо от того,
  какая вкладка открыта.
- Архив — сегментированный переключатель, не отдельная страница; soft-delete
  через `archived_at`.
- Поиск — по нескольким полям одновременно (адрес/метро/район/город/
  координатор/руководитель объекта).
- Дублирование очищает служебные поля и сразу открывает карточку копии.
- Что не должно измениться: существующие разделы (Потребность, Кандидаты,
  Настройки) — поведение и данные не менялись.

- `lib/auth/roles.ts` — `SECTION_ORDER` + `ROLE_PERMISSIONS` (все четыре роли).

### Database

- `supabase/migrations/20260729130000_create_addresses.sql` — таблица,
  индексы, триггер `set_addresses_audit_fields()`.
- `supabase/migrations/20260729130100_addresses_rls_policies.sql` —
  RLS-политики (`select`/`insert`/`update` на `portal_can('addresses')`, без
  `delete`).
- `supabase/migrations/20260729130200_update_portal_role_sections_addresses.sql`
  — `portal_role_sections()` + `'addresses'` для всех ролей.

Backfill не требуется (новая таблица, без существующих данных).
Уникальных ограничений с `onConflict`-зависимостями нет. `database.types.ts`
**не регенерирован** — миграция написана, но не применена к боевой БД (как и
`20260728120000_portal_auth.sql`); типы в `addresses.types.ts` написаны
вручную, с пометкой свести к выводу из `Database` после применения и
регенерации.

## Риски

- Три новые миграции **не применены к боевой БД** — раздел не будет
  получать/сохранять данные до применения (`npx supabase db push --linked`)
  и регенерации `database.types.ts`. Применение — только по отдельной
  команде пользователя, как и для `20260728120000_portal_auth.sql`.
- До применения `20260728120000_portal_auth.sql` вход в портал вообще может
  не работать — это предшествующее состояние проекта, не следствие этой
  задачи, но блокирует визуальную проверку в браузере.
- `addresses.types.ts` написан вручную: возможна рассинхронизация со
  сгенерированными типами после применения миграции — до тех пор,
  разработчик, меняющий схему `addresses`, должен править оба места вручную
  (как и `portalAuth.types.ts` сейчас).
- Откат: новые таблица/функции/политики — `drop table public.addresses
  cascade;` и обратная замена `portal_role_sections()` (убрать
  `'addresses'` из всех веток) отдельной миграцией; данные необратимо
  потеряются при откате, поэтому таблица не удаляется без явной команды.
