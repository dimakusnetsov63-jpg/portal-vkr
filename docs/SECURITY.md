# Безопасность

Практики безопасности портала ВКР и **реестр принятых исключений** по
уязвимостям зависимостей.

Модель доступа — [`database/policies.md`](database/policies.md) и
[`requirements/access-control.md`](requirements/access-control.md).
Обоснование собственной авторизации — [`ADR-004`](architecture/decisions/ADR-004-portal-auth.md).

## Сообщение об уязвимости

Портал внутренний, публичного bug bounty нет. О найденной уязвимости
сообщать руководителю проекта напрямую, **не** через issue в репозитории:
описание уязвимости в публичном трекере само по себе является раскрытием.

## Проверка зависимостей

Обязательная команда перед релизом:

```bash
npm audit --omit=dev
```

`--omit=dev` намеренно: уязвимость в `vitest` или `eslint` не достижима из
production-сборки, и смешивать её с реальным риском — значит обесценить
проверку. Полный `npm audit` (со сборочными зависимостями) полезен, но
релиз не блокирует.

**У этой команды есть слепое пятно, и его нужно знать.** `--omit=dev`
отсекает пакет по его месту в `package.json`, а не по тому, попадает ли он
в сборку. `exceljs` объявлен в `devDependencies`, но импортируется из
`src/lib/imports/excel/readWorkbook.ts` — то есть через `ImportDemandModal`
приезжает в серверный бандл и разбирает загружаемые пользователем файлы.
Проверено фактически: строка `exceljs` присутствует в
`.next/server/chunks/ssr/`. Для него `--omit=dev` показывает «чисто» там,
где чисто не есть.

Поэтому правило ниже применяется к `exceljs` наравне с production-деревом,
а при добавлении новой зависимости в `src/` её место в `package.json`
проверяется отдельно.

**Правило:** любой `high` или `critical` в production-дереве либо
устраняется, либо попадает в реестр ниже с обоснованием и датой пересмотра.
Молча оставленных красных пунктов быть не должно.

## Реестр исключений

Исключение = уязвимость, которую нельзя устранить обновлением прямой
зависимости, и которая оставлена сознательно. Каждая запись обязана
содержать: чем вызвана, почему не эксплуатируется здесь, когда пересмотреть.

### EX-001 · `postcss` внутри `next` — ЗАКРЫТО, override удалён

| | |
|---|---|
| **Пакет** | `postcss` (транзитивно, внутри дерева `next`) |
| **Advisory** | `GHSA-qx2v-qp2m-jg93`, `GHSA-6g55-p6wh-862q`, `GHSA-r28c-9q8g-f849` (high) |
| **Причина** | `next@16.2.12` закрепляет `postcss` **точной** версией `8.4.31`; исправление — в `> 8.5.17`. Апстрим-обновления на момент записи нет |
| **Решение** | Точечный `overrides` в `package.json`, ограниченный деревом `next` |
| **Статус** | ✅ Закрыто апстримом; `overrides` удалён 26 августа 2026 |
| **Дата** | 1 августа 2026, пересмотрено 26 августа 2026 |

**Пересмотр 26 августа 2026 — условие снятия наступило.** `next@16.3.3`
пинит `postcss@8.5.23`; за это время вышло новое advisory
`GHSA-fxqj-rqcc-2cmp` (чтение произвольных `.map` при незаданном `from`),
пропатченное **ровно в 8.5.23**. То есть собственный пин Next закрывает и
старые advisory, и новое, а блок `overrides` стал ровно тем, о чём
предупреждала запись: лишним ограничением, которое со временем удерживает
зависимость ниже апстрима. Удалён.

Проверено после удаления: в дереве остаются `postcss@8.5.23` (внутри
`next`) и `postcss@8.5.26` (внутри `@tailwindcss/postcss`), `npm audit`
по postcss чист, сборка проходит, карта маршрутов не изменилась.

Ниже — как было, для истории.

```json
"overrides": {
  "next": {
    "postcss": "^8.5.25"
  }
}
```

Override **намеренно ограничен `next`**, а не задан глобально: `@tailwindcss/postcss`
резолвит собственный `postcss@8.5.20` (уже пропатченный), и вмешиваться в его
дерево нет причин. Глобальный override менял бы больше, чем требуется.

Риск проверен фактически, а не оценочно: сборка пересобрана начисто и
вывод `.next/static` сравнён по sha256 — **все 18 файлов побайтово
идентичны** версии с `postcss@8.4.31` (различался только случайный build ID
в имени каталога). То есть подмена не изменила ни одного байта CSS или JS.

**Когда пересмотреть:** после каждого минорного обновления Next.js. Как
только `next` поднимет свой пин выше 8.5.17, блок `overrides` становится
избыточным и должен быть удалён — лишний override со временем начинает
удерживать зависимость **ниже** апстрима.

### EX-002 · `sharp` внутри `next` — ЗАКРЫТО апстримом

| | |
|---|---|
| **Пакет** | `sharp@0.34.5` (транзитивно, `optionalDependencies` пакета `next`) |
| **Advisory** | `GHSA-f88m-g3jw-g9cj` — унаследованные уязвимости libvips: `CVE-2026-33327`, `CVE-2026-33328`, `CVE-2026-35590`, `CVE-2026-35591` (high) |
| **Причина** | `next@16.2.12` объявляет `sharp: "^0.34.5"`; исправление — в `>= 0.35.0`. Апстрим-обновления нет |
| **Статус** | ✅ Закрыто 26 августа 2026 обновлением `next@16.2.12 → 16.3.3` |
| **Дата** | 1 августа 2026, закрыто 26 августа 2026 |

**Закрыто по условию 1 из списка пересмотра.** `next@16.3.3` объявляет
`sharp: "^0.35.3"`, то есть апстрим сам перешёл на исправленную ветку, и
принимать риск больше не нужно. Обновление патч-уровня, мажор не менялся.
После него `npm audit --omit=dev` даёт **0 уязвимостей** — впервые с
1 августа.

Оценка «путь до уязвимого кода отсутствует» при этом оказалась верной и
проверку пережила: `next/image` в портале так и не появился. Но полагаться
на неё больше не требуется.

Ниже — как было, для истории.

**Почему не эксплуатируется здесь.** `sharp` используется Next.js
исключительно для Image Optimization API (`/_next/image`). В портале:

- компонент `next/image` не используется **нигде** (проверено grep'ом; вместо
  него три `<img>` с локальными SVG — см. находку M-11 аудита);
- `images.remotePatterns` не настроен — в `next.config.ts` задан только
  блок `headers()`, раздела `images` нет;
- загрузки изображений пользователями в продукте нет вообще: документы в
  «Адресах» — только внешние ссылки, Supabase Storage не подключён;
- хостинг — Vercel, где оптимизацию изображений выполняет платформа, а не
  bundled `sharp` в сборке проекта.

То есть недоверенное изображение физически неоткуда взять — путь до
уязвимого кода отсутствует.

**Почему не закрыто через override.** `sharp 0.34 → 0.35` — не патч: меняются
нативные бинарники и мажорная версия libvips, меняется поведение обработки
изображений. Ставить это ради пакета, который сейчас не исполняется, —
принимать реальный риск сборки ради устранения нулевого риска рантайма.
Решение сознательно отложено.

**Когда пересмотреть — обязательно при любом из событий:**

1. апстрим: `next` поднял `sharp` до `>= 0.35.0` (тогда просто обновиться);
2. в проекте появился `next/image` или `images.remotePatterns`;
3. в проекте появилась загрузка файлов пользователями (Supabase Storage,
   импорт Excel с изображениями, аватары);
4. переход с Vercel на собственный хостинг — тогда `/_next/image` начинает
   обслуживаться bundled `sharp`.

До наступления любого из этих условий запись остаётся действительной.

### EX-003 · `uuid` внутри `exceljs` — ПРИНЯТО, не устраняется

| | |
|---|---|
| **Пакет** | `uuid@8.3.2` (транзитивно, `exceljs@4.4.0` объявляет `uuid: "^8.3.0"`) |
| **Advisory** | `GHSA-w5hq-g745-h8pq` — отсутствует проверка границ буфера в `v3()/v5()/v6()`, когда передан внешний `buf` (moderate) |
| **Причина** | Исправление — в `uuid@11.1.1`; `exceljs` пинит ветку 8.x. Апстрим-обновления `exceljs` нет |
| **Статус** | ⚠ Принято осознанно, полный `npm audit` остаётся жёлтым (2 moderate) |
| **Дата** | 26 августа 2026 |

**Почему не эксплуатируется здесь.** Уязвимы только `v3`, `v5` и `v6`, и
только когда вызывающий передаёт собственный буфер: `v4`, `v1` и `v7`
выбрасывают `RangeError` сами. `exceljs` вызывает `uuid` **в одном файле и
одной функцией** — `cf-rule-ext-xform.js` берёт `{v4: uuidv4}` и зовёт
`uuidv4()` без аргументов, генерируя идентификатор правила условного
форматирования. Ни `v3`, ни `v5`, ни `v6`, ни `buf` в дереве не
используются. Проверено grep'ом по `node_modules/exceljs/lib`, а не по
описанию пакета.

**Важно не повторить ошибку в оценке.** При первом разборе риск был занижен
на неверном основании — «exceljs нужен только разовым скриптам импорта».
Это неправда: он приезжает в серверный бандл и разбирает **файлы, которые
загружает пользователь** (импорт потребности, TASK-011). Недоверенный вход
у него есть. Запись действительна не поэтому, а потому что уязвимый API не
вызывается вовсе.

**Почему не закрыто через override.** `uuid 8 → 11` — три мажора. В v9
поменялась схема экспортов (ESM/CJS), и `require('uuid').v4` внутри
`exceljs` может перестать резолвиться; поломка вылезет не на сборке, а при
разборе конкретного xlsx. Менять способ чтения пользовательских файлов ради
API, который не вызывается, — принимать реальный риск вместо нулевого.

**Почему не через `exceljs@3.4.0`.** Именно это предлагает `npm audit fix`,
и это **откат** с 4.x на 3.x, а не обновление. Под ним лежат четыре скрипта
импорта и весь разбор Excel в `src/lib/imports/`.

**Когда пересмотреть — при любом из событий:**

1. `exceljs` выпустил версию с `uuid >= 11.1.1` (тогда просто обновиться);
2. в коде портала появился прямой вызов `v3`/`v5`/`v6` из `uuid`;
3. `exceljs` заменяется на другой парсер (тогда запись снимается вместе с ним).

## Известные ограничения модели безопасности

Проговорены явно, чтобы не выглядеть закрытыми:

- **Разграничения по проектам нет.** `portal_users.projects` заполняется, но
  ни одна RLS-политика по нему не фильтрует — сотрудник видит данные всех
  проектов. См. `backlog.md` SEC-1.
- **Персональные данные кандидатов доступны всем ролям** с разделом
  «Кандидаты», без журнала доступа и политики хранения.
- **`SUPABASE_JWT_SECRET` функционально эквивалентен `service_role`**:
  им подписываются токены доступа, и тем же секретом можно подписать токен,
  обходящий RLS. Хранится только в серверном окружении, в клиентский бандл
  не попадает.
- **CSP пока нет.** Базовые заголовки заданы (см. раздел ниже), но
  `Content-Security-Policy` вводится поэтапно и на момент записи не
  выставлен — внедрённый скрипт исполнится без ограничений.

Подробности и приоритеты — [`AUDIT-2026-07-31.md`](AUDIT-2026-07-31.md).

## HTTP-заголовки безопасности

Задаются в `next.config.ts` через `headers()` с `source: "/:path*"`.

| Заголовок | Значение |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=()` |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` |

**Почему в `next.config.ts`, а не в `src/proxy.ts`.** Matcher middleware
намеренно исключает `_next/static`, `_next/image` и картинки — часть ответов
осталась бы без заголовков. Плюс `proxy.ts` отвечает за доступ и имеет семь
точек возврата: смешивать там контроль доступа и HTTP-политику значит
увеличивать поверхность ошибки в файле, падение которого означает падение
авторизации.

Проверено фактически: заголовки присутствуют на статических страницах
(`/login`), на API-маршрутах (`/api/auth/token`), на статике
(`/_next/static/...`) **и на 307-редиректах, выдаваемых middleware**
(`/` и `/403` для неаутентифицированного запроса).

Сознательно не выставляются:

- **`X-XSS-Protection`** — устаревший заголовок, в отдельных браузерах сам
  порождал уязвимости; современная замена — CSP.
- **`preload` в HSTS** — отдельное обязательство перед hstspreload.org,
  которое трудно отозвать. Брать только убедившись, что вся DNS-зона под
  контролем.

### План ввода CSP

Поэтапно, потому что лобовая политика ломает гидратацию Next.js:

1. **C-2.1** — базовые заголовки. ✅ Сделано.
2. **C-2.2a** — инфраструктура `Content-Security-Policy-Report-Only`.
   ✅ Сделано, политика ниже.
3. **C-2.2b** — фактический сбор нарушений под авторизованной учётной
   записью. ⏳ **Ожидает ручного прогона**, чек-лист ниже.
4. **M-27** — убрать 50 инлайновых `style={{}}`. Обязательно **до** шага 5:
   пока они есть, `style-src` требует `'unsafe-inline'`, и строгая политика
   получится наполовину строгой.
5. **C-2.3** — enforcement с nonce через `proxy.ts`. Цена, которую надо
   учесть заранее: nonce делает динамическими страницы, которые сейчас
   статичны (`/login`, `/403`, `/_not-found`, `/icon.svg`).

### Действующая политика (Report-Only)

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: https:;
font-src 'self';
connect-src 'self' https://<project-ref>.supabase.co;
frame-ancestors 'none';
base-uri 'self';
form-action 'self';
object-src 'none'
```

Пояснения к неочевидным решениям:

- **`connect-src` — точный origin, не `https://*.supabase.co`.** Wildcard
  разрешал бы соединение с любым чужим проектом Supabase, то есть при
  наличии XSS давал бы готовый канал эксфильтрации. Хост подставляется на
  сборке из `NEXT_PUBLIC_SUPABASE_URL`; при отсутствии переменной —
  fallback на wildcard, чтобы сборка не падала.
- **`style-src 'unsafe-inline'`** — уступка ради 50 инлайновых `style={{}}`
  (M-27). Инлайновых `<style>`-блоков в production-HTML при этом **ноль**,
  поэтому после M-27 директиву можно ужесточить до
  `style-src 'self'; style-src-attr 'unsafe-inline'`.
- **`img-src data:`** — стрелка селекта в `primitives.module.css` задана
  через inline SVG data URI.
- **`font-src 'self'`** — `next/font/google` скачивает шрифты на сборке в
  `/_next/static/media`, внешний домен не нужен.
- **`wss:` не добавлен** — Supabase Realtime в портале не используется
  (`.channel()` не вызывается нигде).
- **`report-uri`/`report-to` не заданы** — приёмник отчётов был бы новой
  неаутентифицированной точкой входа без ограничения частоты и без
  логирования, то есть ровно той поверхностью, которую закрывает C-3.
  Нарушения смотрятся в консоли браузера.

### Что уже проверено по C-2.2a

- заголовок формируется корректно и содержит **точный** origin Supabase,
  без wildcard;
- Report-Only ничего не блокирует: заведомо нарушающий инлайновый скрипт
  выполняется, событие приходит с `disposition: "report"`;
- канал репортинга рабочий — контрольные пробы поймали `script-src-elem`
  (инлайновый скрипт) и `connect-src` (`fetch` на посторонний домен), то
  есть ограничение по origin действительно отсекает эксфильтрацию;
- сборка не сломана, `/login` рендерится, маршруты остались статическими.

**Заведомо известное нарушение:** Next.js отдаёт 6 инлайновых `<script>`
с RSC-payload на страницу, и при `script-src 'self'` без nonce они политике
не соответствуют. Это ожидаемо и является измерением для C-2.3, а не
дефектом.

### C-2.2b — чек-лист ручного прогона

**Статус: ⏳ не выполнен.** Требуется учётная запись портала.

**Важно: прогон делать на production-сборке** (`npm run build && npm start`)
или на preview-деплое Vercel, **не** на `next dev`. Dev-сервер добавляет
собственные инлайновые скрипты и `eval` для HMR, которых в production нет —
их нарушения загрязнят картину.

Смотреть в реальных DevTools (вкладка Console): нарушения при разборе
исходного HTML происходят до того, как страница успевает навесить
слушатель `securitypolicyviolation`, и программно их не собрать.

Пройти под каждой из четырёх ролей:

- [ ] вход на `/login`, выход
- [ ] `/403` (раздел, закрытый для роли)
- [ ] Обзор
- [ ] Потребность — матрица, прокрутка, инлайновое редактирование ячейки,
      меню ячейки, дровер истории, массовое добавление
- [ ] Адреса — таблица, карточка, добавление ссылки на документ
- [ ] Кандидаты — таблица, карточка, добавление, экспорт CSV
- [ ] Описание вакансий
- [ ] Ставки — таблица, карточка, удаление
- [ ] Маркетинг, Аналитика, Уведомления
- [ ] Настройки — списки, команда и роли, журнал действий
- [ ] модальные окна (`createPortal` в `document.body`)
- [ ] выпадающие списки, `Combobox`, тосты
- [ ] мобильная ширина — таб-бар, сайдбар

Найденные нарушения записывать сюда с указанием директивы и источника —
на их основе формируется финальная политика C-2.3.
