# RLS-тесты (H-13)

Проверяют политики RLS против настоящего PostgREST на **эфемерном
локальном** Supabase — не против боевого проекта. Архитектура и
обоснование — `docs/AUDIT-2026-07-31.md` (находка H-13),
`docs/ROLLOUT-rls-tests.md`.

## Запуск

**В CI** — автоматически, отдельный job `rls-tests` в
`.github/workflows/ci.yml`. Не требует секретов: все ключи
(`service_role`, JWT-секрет) — значения одноразового локального
контейнера, не имеющие отношения к боевому проекту.

**Локально** — только если на машине есть Docker (Docker Desktop
или аналог):

```bash
npx supabase start
```

Дождаться, пока команда выведет `API URL`, `anon key`, `service_role key`
и `JWT secret`, и задать переменные окружения (имена — см. `env.ts`):

```bash
export RLS_TEST_API_URL=<API URL из вывода>
export RLS_TEST_ANON_KEY=<anon key>
export RLS_TEST_SERVICE_ROLE_KEY=<service_role key>
export RLS_TEST_JWT_SECRET=<JWT secret>
npm run test:rls
```

Затем `npx supabase stop` — контейнеры не нужно оставлять запущенными
между прогонами.

## Структура

| Файл | Назначение |
|---|---|
| `env.ts` | Чтение и проверка переменных окружения — **не** те же имена, что у боевого `NEXT_PUBLIC_SUPABASE_*`, чтобы исключить случайное подключение не туда |
| `jwt.ts` | Подпись тестовых JWT секретом **локального** контейнера (HS256) — не ES256 приложения; проверяется SQL-логика политик, не то, что приложение умеет подписывать токены (это `src/lib/auth/jwt.test.ts`) |
| `client.ts` | Фикстуры и запросы: `service_role` — только для подготовки/очистки данных в обход RLS, сами проверки — через `asUserFetch()` под реальным тестовым пользователем |
| `smoke.rls-test.ts` | Проверяется первым: переменные заданы, PostgREST отвечает, `service_role` реально проходит мимо RLS. Если окружение не готово — падает здесь с понятной причиной, а не десятками случайных ошибок в сценарных тестах |
| `candidates.rls-test.ts` | H-6, прямая колонка `project` — `portal_has_project()` |
| `rates.rls-test.ts` | H-6, `rates` без своей колонки `project` — `portal_has_rate_card_project()` через join |
| `addressDemandHistory.rls-test.ts` | 20260807100300: RLS `address_demand_history` (read-аудитория `demand` шире write-аудитории `addresses`+`settings`, обе — project-scoped) + `staffing_demand_effective()` через `/rpc/` — SUM по нескольким адресам с явным нулём, победа истории при коллизии с ручной строкой, ручная строка без истории не исчезает, RLS фильтрует чужой проект внутри самой функции, не только через `.from()` |

## Принципы

- **Изоляция.** Каждый тестовый файл генерирует свой `testMarker()` —
  уникальную метку, входящую в `login`/`project` фикстур. `afterAll`
  удаляет всё с этой меткой. Тесты не зависят от существующих данных
  в базе и не оставляют следов друг для друга — даже несмотря на то,
  что база эфемерная и всё равно будет уничтожена целиком после job'а.
- **`service_role` — только для фикстур.** Ни один тест не проверяет
  поведение под `service_role` (он не подчиняется RLS вообще, это не
  показательно) — только под реальными ролями портала через
  `asUserFetch()`.
- **Проверяется и HTTP-статус, и код Postgres**, где применимо (`403` +
  `42501` для нарушения RLS) — так тест не сломается, если PostgREST
  когда-нибудь начнёт возвращать тот же смысл другим статусом, но
  останется чувствительным к самой сути отказа.
