# Раздел «Потребность»

Редактируемая матрица потребности в персонале: проекты → города → должности
(строки, три уровня группировки) × даты (колонки). Реальные данные Supabase
(`public.staffing_demand` — числа по датам; `public.staffing_demand_rows` —
статус и комментарий на уровень строки проект+город+должность, не
привязанные к дате). Должности — общий для всех проектов справочник
(`candidate_list_options`, `list_type = 'position'`), тот же, что и в разделе
«Кандидаты»; управляется в Настройках, новых миграций для новых должностей
не требует. Только режим «День» — Неделя/Месяц не реализованы в этой версии.

Общий контекст — [`../../../../../CLAUDE.md`](../../../../../CLAUDE.md) и
[`docs/architecture/system.md`](../../../../../docs/architecture/system.md).

Матрица — единственная таблица портала, которая **не** использует общий
`primitives.table`: у неё редактируемые ячейки с цветом-уровнем, липкие
колонки с обеих сторон и липкий подвал с итогами. Общими остаются только
токены из `portal-tokens.css`.

## Поток данных

```
DemandSection
  → usePortal(): demandRows, demandWindow, refreshDemand,
                  upsertDemandCell, deleteDemandCell, addDemandBulk, listOptions
  → filterDemandRows(demandRows, {search, project, city, position})
  → listVisibleRows(filtered)   — только тройки project+city+position с хотя бы одной записью
  → buildDemandMatrix(filtered)   — 4 уровня: project → city → position → date
  → getDayColumns(demandWindow.from, demandWindow.to)
  → <DemandMatrix> (→ DemandProjectRow → DemandCityGroupRow → DemandPositionRow → DemandCell)
  → <AddDemandModal onSubmit=addDemandBulk>
```

Компонент не обращается к Supabase напрямую — только через `usePortal()`.
CRUD выполняет `lib/supabase/staffingDemandRepo.ts`, вызываемый из
`PortalContext`.

## Бизнес-правила (сводка)

- Строка project+city+position показывается, только если по ней есть хотя
  бы одна запись за видимый период — новую тройку можно завести только через
  «Добавить потребность» (простое редактирование пустой матрицы новую
  строку не создаёт).
- **Должность** — общий для всех проектов справочник
  (`candidate_list_options`, `list_type = 'position'`), тот же источник, что
  и в разделе «Кандидаты»; текст без FK, как и `city`. Добавление новой
  должности в Настройках сразу становится доступно и в «Потребности», и в
  «Кандидатах» — новых миграций не требует.
- Пустая ячейка = потребность не выставлена (нет строки в БД), `0` — валидное
  явное значение «потребность отсутствует».
- Редактирование ячейки: `Enter`/клик вне — сохраняет, `Escape` — отменяет.
  Новое число ≥ 0 → upsert; очистка существующего значения → физическое
  удаление строки (см. `docs/database/schema.md` про отказ от soft-delete именно для
  этой таблицы).
- Итоги считаются по текущей отфильтрованной выборке (после
  `filterDemandRows`), не по всем данным — так же, как в разделе
  «Кандидаты». Итог по городу теперь суммирует все должности города
  (`cityPeriodTotal(matrix, project, city)`), итог по проекту — все города
  (`projectPeriodTotal`).
- Видимое окно дат по умолчанию — сегодня −14/+45 дней
  (`lib/portal/demandWindow.ts`), от реальной текущей даты.
- Массовое добавление — декартово произведение выбранных городов × должностей
  × дат периода с одним и тем же значением; модалка показывает итоговое число
  записей до сохранения. Если это число превышает
  `DEMAND_BULK_CONFIRM_THRESHOLD` (100), перед сохранением показывается
  дополнительный шаг подтверждения — защита от случайного массового
  перезаписывания при большом числе выбранных городов/должностей/дней.
- Модалка «Добавить потребность» может также задать **статус** и
  **комментарий** для всех затронутых пар город+должность одновременно
  (опционально) — это отдельный upsert в `staffing_demand_rows` после
  успешного сохранения количества, не часть `staffing_demand`.
- **Статус и комментарий строки** (`staffing_demand_rows`) — на тройку
  project+city+position, не на дату (перенесено с project+city в рамках
  добавления должностей). Запись создаётся только при первом изменении
  (upsert по `unique(project, city, position)`); её отсутствие в UI =
  `active` + пустой комментарий (`getRowMeta`). Копирование значений (меню
  «⋯», «Повторить строку на следующую неделю», массовое добавление) трогает
  только `staffing_demand` — статус/комментарий никогда не копируются и
  остаются привязаны к исходной тройке project+city+position.
  Обновление одного поля (`status` или `comment`) не затирает другое —
  `mergeRowMetaPatch` объединяет частичный patch с текущими/дефолтными
  значениями перед upsert.
- Фильтр «Статус строки» (`rowStatus` в URL, whitelist `active/paused/
  closed`) применяется к строкам город+проект+должность **после** фильтра
  «Только заполненные» — обе фильтрации работают на уровне строки, не ячейки.
- Сворачивание в матрице — два независимых уровня: проект (как раньше) и
  город (новое, не влияет на соседние города или родительский проект).
  Кнопки «Развернуть/Свернуть все» управляют только уровнем проекта;
  «Развернуть все» дополнительно сбрасывает свёрнутые города.

## Безопасный порядок изменений

1. Найти затронутые файлы раздела и их использования (`PortalApp`, `index.ts`).
2. Прочитать оркестратор, чистую логику (`demandAggregate.ts`/`demandFilters.ts`/
   `demandMetrics.ts`), типы и стили.
3. Логику агрегации/фильтров/итогов менять в `.ts`-файлах, а не в JSX.
4. Не менять публичный API компонентов и `usePortal()` без необходимости.
5. После изменения — `npx tsc --noEmit`, `npm run test`, затем `lint` и `build`.
6. Проверить в браузере (раздел за авторизацией).
