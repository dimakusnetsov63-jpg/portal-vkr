# Раздел «Адреса»

Единая карточка объекта подбора (даркстор/магазин/склад/ПВЗ/ресторан/…) —
потребность, статус набора, характеристики, контакты, комментарии, архив.
Реальные данные Supabase (`public.addresses`). В отличие от «Потребности»,
один объект = одна карточка, без матрицы по датам и без отдельных карточек
по должностям — специализация здесь просто поле карточки.

Общий контекст — [`../../../../../CLAUDE.md`](../../../../../CLAUDE.md) и
[`docs/architecture/system.md`](../../../../../docs/architecture/system.md).
Бизнес-правила подробно — [`docs/requirements/addresses.md`](../../../../../docs/requirements/addresses.md).

## Поток данных

```
AddressesSection
  → usePortal(): addresses, addressesLoading, refreshAddresses,
                  addAddress, saveAddress, archiveAddressRecord,
                  restoreAddressRecord, duplicateAddressRecord,
                  selectedAddressId, openAddressDrawer, listOptions
  → filterAddresses(addresses, {...filters, showArchived})       — для таблицы
  → filterAddresses(addresses, {...filters, showArchived:false}) — для KPI
  → calculateAddressMetrics(addresses, activeFiltered)
  → <AddressesDashboard> + <AddressesTable> + <AddAddressModal>
```

Компонент не обращается к Supabase напрямую — только через `usePortal()`.
CRUD выполняет `lib/supabase/addressesRepo.ts`, вызываемый из
`PortalContext`. Типы — `lib/supabase/addresses.types.ts`, написаны вручную
(миграция ещё не применена к боевой БД, регенерация `database.types.ts`
невозможна) — см. комментарий в файле про `AddressesDatabase` и почему
именно вложенные object-literal типы, а не отдельные `interface`.

## Бизнес-правила (сводка)

- **Один адрес = одна карточка.** Специализация (`position`) — поле, не
  измерение матрицы; тот же справочник, что у «Потребности»/«Кандидатов»
  (`candidate_list_options`, `list_type = position`) — намеренно назван
  `position`, не `specialization`.
- **Архив — сегментированный переключатель**, не отдельная страница/роут.
  Технически soft-delete через `archived_at`.
- **Дефицит и укомплектованность не хранятся** — всегда считаются в
  `addressMetrics.ts` из `required_count`/`staffed_count`. При
  `required_count === 0` укомплектованность явно `100%` — исключение из
  общего правила «пусто/0 → 0%», принятое для этого раздела.
- **KPI дашборда**: «Всего/Активных/Архивных» — всегда по полному набору,
  остальные пять — по отфильтрованной выборке **без архивных записей**, даже
  если открыта вкладка «Архив».
- **Поиск** — по нескольким полям одновременно (адрес, метро, район, город,
  координатор, руководитель объекта), без выбора конкретного поля.
- **Дублирование** очищает служебные поля (id/даты/авторство), добавляет
  `" (копия)"` к адресу и сразу открывает карточку копии.
- **Служебная информация карточки** (создан/обновлён — кем и когда) —
  снимок в самой строке (`created_by(_login)`/`updated_by(_login)`), не
  замена полноценной истории изменений (следующая задача, см.
  requirements/addresses.md).
- **Документы — только ссылки** (`document_links`, jsonb), без загрузки
  файлов: в проекте нет Supabase Storage.
- Все вычисления (поиск/фильтры/сортировка/KPI) — на уже загруженных
  данных; повторный запрос к серверу только после create/update/archive/
  restore/duplicate.

## Безопасный порядок изменений

1. Найти затронутые файлы раздела и их использования (`PortalApp`, `index.ts`).
2. Прочитать оркестратор, чистую логику (`addressFilters.ts`/`addressMetrics.ts`),
   типы (`addresses.types.ts`) и стили.
3. Логику фильтров/агрегации менять в `.ts`-файлах, а не в JSX.
4. Не менять публичный API компонентов и `usePortal()` без необходимости.
5. После изменения — `npx tsc --noEmit`, `npm run test`, затем `lint` и `build`.
6. Проверить в браузере (раздел за авторизацией).

## Известные ограничения
