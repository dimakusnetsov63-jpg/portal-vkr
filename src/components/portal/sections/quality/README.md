# Раздел «Контроль качества»

Два вида проверки: прослушка КЦ (звонок целиком) и прослушка самоотказов.
Вид выбирается первым полем формы и определяет набор критериев; чек-лист
единый для всех проектов, проект — обычное поле из общего справочника.
Бизнес-правила — [`docs/requirements/quality.md`](../../../../../docs/requirements/quality.md),
задача — [`TASK-013`](../../../../../docs/tasks/TASK-013-quality-control.md).

## Что здесь устроено не как в других разделах

**Серверная пагинация.** Остальные разделы грузят весь массив в
`PortalContext` и фильтруют на клиенте. Здесь так нельзя: в исходной таблице
за один июнь 2026 — 2765 проверок. `listReviews` принимает `limit`/`offset` и
возвращает страницу вместе с общим числом; способа «загрузить всё» в
репозитории нет намеренно.

**Данные раздела не живут в `PortalContext`.** Реестр нужен одному разделу и
двум ролям — как список пользователей в `TeamPanel`.

**KPI считает база.** Пять показателей над реестром берутся из
`portal_quality_report`, а не из загруженной страницы: «средний итог по 25
строкам» под подписью «за период» вводил бы в заблуждение.

**Запись только через RPC.** У `quality_reviews` нет INSERT/UPDATE-политик и
грантов вовсе. Итог вычисляет `portal_save_quality_review` — см.
[ADR-006](../../../../../docs/architecture/decisions/ADR-006-quality-score.md).

**Расчёт продублирован.** `qualityScore.ts` считает то же, что SQL, ради
живого превью в форме. Сверку двух реализаций держит `qualityScore.test.ts` —
на двадцати реальных строках из рабочих файлов вместе с процентами, которые
посчитал Excel, — и тест паритета в `quality.rls-test.ts`, прогоняющий один
набор входов через RPC и через `calculateReviewScore`.

**Даты собираются из местных компонентов.** Ни `startOfMonth`, ни дата
проверки по умолчанию не проходят через `toISOString()`: он переводит момент
в UTC, и восточнее Гринвича местная полночь превращается во вчерашний день —
период по умолчанию начинался 31-го числа прошлого месяца (BUG-07 аудита).

**Списки полей подставляют сохранённое значение.** `optionsWithCurrent`
добавляет к активным вариантам справочника то, что уже записано в проверке.
Без этого отключённое значение пропадало из `select`, и следующее
сохранение стирало его молча (BUG-08). Тот же разрыв есть в других разделах
портала — там он не тронут.

**Здесь единственный в портале `localStorage`.** Состав колонок реестра
настраивается и запоминается (`reviewColumns.ts`, ключ
`vkr.quality.reviewColumns`) — команда КЦ попросила выбирать атрибуты, как
шестерёнкой в воронке Битрикса, а несохраняемый выбор сбрасывался бы на
каждой перезагрузке. В хранилище лежит только список идентификаторов
колонок. Разбор чужого содержимого вынесен в чистую функцию с тестами:
испорченная запись должна возвращать умолчания, а не оставлять человека с
таблицей без колонок.

**Обнуление итога — два независимых правила.** Ноль по критическому пункту
и зафиксированное нарушение. Второе живёт не в чек-листе, а отдельным полем,
поэтому `calculateReviewScore` принимает его третьим аргументом. Проценты
блоков в обоих случаях настоящие: на них строится разрез по блокам, а
`has_critical` относится только к первому правилу — путать их в интерфейсе
нельзя, поэтому баннера в карточке два.

**Шаблон сохраняется целиком, одной RPC.** Правка перемешивает вставки,
обновления и удаления по трём таблицам плюс проверку версии — пошаговая
запись оставила бы шаблон в промежуточном состоянии, а по нему в это время
заполняют проверки. Тот же довод, что у `portal_save_vacancy_project_tree`.
Пункт, по которому уже выставляли оценки, при удалении **архивируется**:
удалить его значило бы потерять оценку.

Один действующий шаблон на пару «вид + проект» — частичные уникальные
индексы с самого начала. Отказ объясняется словами, а не сырым
`duplicate key`: до редактора нарушить это было неоткуда, теперь это
рядовая ошибка пользователя.

Вся работа над черновиком редактора — в `checklistDraft.ts`, без React.
Причина не в опрятности: потеря `id` при перестановке не выглядит ошибкой на
экране — строка просто сохранится как новая, а старая уйдёт в архив вместе
со ссылками из прошлых проверок. Такое проверяют тестом, а не глазами.

**Аналитика раздела описана отдельно** —
[`requirements/quality-analytics.md`](../../../../../docs/requirements/quality-analytics.md):
какие показатели считаются, из чего, какие разрезы возможны и чего в данных
нет совсем.

## Границы расчёта

- «Не применимо» исключает пункт из знаменателя, а не считается нулём.
- Блок без зачтённых пунктов и блок с переключателем «Нет» дают прочерк, а
  не ноль.
- Блок «Возражения» показывается, но в итог не входит (`counts_in_total`).
- Ноль по критическому пункту обнуляет итог; проценты блоков остаются
  настоящими.
- Проценты блоков округляются на выходе, итог считается по неокруглённым.
