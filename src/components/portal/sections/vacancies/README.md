# Раздел «Описание вакансии»

Редактируемый справочник условий по вакансии (график, оплата, требования,
оформление, …). Реальные данные Supabase (TASK-010) — заменил статический
`src/lib/portal/vacancyData.ts` (удалён). В отличие от большинства реальных
разделов, структура вакансии не фиксирована: разделы и поля внутри неё
полностью произвольны, кроме одного системного раздела «Общая информация».

Общий контекст — [`../../../../../CLAUDE.md`](../../../../../CLAUDE.md) §6.4.
Бизнес-правила подробно — [`docs/requirements/vacancies.md`](../../../../../docs/requirements/vacancies.md).

## Поток данных

```
VacanciesSection
  → usePortal(): vacancyProjects, vacancyProjectsLoading, addVacancyProject,
                  archiveVacancyProjectRecord, restoreVacancyProjectRecord,
                  duplicateVacancyProjectRecord, selectedVacancyProjectId
  → searchVacancyProjects(query)     — глобальный поиск по всем вакансиям (RPC)
  → <VacancyDetail projectId>
       → getVacancyProjectTree(id)   — лениво, полное дерево одной вакансии
       → buildDraftFromTree(tree)    — при «Редактировать»
       → saveVacancyProjectTree(id, version, draft) — RPC, атомарно
```

Полное дерево конкретной вакансии **не хранится в `PortalContext`** — только
плоский список (`vacancyProjects`) для левой панели. `VacancyDetail` грузит
и держит дерево локально, пересоздавая его при смене `projectId`.

Типы — [`lib/supabase/vacancyProjects.types.ts`](../../../../lib/supabase/vacancyProjects.types.ts),
выведены из `database.types.ts`, кроме `field_type`/`type` вложения
(text+CHECK в БД, узкие литеральные union на уровне приложения). CRUD —
[`lib/supabase/vacancyProjectsRepo.ts`](../../../../lib/supabase/vacancyProjectsRepo.ts).
**Миграции (`supabase/migrations/20260805*`) не применены** — до применения
и регенерации `database.types.ts` типы раздела не проходят проверку
компилятором (ожидаемо, см. комментарий в файле типов).

## Бизнес-правила (сводка)

- **Разделы полностью произвольны** — головной/координатор может
  переименовать, удалить, добавить свой, кроме системного «Общая
  информация» (не удаляется, не архивируется, всегда первый и развёрнут).
- **Чтение — все 4 роли, запись — только head/coordinator.** Гейт записи —
  `portal_can('settings')`, тот же приём, что у справочников в Настройках,
  а не отдельная проверка роли.
- **Пустой раздел скрыт при чтении**, виден при редактировании (чтобы было
  куда добавить первое поле). Раздел с одним полем показывается всегда.
- **Вложения** привязаны к вакансии, привязка к разделу — необязательна;
  при удалении раздела вложение не удаляется, откатывается к общим.
- **Сохранение — одна атомарная RPC-функция**
  (`portal_save_vacancy_project_tree`), не последовательные REST-запросы —
  весь diff (что добавить/изменить/удалить) применяется одной транзакцией
  на стороне базы, с проверкой `version` (оптимистическая блокировка).
- **Дублирование и поиск** тоже идут через RPC
  (`portal_duplicate_vacancy_project`/`search_vacancy_projects`), не через
  клиентскую оркестровку нескольких запросов.
- **`rich_text` — облегчённое подмножество Markdown**, не WYSIWYG.

## Безопасный порядок изменений

1. Найти затронутые файлы раздела и их использования (`PortalApp`, `index.ts`).
2. Прочитать оркестратор, чистую логику (`vacancyTreeDraft.ts`/
   `renderFieldValue.ts`), типы (`vacancyProjects.types.ts`) и миграции.
3. Логику черновика/поиска/видимости менять в `.ts`-файлах, а не в JSX.
4. Не менять форму payload'а `portal_save_vacancy_project_tree` без правки
   и SQL-функции, и `VacancyProjectTreeDraft`, и вызывающего кода.
5. После изменения — `npx tsc --noEmit`, `npm run test`, затем `lint` и
   `build` (до применения миграций typecheck/build ожидаемо показывают
   ошибки конкретно в файлах этого раздела).
6. Проверить в браузере — возможно только после применения миграций.
